# Local/CI Parity Invariants

This document is the authoritative reference for CI/local check parity in ado-git-repo-insights. Every CI quality gate has a verified local equivalent that runs automatically via git hooks, ensuring developers cannot push code that fails CI. The local PR preflight is authoritative by default and fails closed if a CI-hard gate cannot run.

This document records **invariants and contracts**, not point-in-time state. It does not track drift-prone numbers (test counts, historical failure tallies, line offsets, `Last verified` dates, or gate counts). Authoritative values live in the source files the document references — [scripts/run_pr_preflight.py](scripts/run_pr_preflight.py), [scripts/run_repo_hook.py](scripts/run_repo_hook.py), [.github/workflows/ci.yml](.github/workflows/ci.yml), [.pre-commit-config.yaml](.pre-commit-config.yaml), and the hook scripts under [.husky/](.husky/). If a number would need manual updating to stay truthful, it belongs in code, not here.

## How It Works

```
git commit  -->  .husky/pre-commit  -->  run_repo_hook.py pre-commit  -->  Tier 1 checks
git push    -->  .husky/pre-push    -->  run_repo_hook.py pre-push    -->  Tier 2 checks (includes full preflight)
```

The Tier 1 / Tier 2 labels describe *when* a given run fires, not strict hook
exclusivity. A handful of framework-provided hooks in
`.pre-commit-config.yaml` register for both stages (e.g. `detect-private-key`,
`check-added-large-files`, `check-merge-conflict`, `env-guard`,
`tool-version-parity`) and therefore fire on both commit and push — the YAML
is authoritative for the current set.

**Only bypass**: `--no-verify` flag, which is forbidden by project policy.

| 7f  | commitlint | `pnpm exec commitlint --edit` | Weaker\* | [.husky/commit-msg](.husky/commit-msg), [ci.yml](.github/workflows/ci.yml) `commitlint` job | **CI is authoritative.** CI validates all PR commits via `commitlint --from origin/main --to HEAD`. Locally, the `.husky/commit-msg` hook runs `pnpm exec commitlint --edit` — but see Known Inconsistency below. Config: [commitlint.config.cjs](commitlint.config.cjs) extends `@commitlint/config-conventional` with `ratchet` added to `type-enum` for internal ratchet floor-bump commits, ignores merge commits. Semantic-release commits use `HUSKY=0` in CI to bypass hooks — the release commit format (`chore(release): X.Y.Z [skip ci]`) passes commitlint regardless. Pytest guard: [test_hook_guards.py](tests/unit/test_hook_guards.py) `TestCommitlintInfrastructure`.                                                                                                                                                                                                                                                                                                                                  |

**Known Inconsistency (Weaker\*):** The local commit-msg hook depends on husky's internal dispatcher (`.husky/_/commit-msg`) being intact. External tools that manage git hooks (e.g. `entire`) can overwrite this dispatcher, silently breaking the chain to commitlint. A pre-commit health check warns when this is detected and prints the fix command (`pnpm exec husky`), but does **not** block — because the external tool re-injects on every commit, creating an unwinnable loop if the check were fatal. **CI is the authoritative gate.** Malformed commit messages will always be caught on PR, even if the local hook is bypassed. This is an accepted asymmetry: local enforcement is best-effort developer UX; CI enforcement is mandatory.

## Governance

- **Adding a new CI check**: MUST add corresponding local equivalent in `run_repo_hook.py` or `run_pr_preflight.py` before merging. Update this document.
- **Trigger scope alignment**: Pre-commit trigger scope MUST match or exceed the effective compilation scope of the gate it guards. Any file included in a gate's tsconfig (or equivalent config) MUST have a corresponding trigger in `is_test_trigger()` or `is_ui_trigger()`. If a gate compiles files from multiple directories (e.g., `tsconfig.test.json` includes `tests/`, `ui/`, and `types/`), the trigger must fire for changes to any of those directories. Define triggers by what the compiler reads, not by what the developer intends to change. If a tsconfig gains a new include path, add a trigger and a regression test. Regression tests: [tests/unit/test_hook_triggers.py](tests/unit/test_hook_triggers.py).
- **Weakening a local check**: MUST document rationale in this file. CI-hard-gate checks must never exist in a weaker local mode. `python scripts/run_pr_preflight.py --allow-local-degraded` is diagnostic-only and never counts as parity.
- **Pre-commit selectivity (Tier 1 asymmetry)**: Pre-commit gates are intentionally selective — they run only when relevant files are staged, not unconditionally. This is a performance tradeoff: pre-push (Tier 2) runs unconditionally and catches anything pre-commit missed. The asymmetry is between Tier 1 and Tier 2, not between local and CI. This is by design, not a defect.
- **Clean-worktree guards**: Any pre-commit gate that reads the worktree (tsc, parity script, etc.) MUST have a corresponding clean-worktree guard covering its full input scope. The guard blocks commit if unstaged changes exist in any path the gate reads. Current guards: `require_clean_ui_sources()` (extension/ui/), `require_clean_test_compilation_scope()` (extension/tests/, extension/ui/, types/), `require_clean_tsconfigs()` (extension/tsconfig*.json).
- **Entry point alignment**: When adding a new gate to CI or pre-commit, also add it to `pnpm test:ci` in the root `package.json`. The root `test:ci` script is the documented local equivalent of the CI gate chain — if they diverge, `pnpm test:ci` can pass while CI fails. The `test:ci` script runs the suppression audit first, then all CI gates (ruff, mypy, pytest, tsc, eslint, jest, smoke).
- **Verify before commit**: Every new gate, guard, trigger, pathspec, or config change MUST be mechanically verified against real execution before committing. If you cannot point to terminal output proving the change works, do not commit it. Verify the success path AND the failure path.
- **Test count ratcheting**: The authoritative floor lives in [.test-floor-contract.json](.test-floor-contract.json). Both [run_pr_preflight.py](scripts/run_pr_preflight.py) and [ci.yml](.github/workflows/ci.yml) read it via `--min-collected-artifact`; no hardcoded integer exists in either file. The Python floor MUST use the **cross-platform minimum** collected count — see "Platform-Conditional Test Collection" below. Cross-OS equality of the Python floor is enforced by the `python-collection-parity` CI job which compares exact node_id sets between Ubuntu and Windows. The Extension floor uses the exact actual count (single CI environment, no matrix). Zero-tolerance on discovery count; `--max-skips` handles execution variance separately. When adding tests, bump `.test-floor-contract.json` by exactly the delta in the same commit. When removing tests, update with PR justification. Per-commit enforcement is done by **Tier 2 Row 27a** (`check_ratchet_bump.py`), which walks the first-parent range and compares per-commit `floor_delta` vs `actual_delta`. Bypass: `[ratchet-realignment]` or `[ratchet-test-removal]` in the **subject line of the specific commit** that introduced the delta (scanned via `git log --oneline`; markers in bodies are NOT honored; markers on other commits in the range do NOT cover unrelated commits). **Collection-time stability rule**: shared-floor Python tests must be defined unconditionally across the canonical interpreter lane. Python-version branching may change execution (for example, `pytest.skip(...)` inside the test body) but must not hide or create `def test_*` definitions at import time, or the collected floor will drift by interpreter version.
- **`--no-verify`**: Forbidden by project policy. Never bypass git hooks.
- **Reviewing this document**: After any CI pipeline change, verify parity by running the full preflight locally: `python scripts/run_pr_preflight.py`.
- **Split tsconfig architecture**: The extension uses separate configs for type checking (`tsconfig.json`: `module: "ES2022"`, `moduleResolution: "bundler"`) and build emission (`tsconfig.build.json`: `module: "CommonJS"`, `moduleResolution: "bundler"`). The build config MUST emit CommonJS — Node-executed scripts in `dist/` require CJS runtime semantics (`__dirname`, `require()`). The `build:tsc` script in `package.json` MUST reference `tsconfig.build.json` explicitly. **`dist/ui/` is owned exclusively by esbuild (`build:ui`)**; `tsconfig.build.json` MUST NOT include `ui/` — otherwise `build:tsc` silently overwrites IIFE bundles with CJS, breaking browser runtime. Guard: [build-output-format-guard.test.ts](extension/tests/meta/build-output-format-guard.test.ts) pins module + moduleResolution for each config, the build script entry point, and ui/ exclusion from build scope. When upgrading TypeScript, verify both configs resolve to their expected values.

## Platform-Conditional Test Collection

Python CI runs the OS × Python matrix declared in [.github/workflows/ci.yml](.github/workflows/ci.yml). Some tests are platform-specific (e.g., Windows console handler tests). These must **never** use `pytest.mark.skip`, `pytest.mark.skipIf`, or runtime `pytest.skip()` calls because CI enforces `--max-skips=0`. Any form of skip — declarative or runtime — counts against the zero-tolerance gate.

**Pattern**: Platform-conditional tests live in files named `test_*_windows.py` (or `_linux.py`, `_macos.py` when added). The glob patterns that match those files are declared once in [scripts/_platform_test_filters.py](scripts/_platform_test_filters.py) as `PLATFORM_CONDITIONAL_IGNORE_GLOBS` and imported by both [tests/conftest.py](tests/conftest.py) (`collect_ignore_glob` on non-Windows) and [scripts/check_ratchet_bump.py](scripts/check_ratchet_bump.py) (`--ignore-glob` CLI flags for its hermetic subprocess). A parity test in [tests/unit/test_platform_conditional_collection.py](tests/unit/test_platform_conditional_collection.py) asserts at the AST level that **both** call sites import the shared constant — either side dropping the import fails the test immediately, so the filter sets cannot drift.

This means:

- On Windows: all tests are collected (including `test_*_windows.py`)
- On Linux/macOS: files matching `PLATFORM_CONDITIONAL_IGNORE_GLOBS` are never discovered — they don't count as collected or skipped
- The `--min-collected` threshold MUST use the **cross-platform minimum** — the count pytest produces when the shared globs are applied. This is what Linux/macOS cells see and what Windows cells see after the filter is applied.

**Cross-platform minimum vs. Windows hermetic full count**: On a Windows machine, a hermetic `pytest --collect-only` without the platform-conditional `--ignore-glob` filter reports a number **larger** than the floor because it sees the platform-conditional files. The ratchet-bump gate prints both numbers — the floor-comparison number is labeled `cross-platform (Windows-filtered)` and the un-filtered number is labeled `Windows hermetic full count (no platform filter)` — so the Windows-machine developer can reconcile the two. Both numbers come from the same hermetic code path (plugins disabled, `PYTEST_ADDOPTS`/`PYTEST_PLUGINS` scrubbed, `-o addopts=` cleared); the Windows hermetic full count is NOT what a bare `pytest --collect-only` in an arbitrarily-configured developer shell would return — it is what Windows CI cells see, which is the relevant comparison point for ratchet-bump drift. The delta between the two numbers is derived at runtime from `scripts._platform_test_filters.count_platform_conditional_test_functions`, which AST-walks every file matched by `PLATFORM_CONDITIONAL_IGNORE_GLOBS` — never hardcoded, and extensible to Linux/macOS conventions without any helper edit. A Windows-only measured drift test at [tests/unit/test_platform_conditional_collection_windows.py](tests/unit/test_platform_conditional_collection_windows.py) fails if the AST-derived count diverges from the real pytest-measured count (e.g. when a `test_*_windows.py` test is parametrized without updating the helper).

**Adding new platform-conditional tests**:

1. Create a file whose name matches one of the patterns in `PLATFORM_CONDITIONAL_IGNORE_GLOBS` (currently `test_*_windows.py`). If you are adding a Linux- or macOS-only test, extend `PLATFORM_CONDITIONAL_IGNORE_GLOBS` with the new pattern — both conftest and the gate pick it up automatically.
2. Do NOT use `pytest.mark.skip` — use the collection exclusion pattern.
3. Re-measure the cross-platform minimum. The authoritative method is to run the ratchet-bump guard: `python scripts/check_ratchet_bump.py --base-ref origin/main --junit-extension extension/test-results.xml`. Its output line `actual=N (cross-platform (Windows-filtered))` is the correct floor regardless of the developer's OS. (Bare `pytest --collect-only` on a Windows machine over-reports by the platform delta.)
4. Update `python.min_collected` in [.test-floor-contract.json](.test-floor-contract.json) to the reported number in the same commit. Both [run_pr_preflight.py](scripts/run_pr_preflight.py) and [ci.yml](.github/workflows/ci.yml) read from this artifact — no other file needs editing. Cross-OS parity of the new floor is proven by the `python-collection-parity` CI job on each PR.

**Interpreter-version parity rule**: the shared Python floor is measured on the canonical Python lane (`3.12` in CI today), but collection must stay stable across supported interpreters for any test that contributes to that floor. Do not wrap `def test_*` definitions in module- or class-level `if _IS_BASELINE_PYTHON:` branches. If a behavior is baseline-only, define the test unconditionally and call `pytest.skip(...)` inside the body on non-baseline interpreters. That keeps collection stable while preserving runtime semantics.
