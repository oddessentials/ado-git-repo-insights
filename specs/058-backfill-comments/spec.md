# Feature Specification: Historical PR Thread Backfill Subcommand

**Feature Branch**: `058-backfill-comments`
**Created**: 2026-04-16
**Status**: Draft
**Input**: User description: "Add a dedicated backfill-comments CLI subcommand that drains historical PR thread backlogs for review_time computation without re-extracting PR metadata, preserving every existing invariant of the extract --include-comments path."

## Overview

Azure DevOps pull-request thread data is the sole input to this tool's `review_time_minutes` metric. Users who adopted the pipeline before thread extraction was enabled (or who enabled it only after accumulating a large historical dataset) currently see blank review-time panels across months or years of historical PRs. The existing incremental path — `extract --include-comments` — selects PRs newest-first with a fixed per-run cap, which means a churning queue of newly closed PRs can starve historical PRs indefinitely. This feature introduces a dedicated command whose selection, commit, and reporting behavior are purpose-built for historical backlog drainage, with strict preservation of every invariant that governs the existing extraction path.

The feature resolves issue [#251](https://github.com/oddessentials/ado-git-repo-insights/issues/251) in full.

## Clarifications

### Session 2026-04-16

- Q: Does the subcommand emit a structured run-summary artifact on every invocation, and if so, with what schema? → A: Yes — emit a `run_summary.json` artifact whose schema matches the contract already produced by the existing extraction flow, so future pipeline integrations observe both flows through a single, uniform artifact shape.
- Q: What exit-code semantics should a run with per-pull-request failures produce, including the extreme case where every attempted pull request failed? → A: Strict parity with the existing extraction flow — exit zero whenever the loop ran to completion (regardless of per-pull-request failure rate); non-zero is reserved for fatal pre-loop errors. Downstream consumers apply their own failure-rate thresholds by inspecting the `run_summary.json` artifact.
- Q: What mid-run progress visibility should a long-running backfill provide, given that large historical backlogs can take hours? → A: One `INFO`-level log line per processed pull request carrying a running counter (`covered PR <uid> (N of T)`). Deterministic cadence, consistent with the existing per-failure warning shape, log-level-suppressible for users who find it noisy.
- Q: How should the `run_summary.json` artifact surface the identity of pull requests that failed during a run, so operators and future pipeline retry steps can act on specific failures? → A: Append one structured string per failure into the artifact's existing `warnings` list in a parser-stable form (`"backfill-comments: failed to process PR <pull_request_uid>: <normalized error summary>"`). Preserves byte-for-byte schema parity with the existing extraction flow's artifact (committed in Q1) while keeping failed-PR identity machine-readable from the artifact alone.

### Code-Validation Pass — 2026-04-16

This pass validated the spec's load-bearing claims against the actual codebase (not against the feature description) and fixed five concerns where spec language was either ambiguous, semantically incompatible with extract, or internally inconsistent.

- **Truncation-preserve was a latent infinite-loop bug in backfill's workload.** The existing code at `cli.py:616-621` performs a `pass` when `_dropped_threads_all_stored` returns True, leaving the coverage marker in its pre-iteration state. The code comment "Prior stamp (if any) correctly reflects completeness" silently assumes a prior stamp exists — an assumption that holds in extract's newest-first workload but fails in backfill's `comments_extracted_at IS NULL` selection predicate. A PR that entered with NULL stamp and hit this branch would stay NULL, get reselected every run, and loop forever. **FR-015 now FORBIDS the preserved-unset outcome** and renames the branch to "truncation-verified-complete". **FR-015a** locks the resolution path: either a proven-behavior-preserving fix to the shared helper (audit-gated) or a backfill-driver override that does not touch extract's behavior. The Outcome Taxonomy table was updated to remove "preserved-unset" from the set of reachable Processed end-states.
- **`counts.prs_fetched` is semantically incompatible between the two flows.** Code audit showed `cli.py:725` assigns `counts.prs_fetched = summary.total_prs` and `run_summary.py:127` renders it as `"{n} PRs extracted"`. Extract's literal semantic is "count of PR metadata rows fetched from the upstream ADO list API". Backfill fetches zero PR metadata rows, so mapping T to `prs_fetched` would mislead downstream consumers and render a false "N PRs extracted" final line. **FR-019d now mandates `counts.prs_fetched = 0` for backfill** and surfaces T through FR-018a's opening `INFO` line and FR-018b's per-pull-request progress counter. The plan MUST audit existing consumers of `run_summary.json` to confirm no consumer depends on `prs_fetched > 0` as a liveness signal.
- **FR-030f / SC-020 byte-identical source-diff target was brittle.** A harmless internal refactor (comment rewording, import reorder, body refactor preserving all observable behavior) would fail the feature for the wrong reason and encourage churn-avoiding contortions. **FR-025a** reframed the preservation target from "source bytes" to "observable behavior of the public producer surface". **FR-025c** introduced a golden-snapshot test that renders `RunSummary.to_dict()`, `create_minimal_summary`, and `normalize_error_message` against a deterministic fixture and asserts rendered JSON equality. FR-030f and SC-020 now target behavior-preservation.
- **Concurrent-invocation edge case was acknowledged but not fenced.** Two concurrent backfill runs against the same database each materialize their own FR-011a snapshot, can iterate the same pull requests, and emit misleading progress / artifact counts even when DB writes converge. **The concurrent-invocation edge case now explicitly declares concurrent runs unsupported and unfenced**, enumerates the exact misbehaviors that result, and forbids the help text (FR-021) from claiming concurrency safety. Adding a process-level lock is out of scope for this feature.
- **SC-013 was inconsistent with FR-018b and the Outcome Taxonomy.** SC-013 said "every processed pull request produces exactly one INFO-level progress line", but FR-018b requires one line per Attempted pull request (Processed or Failed). **SC-013 now says "Attempted"** to align with FR-018b, and specifies the exact test assertions (INFO count == T, WARNING count == Failed, per-line outcome token matches actual outcome) so the implementation and the test cannot fight each other.

### Planning-Readiness Pass — 2026-04-16

This pass converts remaining deferred decisions into pre-plan constraints so the planning phase has zero architectural branching risk. Every concern below was either a "plan will decide" hedge or an ambiguity a diligent planner would have flagged at the first design review; both are eliminated here.

- **FR-015a was a hedged decision.** The previous wording let the plan choose between a shared-helper fix and a driver override. Both paths carry determinism risk if not locked early — a mid-implementation pivot would invalidate tests and parity guarantees. **FR-015a now locks the approach**: refactor the fetch-and-upsert body out of the stamp decision, place the stamp decision at each caller's loop body, and have backfill apply a simplified 2-outcome stamp rule that never traverses the existing code's "preserve" branch. FR-015b carries the helper shape (`_fetch_and_upsert_threads_for_pr` returning a `FetchOutcome` dataclass). Mode-flag helpers are explicitly forbidden.
- **`counts.prs_updated` semantic expansion was acknowledged but unbounded.** Extract's historical convention is `counts.prs_updated == 0` (no assignment on any code path). Backfill setting it to Processed is a de facto semantic expansion. A downstream consumer relying on the "always zero" invariant could misread a backfill artifact. **FR-019d now locks a pre-plan consumer audit with a three-bucket classification** (no-read / safe-read / unsafe-read) and a pre-authorized fallback: if any Bucket 3 consumer is found, backfill sets `counts.prs_updated = 0` and surfaces Processed through a structured warnings entry. The plan does not need a second decision gate for the fallback.
- **Dual-contract risk (schema parity + semantic divergence) needed an enforcement artifact, not just an acknowledgement.** `counts.prs_fetched = 0` and `counts.prs_updated = Processed` preserve schema shape but change field meanings. **FR-025d now mandates a consumer-audit artifact as a pre-plan deliverable** enumerating every reader of `run_summary.json` in the repository, classifying each into three buckets, and — crucially — designating exactly ONE authoritative discriminator (warnings-prefix, rows_per_csv shape, or joint-condition) that consumers use to distinguish backfill from extract artifacts. The discriminator is locked at plan time, not at implementation time.
- **Concurrent runs were explicitly unfenced but the "no implicit safety claims" contract was not fully enforced.** The edge case warned against concurrency claims in help text only. **FR-024a now forbids implicit safety claims on every user-visible surface** — help text, log messages, artifact content, terminal summary lines — and enumerates the forbidden keyword set (`thread-safe`, `concurrent`, `atomic` outside permitted usage, `complete` in database-wide context, `resumable` without FR-012/013 qualification). SC-025 + FR-030j lock the scan test.
- **Progress-log-before-commit was an implicit timing race.** FR-018b described the line content but not its emission ordering. If a progress line is emitted before commit/rollback resolves, a commit failure would produce a log line that lies about the outcome. **FR-018c now mandates strict ordering**: the progress line is emitted AFTER commit or rollback, with the now-known outcome token. FR-030h locks a test that forces a commit failure mid-loop and asserts the log carries Failed (never Processed).
- **Legacy-schema run and empty-selection run were indistinguishable by shape.** Both produced `Processed = 0, Failed = 0, final_status = "success"` artifacts. A consumer had to parse warnings to tell them apart, but the parsing contract was not locked. **FR-017 now mandates a visibly distinct terminal summary line** (`"skipped (legacy schema; …)"` vs `"processed 0 pull requests (0 failures)"`) and **FR-017a locks the warning-prefix contract** (`"backfill-comments: legacy-schema-skip:"` appears in exactly one artifact category) as the authoritative artifact-level discriminator. FR-030i locks the discriminator test. SC-024 is the enforcement tooth.

After this pass, planning has no remaining architectural branching points. Every pre-plan constraint is either a locked structural decision, a locked test requirement, or a locked audit deliverable. ## User Scenarios & Testing *(mandatory)*

### User Story 1 — Drain a historical backlog to unblock review-time metrics (Priority: P1)

A data administrator manages a database populated by months or years of prior `extract` runs that never fetched thread data. Their review-time dashboard is blank for all historical periods, blocking stakeholder reviews. They need to populate thread coverage for every historical pull request without re-fetching the pull-request metadata already in the database, and they need the tool to prioritize the oldest pull requests lacking coverage so new pull-request activity does not push them out of reach.

**Why this priority**: This is the feature's reason for existing. Without it, a sizable class of users (everyone who ran the tool before enabling thread extraction) cannot unlock the review-time metric regardless of how long they wait for the incremental path to drain.

**Independent Test**: Seed a database with three completed pull requests that lack thread coverage. Invoke the subcommand with valid credentials. Verify that thread data is now stored for all three pull requests and that `review_time_minutes` is populated for pull requests that had reviewer vote activity. Verify that no pull-request metadata row was rewritten by the command.

**Acceptance Scenarios**:

1. **Given** a database with historical completed pull requests that have never had thread data fetched, **When** the user invokes the subcommand with valid credentials, **Then** thread data is fetched for each such pull request and `review_time_minutes` is recomputed for every pull request that now has complete coverage.
2. **Given** a database where the top of the "recently closed" queue churns during the run (new pull requests keep arriving), **When** the subcommand runs to completion, **Then** the oldest uncovered pull request is drained before any newly closed pull request is considered.
3. **Given** a database with a mix of pull requests already covered and pull requests still uncovered, **When** the subcommand runs, **Then** only the uncovered pull requests trigger outbound thread-fetch API calls — covered pull requests are skipped without any API activity.

### User Story 2 — Resume after interruption without rework (Priority: P1)

The same administrator kicks off a backfill against a multi-thousand-PR backlog. Mid-run, the network fails, the session terminates, or they intentionally interrupt the job to free bandwidth. They re-run the same command later and expect the tool to pick up exactly where it left off — with no re-fetching of pull requests whose thread data was already stored, and with full durability of everything that completed before the interruption.

**Why this priority**: Enterprise backfills are long-running. Without resume safety, any failure forces the user to start over, which is practically unacceptable at scale and also wastes API budget. Resume safety is the property that turns this subcommand from a demo into a production tool.

**Independent Test**: Seed a database with ten uncovered pull requests. Run the subcommand, forcing it to abort after the fifth pull request completes. Query the database and confirm the first five are covered and the remaining five are not. Run the subcommand again. Confirm the second run selects and processes exactly the remaining five, and confirm the second run would make zero outbound calls against a fully-drained fixture.

**Acceptance Scenarios**:

1. **Given** a run interrupted after N pull requests have been successfully covered, **When** the subcommand is re-invoked with the same arguments, **Then** the second invocation processes only pull requests not yet covered and leaves the previously covered pull requests untouched.
2. **Given** a database whose backlog has already been fully drained, **When** the subcommand is re-invoked with the same arguments, **Then** zero pull requests are selected, zero outbound thread-fetch API calls are made, and the command exits successfully with a terminal summary indicating the no-op.
3. **Given** a run is interrupted partway through processing an individual pull request, **When** the database is inspected afterwards, **Then** no partial thread rows are present for that pull request, and its coverage marker remains unset so the next run will reprocess it cleanly.

### User Story 3 — Constrain scope to a project or date range (Priority: P2)

A platform owner needs to backfill thread data only for a specific project (to respect a stakeholder's API-budget ceiling) or only for a specific date window (to match a compliance reporting scope). They expect the subcommand to accept the same project and date filters that the existing extraction flow accepts, with identical semantics, so the two flows can be reasoned about as a single consistent surface.

**Why this priority**: This is the correctness guarantee that will let a future pipeline integration forward the triggering pipeline's exact scope to the backfill step — preventing backfill from silently widening coverage beyond what the pipeline owner intends. The filters are correctness knobs, not convenience knobs.

**Independent Test**: Seed a database with uncovered pull requests across two projects and two date windows. Invoke the subcommand with a single-project filter and a `--since` date. Verify that only pull requests matching both filters are processed, that pull requests outside the filter window remain uncovered, and that the coverage counter reflects only the filtered subset.

**Acceptance Scenarios**:

1. **Given** a database with uncovered pull requests in multiple projects, **When** the subcommand is invoked with a project-list filter, **Then** only pull requests whose project matches one of the listed names are selected and processed.
2. **Given** a database with uncovered pull requests spanning a wide closed-date range, **When** the subcommand is invoked with `--since` and `--until` bounds, **Then** only pull requests whose closed date falls within the half-open window `[since, until)` are selected and processed.
3. **Given** a filter combination that matches no pull requests, **When** the subcommand runs, **Then** the command exits successfully with a summary line reporting zero pull requests processed and zero failures — an empty filter is not an error.

### User Story 4 — Isolate individual failures without aborting the run (Priority: P2)

An administrator runs a large backfill and one pull request's thread fetch fails for a non-transient reason (for example, the pull request lives in a repository the PAT no longer has access to, or the ADO service returns an unrecoverable error for that specific pull request). They expect the failure to be isolated to that one pull request: the remaining pull requests continue processing, the failed pull request's coverage marker stays unset so it remains a candidate for future runs, and the overall invocation reports the failure count without exiting non-zero for an otherwise successful run.

**Why this priority**: A hard-abort on a single-PR failure turns a manageable exception into a total outage for every remaining PR, which contradicts the whole purpose of a long-running backfill tool.

**Independent Test**: Seed a database with three uncovered pull requests and arrange for the middle pull request's thread fetch to fail. Run the subcommand and verify that the first and third pull requests are covered, the second pull request's coverage marker remains unset, the terminal summary reports one failure, and the process exit code indicates a successful run.

**Acceptance Scenarios**:

1. **Given** a set of uncovered pull requests where one pull request's thread fetch raises a non-fatal error, **When** the subcommand runs, **Then** the remaining pull requests continue processing uninterrupted and the failed pull request's coverage marker is not set.
2. **Given** a run that had one or more per-pull-request failures but completed the loop, **When** the subcommand finishes, **Then** the terminal summary line reports the processed count and failure count explicitly, and the process exits successfully.
3. **Given** a failed pull request from a prior run, **When** the subcommand is re-invoked, **Then** the previously failed pull request is reselected and a fresh attempt is made.

### Edge Cases

- **Empty database**: A database that contains no completed pull requests at all must result in a successful no-op run reporting zero processed and zero failed.
- **All pull requests already covered**: A database whose completed pull requests all already have coverage must make zero outbound thread-fetch API calls and must exit successfully.
- **Invalid date format on `--since` or `--until`**: Malformed date values must be rejected before any database or network work begins, with an error message that identifies the offending argument and the expected shape.
- **Negative value on any numeric flag**: Must be rejected with the same validation contract that the existing extraction flow already enforces.
- **`--since` greater than `--until`**: Produces an empty selection and exits successfully — this is treated as a valid but non-matching filter combination, not an error.
- **`--limit 0`**: Treated as unbounded; there is no safety cap beyond what the database contains.
- **Database file missing**: Rejected with a clear error before any network work begins.
- **Database missing the thread-storage tables (legacy schema)**: Handled gracefully — the command does not crash and the review-time recompute step skips cleanly rather than failing.
- **Rate limiting from the upstream service**: The existing retry contract applies unchanged; per-pull-request retries are bounded and the loop continues afterward.
- **Interrupt mid-pull-request (Ctrl-C, SIGTERM, process kill)**: The interrupted pull request is left in its pre-iteration state per FR-013a — no partial thread rows, no partial comment rows, coverage marker unchanged. Pull requests whose iterations committed before the signal remain durably persisted. The next invocation reselects the interrupted pull request; it does not reselect the pull requests that committed.
- **New pull requests arriving in the `pull_requests` table mid-loop**: Cannot enter the current run because the selection snapshot is materialized once at run start (FR-011a). They are eligible candidates for the next invocation.
- **Two concurrent invocations against the same database**: **Explicitly unsupported and unfenced.** The subcommand makes no attempt to detect or prevent concurrent invocations. The user is responsible for ensuring at most one backfill process runs against a given database at a time. Running two concurrently produces: (a) duplicate upstream API calls for any pull request both snapshots selected (one invocation's work is wasted); (b) misleading progress lines and `run_summary.json` counts — each invocation reports its own snapshot size as if it were the sole worker, even though the combined database state reflects both; (c) last-write-wins on coverage-marker updates at commit boundaries; partial-thread writes are still prevented by per-pull-request atomicity (FR-012/013), so no corruption of thread rows is possible, but the marker's end state may reflect either invocation's outcome for a given pull request. This is a conscious scope decision — adding a process-level lock is out of scope for this feature and would be a separate follow-up. The documentation (help text, FR-021) MUST NOT claim concurrency safety.
- **A pull request's thread fetch is truncated by a per-pull-request thread cap**: The three truncation branches of FR-015 apply. Truncation-preserve → Processed, marker unchanged. Truncation-clear → Processed, marker cleared, pull request reselected on the next run. Neither branch counts as Failed; both count as Processed per the Outcome Taxonomy.
- **Database has the `pull_requests` table but lacks the `pr_comments` / `pr_threads` tables (legacy schema)**: Classified as a successful no-op per FR-017. A full `run_summary.json` artifact is emitted with `final_status = "success"`, zero counts, `first_fatal_error = null`, and one legacy-schema warning. Exit code zero. This is distinct from a fatal pre-loop error (FR-019c), which has `final_status = "failed"` and a non-null `first_fatal_error`.

## Outcome Taxonomy *(authoritative)*

Every functional requirement and success criterion in this spec that talks about "processed", "failed", or "covered" pull requests uses the following normalized vocabulary. The terms are deliberately distinct because the difference between them is the difference between a well-behaved summary line and a misleading one.

| Term | Definition | Coverage-marker end state |
|------|------------|---------------------------|
| **Attempted** | The pull request's row appeared in the run's materialized selection set and the loop reached its iteration. Identical to the total `T` surfaced in FR-018a. | Any (pre-run state preserved if the attempt raised). |
| **Processed** | The loop iteration for this pull request returned without raising a non-fatal error. Includes all three non-error coverage-marker branches: full-success (stamp set), truncation-verified-complete (stamp set — preserved-unset is forbidden per FR-015), and truncation-clear (stamp cleared because hidden threads have unseen updates). | Either set (full-success, truncation-verified-complete) or cleared (truncation-clear). **No Processed outcome ever leaves the marker in an "unchanged-unset" state** — see FR-015 truncation-verified-complete branch. |
| **Failed** | The loop iteration for this pull request raised a non-fatal error (an `ExtractionError` or semantically equivalent). The run continues with the next pull request. | Unchanged from the pre-run state (the failed attempt neither sets nor clears the marker). |
| **Newly Covered** | A **subset of Processed** where the coverage marker transitioned from unset (NULL or cleared) at run start to set (ISO-8601 timestamp) at run end. This is the count a dashboard operator actually cares about — "how many PRs went from blank to populated". | Set. |
| **Covered (post-run)** | A pull request whose coverage marker holds an ISO-8601 timestamp at the end of the run, regardless of whether this run was responsible for setting it. | Set. |

**Invariants:**

- `Attempted = Processed + Failed` (every attempt either returned or raised; no third outcome).
- `Newly Covered ⊆ Processed` (a pull request must have been attempted without error to become newly covered).
- `Processed` is **not** a superset of `Newly Covered`: the truncation-clear branch of the coverage-marker logic counts as Processed but does **not** count as Newly Covered (its marker is cleared, so a later run will reselect it).
- A pull request that is Failed in one run remains selectable on the next run (its marker was unchanged). A pull request that is Processed-via-truncation-clear also remains selectable on the next run (its marker is cleared). A pull request that is Newly Covered does **not** remain selectable.
- **No processed-but-no-progress state exists by design.** Every Processed pull request either has its marker set (full-success, truncation-verified-complete → removed from next run's selection) or cleared (truncation-clear → reselected, but with the guarantee that the clear happened for a reason that differs from the prior run's state). A Processed pull request can never leave the marker in the same unset state it entered with — FR-015's truncation-verified-complete branch forbids that outcome explicitly to prevent infinite loops.
- The per-pull-request `INFO` progress line (FR-018b) emits a success/failure token that maps to Processed vs. Failed — not to Newly Covered vs. not-newly-covered, because progress lines describe loop iteration outcomes, not coverage-marker transitions.

The authoritative count pair surfaced in the terminal summary line (FR-018) and recorded in the `run_summary.json` artifact is **Processed** and **Failed**. Newly Covered is additional visibility that MAY be surfaced but MUST NOT replace Processed as the primary count, because dashboard operators triaging a backfill need to know the loop outcome first and the coverage-state transition second.

## Requirements *(mandatory)*

### Functional Requirements

#### Selection and ordering

- **FR-001**: The tool MUST expose a new subcommand that initiates a historical thread-coverage backfill on an existing database.
- **FR-002**: Backfill selection MUST include only pull requests with status `completed` and an unset coverage marker; any pull request whose coverage marker is set MUST be excluded from selection.
- **FR-003**: Backfill selection MUST order candidate pull requests by ascending closed date; ties MUST be broken by ascending primary-key identity so that two pull requests closed at the same instant drain in a deterministic, reproducible order across invocations.
- **FR-004**: Backfill MUST accept an optional project-list filter. The filter value MUST be parsed, trimmed, and normalized using the exact same rules the existing extraction flow applies to its equivalent project-list input — comma-separated entries, per-entry whitespace trimming, empty entries dropped, preserved input order, case-sensitive exact match against the pull request's stored project name. If the existing extraction flow exposes a shared parsing helper, backfill MUST reuse it; if the existing flow inlines its parsing, backfill MUST introduce a new helper whose accept/normalize behavior is provably identical to the existing flow's (proven by a parity test). Backfill MUST NOT modify the existing extraction flow's parsing path in the same change.
- **FR-005**: Backfill MUST accept optional inclusive-start (`--since`) and exclusive-end (`--until`) date filters, each in `YYYY-MM-DD` form, applied to the pull request's stored `closed_date` column. The half-open interval convention `[since, until)` MUST match the convention the existing extraction flow applies to its `--start-date` / `--end-date` pair byte-for-byte. Date-shape validation (rejection of malformed strings like `2024-13-99` or `not-a-date`) MUST reuse the existing extraction flow's date-validation helper if one is exposed; if the existing flow inlines its validation, the backfill implementation MUST introduce a new helper whose accept/reject set is provably identical to the existing flow's behavior for every date string (proven by a parity test that feeds the same input set to both paths and asserts matching outcomes). Backfill MUST NOT modify the existing extraction flow's validation path in the same change — preservation of extract's behavior (FR-025) takes precedence over ergonomic code sharing. Date comparisons MUST operate on the stored `closed_date` column's representation without transforming or re-normalizing the stored value.

#### Per-pull-request processing and durability

- **FR-011**: Backfill MUST process selected pull requests one at a time, in the order produced by the selection query (see FR-011a for the selection-snapshot guarantee).
- **FR-011a**: The selection query MUST execute exactly once, at the start of the run, before any pull-request iteration begins. The result set MUST be materialized in full (not consumed as a live cursor) so that rows inserted or modified in the `pull_requests` table during the loop — by any actor, including concurrent processes — cannot widen, narrow, or reorder the run's working set mid-run. The total count `T` surfaced by FR-018a and the per-pull-request ordinal `N` surfaced by FR-018b are both derived from this snapshot and are therefore stable for the duration of the run.
- **FR-012**: Each Processed pull request's entire write set — thread upserts, comment upserts, user-row dependency upserts, and the coverage-marker update — MUST be committed as a single atomic unit before the next pull request's iteration begins. Either every write for the pull request persists together or none do. Partial persistence (some threads but not all, some comments but not all, threads without their coverage-marker update) is a contract violation and MUST be prevented at the transaction-boundary level, not by best-effort cleanup after the fact.
- **FR-013**: A pull request whose iteration raises a non-fatal error MUST have its in-progress write set rolled back in full before the loop continues. The roll-back MUST leave the pull request's database state bit-identical to its pre-iteration state: no partial thread rows, no partial comment rows, no dependency rows added by this iteration, no coverage-marker modification. The same atomic-unit guarantee from FR-012 applies in reverse — either the iteration commits completely or it leaves no trace.
- **FR-013a**: An interruption signal (`SIGINT`, `SIGTERM`, process kill) received during a pull request's in-flight iteration MUST leave that pull request in its pre-iteration state, identical to the FR-013 roll-back outcome. Pull requests whose iterations committed prior to the signal MUST remain durably persisted. The next invocation MUST reselect the interrupted pull request (its coverage marker is still in its pre-iteration state) and MUST NOT reselect the pull requests that committed before the signal (their coverage markers are set or cleared per FR-015).
- **FR-014**: A single pull-request Failed outcome MUST NOT abort the run; processing MUST continue with the next pull request in the materialized selection snapshot.
- **FR-015**: The subcommand MUST maintain the coverage-marker invariant inside the per-pull-request atomic unit defined by FR-012/FR-013 so that the marker state cannot diverge from the thread-row state for any pull request at any commit boundary. The four branches are:
  - **Full-success branch** (fetch untruncated): the marker is set to an ISO-8601 timestamp; all threads and comments from the fetch are committed in the same atomic unit. The pull request counts as Processed and Newly Covered.
  - **Truncation-verified-complete branch** (fetch truncated, and every dropped thread is already stored locally with a `last_updated` at least as recent as the API's reported value): the marker MUST be set to an ISO-8601 timestamp. The combination "truncated fetch + every dropped thread verifiably stored-and-current locally" is sufficient evidence that this pull request's thread coverage is presently complete, and the marker MUST record that completeness regardless of its pre-iteration state. A pre-iteration set stamp MAY be preserved in-place (idempotent for downstream consumers) or refreshed to the current timestamp — both are acceptable because both satisfy `comments_extracted_at IS NOT NULL`, the only predicate downstream consumers evaluate. The pull request counts as Processed and Newly Covered. **This branch explicitly FORBIDS a preserved-unset outcome** (marker remaining NULL after an iteration whose evidence indicates completeness); such an outcome would create an infinite Processed-but-no-progress loop in backfill's oldest-first workload (the pull request would be reselected every run, re-verified every run, and never escape the loop despite each iteration completing without error).
  - **Truncation-clear branch** (fetch truncated, and at least one dropped thread is missing locally or stale): the marker is cleared (set to `NULL`); the threads from the truncated page are still committed so no data is lost. The pull request counts as Processed but NOT Newly Covered; it will be reselected on the next run (FR-002).
  - **Non-fatal-error branch** (`ExtractionError` raised during fetch or during any write): the marker is not touched (neither set nor cleared); no thread, comment, or dependency rows from this iteration persist (per FR-013's atomic-unit roll-back). The pull request counts as Failed and remains selectable on the next run.
- **FR-015a**: Resolving FR-015's truncation-verified-complete requirement under FR-025's preservation rule is a **pre-plan decision, locked here to eliminate mid-implementation branching risk**. The implementation MUST take the following approach, not a shared-helper behavior change:
  - **The existing per-pull-request body at `cli.py:510-651` is refactored into a helper that returns fetch state (threads committed, truncation boolean, dropped-thread list), without applying the coverage-marker update.** The stamp decision is moved to each caller. This is an internal, behavior-preserving refactor of the existing extraction flow's code path — extract's total observable behavior (final stamp state for every reachable input) is unchanged, because extract's caller applies the existing 3-case stamp logic (full-success set / truncation-preserve pass / truncation-clear null) identically to the current inline code.
  - **Backfill's caller applies a simpler 2-outcome stamp decision**: `if the fetch completed without error AND (untruncated OR _dropped_threads_all_stored returns True): set marker to ISO-8601 timestamp; else: leave marker unchanged (which, for backfill's selection predicate, means leave NULL)`. This decision path never traverses the existing code's "preserve" branch, so the preserved-unset outcome is unreachable by construction — not by overriding it after the fact, but by never entering the branch that produces it.
  - **The existing `_dropped_threads_all_stored` helper is reused unchanged.** It is a pure predicate and its behavior is safe to share.
  - **The shared fetch-and-upsert helper MUST NOT contain any "current-subcommand" flag or mode parameter.** The stamp decision is the caller's responsibility, and each caller has its own simple, local decision. Mode-flag helpers hide divergent behavior behind a single call site and break the principle that code should be readable without cross-referencing flag values.

  This locks the structure BEFORE planning: the plan cannot choose "shared-helper fix with audit" because that path is explicitly rejected; it cannot choose "backfill driver override on the post-call state" because that path is also explicitly rejected. The approved path is: **refactor the fetch-and-upsert body out of the stamp decision, then let each caller apply its own stamp decision locally**. The regression lock is the existing `tests/unit/test_extract_comments.py` suite passing unchanged (FR-034).

- **FR-015b**: The pre-plan decision locked in FR-015a implies the helper boundary. The refactor MUST extract a helper with a name and signature that make the fetch/stamp separation obvious — for example, `_fetch_and_upsert_threads_for_pr(client, db, repo, pr_row, max_threads_per_pr) -> FetchOutcome` where `FetchOutcome` carries `status: Literal["ok","failed"]`, `truncated: bool`, and `dropped_threads: list[AdoThread]` — and MUST NOT embed the coverage-marker update inside that helper. The caller-side stamp decision MUST live adjacent to the caller's loop body (either inline or in a small caller-local helper) so that reading the caller makes the stamp policy evident without traversing shared code. The plan MUST carry this helper shape; it is not a plan-time design decision.

#### Review-time recomputation

- **FR-016**: On completion of the loop, the subcommand MUST trigger the same review-time recomputation hook already invoked by the existing extraction and aggregation paths, so that `review_time_minutes` is populated for every pull request that now has complete coverage.
- **FR-017**: A database lacking the thread-storage tables (legacy schema) is NOT treated as a fatal pre-loop error. The subcommand MUST:
  - Detect the legacy-schema condition **before** the selection query runs, so the loop never iterates against an unsupported schema;
  - Classify the run as a **successful no-op** (not a fatal failure);
  - Skip the recomputation hook cleanly rather than invoke it against a schema that does not support it;
  - Emit a `WARNING`-level log line naming the legacy schema as the reason for the short-circuit;
  - Emit a **full** `run_summary.json` artifact per the FR-019a-d chain — NOT the minimal fatal-summary shape defined by FR-019c — with `final_status = "success"`, Processed = 0, Failed = 0, `first_fatal_error = null`, and exactly one warning entry appended to the `warnings` list in the stable form `"backfill-comments: legacy-schema-skip: <reason>"`, where the reason names the missing tables explicitly (for example, `"pr_threads and pr_comments tables not present; run a migration or extract with --include-comments first"`);
  - Emit a terminal summary line that is **visibly distinct** from an empty-selection no-op — specifically `"backfill-comments: skipped (legacy schema; no thread storage tables)"` rather than `"backfill-comments: processed 0 pull requests (0 failures)"`. An operator reading the terminal output MUST be able to tell the two states apart without parsing the artifact;
  - Exit with code zero.
  This categorization decision is load-bearing for artifact-parity semantics: a legacy-schema database produces a well-formed success artifact that downstream consumers can process identically to an empty-but-modern-schema run at the schema level, whereas a fatal pre-loop error (FR-019c) produces the minimal fatal-summary shape distinguished by a non-null `first_fatal_error` field.
- **FR-017a**: The legacy-schema artifact and the empty-selection artifact have identical shape but distinct semantic meaning. To prevent consumer confusion, the artifact discriminator contract is:
  - **Empty-selection run**: `counts.prs_fetched = 0`, `counts.prs_updated = 0`, `warnings` list contains no entry with the `"backfill-comments: legacy-schema-skip:"` prefix. The run ran through to completion; nothing matched.
  - **Legacy-schema run**: `counts.prs_fetched = 0`, `counts.prs_updated = 0`, `warnings` list contains **exactly one** entry with the `"backfill-comments: legacy-schema-skip:"` prefix. The run short-circuited; no iteration occurred.
  The `"backfill-comments: legacy-schema-skip:"` warning prefix is the **authoritative discriminator** between these two states at the artifact level. A test MUST lock this prefix and MUST assert that a consumer parsing the warnings list can unambiguously distinguish the two states — no other warning entry may begin with `"legacy-schema-skip:"`, and the legacy-schema run MUST NOT emit additional warnings that could obscure the discriminator. Consumers documented in the plan's consumer-audit artifact (FR-025d) MUST either dispatch on this prefix or MUST NOT depend on the distinction; any consumer that needs the distinction without parsing the warnings list is in Bucket 3 of FR-025d and requires resolution before merge.

#### Reporting

- **FR-018**: The subcommand MUST emit a single terminal summary line at the end of the run, stating the **Processed** count and the **Failed** count per the Outcome Taxonomy. The line MUST NOT conflate Processed with Newly Covered: a run with Processed = 10, Failed = 0, and Newly Covered = 7 (because 3 pull requests went through the truncation-clear branch) is a fully successful run whose summary line states Processed = 10 / Failed = 0. The Newly Covered count MAY be appended to the summary line as supplementary visibility, but MUST NOT replace the primary Processed / Failed count pair.
- **FR-018a**: At the start of the loop, immediately after the selection snapshot is materialized (FR-011a), the subcommand MUST emit one `INFO`-level log line stating the total count `T` of pull requests the run will attempt. This line is the anchor for the per-pull-request progress counter introduced in FR-018b. `T` is the primary surface for the selection-snapshot size; it does NOT map into `counts.prs_fetched` of the run-summary artifact (see FR-019d for why that mapping is forbidden). `T` is stable for the duration of the run.
- **FR-018b**: During loop execution, the subcommand MUST emit exactly one `INFO`-level log line per Attempted pull request carrying a running counter in the form `(N of T)`, where `N` is the 1-based ordinal of the pull request within the materialized selection snapshot and `T` is the total count emitted by FR-018a. The line MUST include the pull request's stable identifier and a **Processed-or-Failed** outcome token (not a Newly-Covered-or-not token — the progress line describes loop-iteration outcome, not coverage-marker transition). Existing per-pull-request failure `WARNING` lines MUST continue to be emitted in addition to (not in place of) the progress line, preserving the existing per-failure warning shape.
- **FR-018c**: The progress line MUST be emitted **strictly after the per-pull-request outcome is finalized** — that is, after the per-pull-request atomic unit (FR-012) has committed or rolled back and the final outcome (Processed or Failed) is known with certainty. Emitting the progress line before commit/rollback resolution is forbidden because a commit failure after an "optimistic" progress line would produce a log entry that lies about the outcome — the log would claim Processed while the database state and the artifact would reflect Failed. The ordering contract is: (1) fetch threads, (2) perform all upserts inside the transaction, (3) apply the stamp decision, (4) commit or roll back the transaction, (5) **only then** emit the progress line with the now-known outcome token. A test MUST lock this ordering: a fixture that forces a commit failure partway through the loop MUST show the progress line for the affected pull request carrying a Failed token (never Processed), and the log MUST NOT contain an earlier, conflicting progress line for the same pull request.
- **FR-019**: The subcommand's exit code MUST be zero for any run where the loop ran to completion, regardless of the per-pull-request failure rate (including the extreme case where every attempted pull request failed). A non-zero exit code MUST be reserved for fatal errors that prevent the loop from running at all (invalid configuration, unopenable database, unauthenticated upstream). This matches the existing extraction flow's contract byte-for-byte and defers "what counts as an unacceptable failure rate" policy to downstream consumers, who inspect the `run_summary.json` artifact to apply their own thresholds.
- **FR-019a**: The subcommand MUST write a `run_summary.json` artifact to the invocation's artifacts directory on every terminated run — successful runs, runs with per-pull-request failures, and fatal-error runs that never entered the loop. The artifact MUST use the same schema the existing extraction flow produces (status, counts, timings, warnings, per-project status, first fatal error), populated with backfill-specific values where category meanings are analogous (for example, "PRs processed" maps to the extract flow's comparable counter). The artifacts directory MUST honor the same path resolution the existing extraction flow uses, so both flows write to the same location by default.
- **FR-019b**: The `run_summary.json` artifact MUST record the count of pull requests that failed per-pull-request thread fetches, and MUST record the resolved scope of the run (the effective project list and date window, if any) so a downstream consumer can reconstruct what the invocation operated on. For each pull request whose thread fetch raised a non-fatal error during the run, the artifact MUST append one entry to its existing free-form `warnings` list in the parser-stable form `"backfill-comments: failed to process PR <pull_request_uid>: <normalized error summary>"`, where the normalized error summary is produced by the same helper the existing extraction flow uses for its per-pull-request warnings. This keeps failed-pull-request identity machine-readable from the artifact alone without introducing any new typed field that would break schema parity with the existing extraction flow's artifact.
- **FR-019c**: Fatal errors (invalid configuration, missing database, unauthenticated upstream) MUST still produce a minimal `run_summary.json` via the same minimal-summary helper the existing extraction flow uses when it aborts before the main loop. The minimal-summary shape has `final_status = "failed"` and a non-null `first_fatal_error` field carrying the normalized error message; it is the distinguishing feature that separates a fatal pre-loop abort from a legacy-schema successful no-op (FR-017) and from a loop-completed run (FR-019a-b).

### Key Entities

- **Pull request**: The domain record a backfill run operates on. Identified by a stable primary key; classified by status and closed date. The pull request's coverage marker is the authoritative indicator of whether its thread data is complete.
- **Coverage marker**: The per-pull-request field that records whether this pull request's thread data has been fully fetched and stored. Its three states — unset, set-to-timestamp, and the transitional "cleared-after-truncation" — are the sole inputs to backfill selection and to downstream review-time eligibility.
- **Thread**: The unit of upstream data fetched per pull request. Threads and their comments are the raw material from which review timestamps are derived.
- **Backfill run**: A single invocation of the subcommand, bounded by its flag set (organization, database, optional filters, optional caps). A run produces a deterministic set of per-pull-request outcomes (success, failure, or skipped-because-already-covered) and a single structured artifact (`run_summary.json`) that mirrors the schema of the existing extraction flow's artifact so downstream consumers observe both flows identically.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user with a database containing any number of historical completed pull requests lacking thread coverage can, in a single invocation of the new subcommand, drive every selected pull request to full coverage (subject only to a user-supplied limit) without invoking any re-extraction of pull-request metadata.
- **SC-002**: A second invocation of the subcommand against a database whose selected scope has already been fully drained performs zero upstream thread-fetch calls and exits successfully.
- **SC-003**: Under a workload where new pull requests continue to close during a run, the oldest pull request lacking coverage at the start of the run is processed before any newly closed pull request is considered — measurable by seeding a fixture, invoking the subcommand, injecting additional candidates mid-run, and inspecting the processing order.
- **SC-004**: A run in which a single pull request's thread fetch raises a non-fatal error Attempts every other pull request in the selection snapshot, produces Processed and Failed counts consistent with the Outcome Taxonomy in both the terminal summary line and the `run_summary.json` artifact, and exits successfully.
- **SC-005**: After any successful run, every pull request whose coverage marker was set during the run has `review_time_minutes` populated if and only if the pull request's reviewer activity meets the existing review-time eligibility rules.
- **SC-006**: The subcommand's own help output contains, for every flag, a statement of effect, default (where applicable), and permitted shape — verifiable by an automated check against the generated help text.
- **SC-007**: The existing extraction flow's full regression suite passes unchanged on the feature branch. No test in that suite is modified, skipped, deleted, or gated behind environment conditions.
- **SC-008**: No file under the Azure DevOps extension tree, the task manifest, the extension manifest, or the user-facing documentation tree is modified by the feature branch — verifiable by a diff of the merged commit range against the feature base.
- **SC-009**: The full pre-push gate chain defined by the repository's local/CI parity contract (authoritative preflight plus version-guard plus ratchet-bump parity plus cross-OS collection parity) passes end-to-end on the feature branch before merge.
- **SC-010**: The feature closes every acceptance checkbox on issue [#251](https://github.com/oddessentials/ado-git-repo-insights/issues/251) — verifiable by walking each checkbox against the behavior delivered and the tests that lock it.
- **SC-011**: Every invocation of the subcommand — successful, partially failed, or fatally aborted — writes a `run_summary.json` artifact whose schema is byte-for-byte compatible with the artifact produced by the existing extraction flow's equivalent outcome category, verified by a parity test that loads one artifact of each kind and asserts identical key sets and type shapes.
- **SC-012**: A run in which every attempted pull request fails still exits with status code zero, and its `run_summary.json` artifact carries counts accurate enough for a downstream consumer to enforce its own failure-rate policy — verified by a test that drives a 100%-failure fixture and asserts both the exit code and the artifact's failure-count field.
- **SC-013**: During a run, every **Attempted** pull request (Processed or Failed, per the Outcome Taxonomy — NOT just Processed) produces exactly one `INFO`-level progress line with a 1-based counter against the total selection size, and every **Failed** pull request additionally produces its existing `WARNING`-level failure line. Verified by a test that captures the log stream of a mixed-outcome fixture (some Processed, some Failed) and asserts: (a) the `INFO` progress line count equals `T = Processed + Failed`, (b) the `WARNING` failure line count equals Failed, and (c) every progress line carries a Processed-or-Failed outcome token matching the pull request's actual outcome. The wording "Attempted" is deliberate and aligns with FR-018b — conflating Processed with Attempted in the logging contract would cause the test and the implementation to fight each other.
- **SC-014**: A downstream consumer can enumerate every Failed pull request of any terminated run by parsing the `warnings` list in `run_summary.json` alone — verified by a test that runs a mixed-outcome fixture, parses the resulting artifact, and reconstructs the Failed pull-request identifier set without recourse to the log stream.
- **SC-015**: The selection snapshot `T` and per-pull-request ordinal `N` are stable for the duration of a run — verified by a test that materializes a selection of known size, mutates the `pull_requests` table mid-loop (inserts rows that would match the selection predicate), and asserts that neither `T` nor the sequence of processed pull-request identities changes.
- **SC-016**: For every pull request the loop iterates over, the iteration's write set is atomic — verified by a test that forces an exception partway through a pull request's upsert sequence and asserts that the database state is bit-identical to its pre-iteration state (no partial thread rows, no partial comment rows, no coverage-marker modification).
- **SC-017**: An interruption signal received mid-pull-request leaves already-committed pull requests durably persisted and leaves the interrupted pull request in its pre-iteration state — verified by a test that simulates the signal between pull-request iterations and between individual upserts within a single iteration, and asserts the resume-safety invariant holds in both cases.
- **SC-018**: The feature's pull-request-scope and date-scope filter parsing produces the same accept/normalize outcomes as the existing extraction flow's equivalent filters — verified by a parity test that feeds an identical input set to both paths and asserts matching outcomes for every input.
- **SC-019**: The `run_summary.json` artifact produced by backfill has the same top-level key set, the same nested-object key sets, and the same per-field type shapes as the artifact produced by the existing extraction flow — verified by the parity test introduced by FR-025b. The test MUST fail if future work causes either flow's artifact to diverge in shape.
- **SC-020**: The existing extraction flow's observable artifact-producer behavior is preserved on the feature branch — verified by the golden-snapshot test introduced by FR-025c exercising `RunSummary.to_dict()`, `create_minimal_summary`, and `normalize_error_message` against a deterministic fixture. The test asserts rendered JSON equality, which catches every user-observable change while ignoring harmless source-level refactors (comment rewording, import reorder, body refactor that preserves behavior). This is the enforcement tooth behind FR-025a.
- **SC-021**: No file under the user-facing documentation tree is modified, added, or regenerated by any automation the feature branch introduces — verified by a branch-scope diff assertion at merge time that documentation paths have zero diff.
- **SC-022**: The truncation-verified-complete branch NEVER produces a preserved-unset outcome in backfill — verified by a test that seeds a pull request with a pre-iteration NULL marker, forces a truncated fetch whose every dropped thread is already stored and current, runs backfill, and asserts the post-iteration marker is non-null. The same fixture run a second time MUST select zero pull requests (confirming the marker stuck).
- **SC-023**: The progress log line for any pull request reflects that pull request's post-commit / post-rollback outcome — verified by a test that forces a commit failure partway through the loop and asserts the log line for the affected pull request carries a Failed token, with no earlier conflicting Processed token in the log for the same pull request.
- **SC-024**: A consumer of `run_summary.json` can distinguish a legacy-schema run from an empty-selection run by parsing a single stable warning prefix — verified by a test that produces one artifact of each kind against controlled fixtures and asserts the legacy-schema artifact contains exactly one `"backfill-comments: legacy-schema-skip:"` warning while the empty-selection artifact contains zero such warnings.
- **SC-025**: No user-visible surface produced by the subcommand (help text, logs, artifact content, terminal summary) contains forbidden claim-keywords without an accompanying qualifier — verified by a scan test that checks the rendered help output, the log stream of a controlled fixture, and the artifact content for the FR-024a keyword list and fails on any unqualified occurrence.
- **SC-026**: The plan document carries an explicit consumer-audit artifact (FR-025d) that enumerates every reader of `run_summary.json` in the repository and classifies each into the three-bucket taxonomy, with Bucket 3 entries each carrying a resolution (discriminator dispatch, `prs_updated = 0` fallback, or follow-up issue link). The audit artifact is a prerequisite for planning completion — not a deliverable produced mid-implementation.
