# Feature Specification: Cycle-Time Chart PR-Level Detail

**Feature Branch**: `361-cycle-time-pr-drilldown`
**Created**: 2026-05-01
**Status**: Draft
**Input**: User description: "PR-level detail on cycle-time chart drill-down (closes #361). Engineers and managers asking 'which PRs are sitting at this week's P90?' currently get an aggregate dead end — the panel that opens when they click a cycle-time dot shows only headline numbers and a per-repository breakdown. The throughput chart already answers the symmetric 'which PRs merged this week?' question via a PR list section in its drill-down panel. This feature closes the asymmetry by reusing the same PR list pattern on the cycle-time surface, with no producer-side changes."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - See the slow PRs behind a slow week (Priority: P1)

A manager or engineer notices a spike on the cycle-time trend chart — last week's P90 cycle time jumped to 60 hours. They click the P90 dot to investigate. Today, they see only aggregate numbers and a per-repository breakdown, then they have to leave the dashboard to figure out which actual pull requests caused the spike. After this change, the same panel will also list the actual pull requests that drove that week's cycle time, with the slowest ones at the top, and a one-click link straight to each PR in Azure DevOps. They can immediately see whether the spike was driven by one stuck PR, a handful of large refactors, or a broad pattern.

**Why this priority**: This is the entire user-visible value of the feature. Without this story, a manager investigating a slow week still has to leave the dashboard, open Azure DevOps, build a date-bounded query, and cross-reference it against the chart week — a workflow that typically takes several minutes and breaks the flow of investigation. With this story, the same investigation completes inside the dashboard in two clicks. Every other story in this feature is in service of making this one trustworthy and not misleading.

**Independent Test**: Open the dashboard with no filters applied. Click any P50 or P90 dot on the cycle-time trend chart. Verify a list of pull requests appears in the side panel below the per-repository breakdown, with the highest cycle times at the top, and that clicking any row opens that pull request in Azure DevOps in a new tab. Delivering only this story would already give a manager investigating any unfiltered week the answer they need.

**Acceptance Scenarios**:

1. **Given** a week on the cycle-time chart with at least one qualified PR and no team / reviewer / comparison filter active, **When** the user clicks the week's P90 dot, **Then** the side panel opens and shows, in this order: the metric headline (P90 value), the per-repository breakdown, and a list of pull requests for that week with the slowest first.
2. **Given** the side panel is already open showing the PR list for week X's P90, **When** the user clicks the P50 dot for the same week X, **Then** the metric headline at the top updates from "P90" to "P50" but the PR list below stays the same set of pull requests — because both metrics summarize the same underlying week of PRs and showing two identical lists would confuse the user.
3. **Given** the PR list is rendered, **When** the user clicks any PR row, **Then** the corresponding pull request opens in Azure DevOps in a new browser tab, leaving the dashboard state intact.
4. **Given** the PR list is rendered, **When** the user reads the rows top to bottom, **Then** the cycle times decrease (slowest first); ties on cycle time are broken by pull-request identifier, ascending.

### User Story 2 - Sensible behavior under team and reviewer filters (Priority: P2)

The user has applied a team filter (or reviewer filter) and clicks a cycle-time dot. The throughput chart's drill-down already handles this case by replacing its PR list with a short inline message ("Clear the team filter to see PRs"). The cycle-time drill-down should do the same — not show a PR list at all under those filter shapes, since per-PR detail under team or reviewer filters is intentionally deferred to a separate piece of work in the parent catalog. Misleading the user by rendering a partial list, or confusing them with an empty section, is not acceptable.

**Why this priority**: Without this story, applying a team or reviewer filter would either show a misleading PR list (rendered against the unfiltered set, contradicting the user's filter intent) or render a confusing empty state. The throughput chart already solved this; for the cycle-time chart to feel coherent next to it, the messaging must match exactly — same wording, same place in the panel, same dismiss behavior on filter change. Anything else feels like two charts written by two different teams.

**Independent Test**: Apply a single team filter. Click any P50 or P90 dot on the cycle-time chart. Verify the panel shows the same inline "clear the team filter" message that the throughput drill-down already shows under the same filter shape — same wording, same position. Repeat with a single reviewer filter. Verify the matching reviewer message appears.

**Acceptance Scenarios**:

1. **Given** the user has applied at least one team filter and no reviewer filter, **When** they click any cycle-time dot, **Then** the panel's PR-list area is replaced by the inline "clear the team filter" message that is verbally and visually identical to the message the throughput drill-down panel shows under the same filter shape.
2. **Given** the user has applied at least one reviewer filter and no team filter, **When** they click any cycle-time dot, **Then** the panel's PR-list area is replaced by the inline "clear the reviewer filter" message that is verbally and visually identical to the message the throughput drill-down panel shows under the same filter shape.
3. **Given** the user has applied any combination of author and/or repository filters but no team or reviewer filter, **When** they click any cycle-time dot, **Then** the PR list renders normally, showing the filtered week as the throughput drill-down already renders it under the same filter shape.
4. **Given** the user has comparison mode enabled, **When** they click any cycle-time dot, **Then** the existing comparison-mode toast denial fires and no panel opens — behavior is unchanged from today.

### User Story 3 - Honest signaling for high-volume and unavailable-data states (Priority: P3)

For a few high-volume weeks, the underlying PR set may exceed the producer's per-week display cap. In that case, the panel needs to tell the user "you are looking at the slowest N of M PRs" rather than silently truncating. The throughput drill-down already renders this cue when its own list is truncated; the cycle-time list should match.

Likewise, when per-PR detail is unavailable for a week, the section must show a brief inline empty-state message instead of silently disappearing — preserving the panel's section ordering and signaling clearly that the data, not the feature, is the limitation. Per-PR detail is unavailable when (a) the week has zero qualified PRs, (b) the host data is loaded outside an Azure DevOps web context (so PR URLs cannot be composed), or (c) the rollup is malformed in a way that omits the truncation cap marker. The user sees the same inline empty-state message in all three cases — the throughput drill-down already exposes that exact state ("supported-empty") and the cycle-time drill-down must match it.

**Why this priority**: Most weeks will not hit the truncation cap, and the unavailable-data states are uncommon in practice. So this is not the primary value driver. But silently truncating without signaling — or silently dropping the section under unavailable-data conditions — would erode trust in every other view: a user who has been bitten once by a hidden truncation will second-guess every count thereafter. The cost of surfacing the cue is small; the cost of not surfacing it is cumulative across the entire product.

**Independent Test**: For the truncation case, identify (or construct) a week with more qualified PRs than the producer's display cap, click its dot, and verify the same truncation cue the throughput drill-down already shows. For the empty case, construct a fixture week with zero qualified PRs and verify the same `supported-empty` inline message the throughput drill-down already shows for the same condition. (Note: the currently published demo dataset DOES carry per-PR fields, so demo behavior is "renders the PR list" — same as throughput; demo stripping is a separate tracking concern under #315 and this feature stays correct under either outcome.)

**Acceptance Scenarios**:

1. **Given** a week's underlying PR set exceeds the display cap and the user has no team / reviewer / comparison gate active, **When** they click the dot, **Then** the panel renders the same truncation cue the throughput drill-down renders for the same condition.
2. **Given** a week with zero qualified PRs (rare but possible — e.g., all PRs in that week are still open), **When** the user clicks its dot, **Then** the PR list section renders the same `supported-empty` inline message that the throughput drill-down renders for its zero-PR case — section ordering in the panel is preserved.
3. **Given** the dashboard is loaded outside an Azure DevOps web context (so the PR URL composer has no `webContext` to anchor against), **When** the user clicks any cycle-time dot, **Then** the PR list section renders the same `supported-empty` inline message — no half-built rows, no link-less list.
4. **Given** the currently published demo dataset (which includes `prs` arrays, verified at the time of drafting), **When** the user clicks any cycle-time dot, **Then** the PR list renders the same way it would for any other supported-filter dataset — identical to how the throughput drill-down renders the demo. (No demo-specific empty state is forced; the demo's per-PR-stripping question is tracked separately under #315 and this feature behaves correctly regardless of the outcome there.)

### Edge Cases

- **Same week, both metrics clicked back-to-back**: the panel content updates in place; the PR list section does not flicker, vanish, or duplicate. Only the metric-specific headline above the list swaps.
- **Single qualified PR for the week**: the PR list still renders as a single-row list. Subtitle wording stays consistent ("1 PR" vs "N PRs").
- **Comparison mode toggled on while panel is open**: the existing panel-dismiss behavior triggers; no new code path is introduced by this feature.
- **Filters changed while panel is open**: the existing panel-dismiss behavior triggers; no new code path is introduced by this feature.
- **Currently published demo dataset (`docs/data/`)**: includes `prs` arrays at HEAD (verified during spec drafting: e.g., `2025-W28.json` carries 151 PRs with `_prs_cap=500`). On the demo, cycle-time drill-down will render the PR list normally — same as throughput renders today. There is no special "demo empty-state" path. The broader question of whether the demo SHOULD strip per-PR detail (the FR-023 strip gate exists in `scripts/strip_pr_arrays.py` but is not currently being applied to the published demo) is tracked under #315; this feature is data-state-driven and behaves correctly whether or not #315 changes the demo's stripping posture.
- **Host data without comments-metrics capability**: PR rows render with the same columns (title, cycle time, link to ADO) the throughput drill-down rendered before per-row comments counts existed — visually identical layout, no reserved space for absent columns.
- **Host data with comments-metrics capability**: PR rows include the same per-row thread, comment, and unresolved-thread counts the throughput drill-down already shows under the same capability — no new column, no new wording, no new policy introduced here.
- **PR row with partial comments coverage**: when the capability is on but a particular PR's comments coverage is incomplete (a state the producer signals on a per-row basis), the row's comments-metrics cells render the same partial-coverage indicator the throughput drill-down already renders. This feature does not invent new partial-state semantics.
- **Producer-emitted PR order ever drifts**: if a future producer change re-orders the `prs` array away from `cycle_time desc, id asc`, the consumer-side rendered-order assertion (FR-019) fails. Implementation may either trust producer order or sort at the consumer; either way, the test is the source of truth on what the user sees.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: When the user clicks a P50 or P90 dot on the cycle-time trend chart with no team, reviewer, or comparison gate active, the side panel MUST render a list of pull requests for that week, in addition to the existing headline numbers and per-repository breakdown.
- **FR-002**: The PR list MUST appear AFTER the per-repository breakdown in the panel content order, so the user reading top-to-bottom sees aggregate context first, then specific PRs.
- **FR-003**: PR rows MUST be ordered slowest first (cycle time descending; pull-request identifier ascending as the stable tiebreak), so the natural top-of-list scan surfaces the outliers that drove the metric.
- **FR-004**: Each PR row MUST be a click-through hyperlink to the pull request in Azure DevOps; activating the row opens the PR in a new tab/window without disturbing the dashboard state, panel state, or filter state.
- **FR-005**: The PR list rendered for a given week MUST be the same set of pull requests for both the P50 and P90 dots on that week. Switching between the two metric dots while the panel is open MUST update only the metric headline above the list, not the list contents.
- **FR-006**: When the user has applied at least one team filter, the PR list section MUST be replaced with the same `team-inline` message that the throughput drill-down panel shows under the same filter shape — verbally and visually identical, same wording, same position. (This is a distinct content state from the empty-state in FR-011 and from the reviewer message in FR-007.)
- **FR-007**: When the user has applied at least one reviewer filter (and no team filter), the PR list section MUST be replaced with the same `reviewer-inline` message that the throughput drill-down panel shows under the same filter shape — verbally and visually identical. (Distinct from FR-006 and from FR-011.)
- **FR-008**: When the user has applied any combination of author and/or repository filters but no team or reviewer filter, the PR list MUST render the filtered week as the throughput drill-down already renders it under the same filter shape.
- **FR-009**: When comparison mode is active at the moment of click, the existing comparison-mode toast denial behavior MUST remain unchanged: no panel opens, the toast informs the user that drill-down is unavailable in comparison mode.
- **FR-010**: When the underlying PR set for a week exceeds the producer's per-week display cap, the panel MUST render the same truncation cue the throughput drill-down already renders for the same condition. The cue MUST appear whenever the producer flags the week as truncated, and MUST NOT appear when the producer does not flag truncation.
- **FR-011**: When per-PR detail is unavailable for a week — that is, the rollup carries no `prs` array, or the `prs` array is empty, or the host data lacks an Azure DevOps web context for URL composition, or the rollup is malformed in a way that omits the truncation cap marker — the PR list section MUST render the same `supported-empty` inline message that the throughput drill-down renders under the same conditions. The section MUST NOT be omitted; section ordering in the panel is preserved across all data scenarios. The `supported-empty` message is verbally and visually distinct from the team-filter message (FR-006) and the reviewer-filter message (FR-007); it is NOT a "clear the filter" message because no filter is the cause.
- **FR-012**: The PR list section's heading and accessible name MUST remain stable across all four content states (`pr-list`, `supported-empty`, `team-inline`, `reviewer-inline`). Assistive technology hears one consistent section identity regardless of which content state is rendered. Coverage MUST be proven by a consumer-side automated test on the cycle-time drill-down — citation of the throughput equivalent is NOT sufficient, since that test covers throughput-rendered DOM, not cycle-time-rendered DOM.
- **FR-013**: Drill-down activation on the cycle-time chart MUST continue to work via mouse click and via Enter / Space when a dot is keyboard-focused — unchanged from today's behavior. The PR list rows MUST be reachable via Tab once the panel is open, in the same focus order the throughput drill-down already establishes for its PR list. Coverage MUST be proven by consumer-side automated tests on the cycle-time drill-down: at least one test for keyboard activation of a cycle-time dot opening the panel with a PR list, and at least one test for Tab reachability of PR rows inside the cycle-time panel. Citation of the throughput equivalent is NOT sufficient — those tests exercise throughput's chart-side bars, not the cycle-time chart's dots.
- **FR-014**: Switching from the P50 dot to the P90 dot on the same week (or vice versa) without first dismissing the panel MUST update the panel content in place — no close-then-reopen flicker — preserving the existing detail-panel retarget behavior.
- **FR-015**: When the host data carries the comments-metrics capability, the PR list rows MUST display the same per-row thread, comment, and unresolved-thread counts the throughput drill-down already displays under the same capability. When the capability is off, the PR list rows MUST render in a layout visually identical to the pre-capability shape — no reserved column space for absent counts.
- **FR-016**: This feature MUST NOT introduce any change to the producer side — no new database queries, no new aggregator pass, no new fields on any rollup record, no new schema validations, no new migrations. The feature consumes only fields the producer already emits today.
- **FR-017**: This feature MUST NOT add or remove fields on any cross-surface PR-record contract; the existing locked fields plus the existing capability-gated fields are reused as-is.
- **FR-018**: This feature MUST NOT change the behavior of any other chart's drill-down (throughput, reviewer activity, sparkline) or any other panel surface. All previously-passing drill-down behavior on other charts MUST remain unchanged.
- **FR-019**: A consumer-side automated test on the cycle-time drill-down MUST assert the rendered DOM order of PR rows is `cycle_time` descending with `id` ascending as the stable tiebreak. The assertion MUST operate on the rendered output, not on the input array — so the contract holds whether the implementation trusts the producer's existing sort or sorts in the consumer. If a future producer change re-orders the `prs` array, this test fails immediately, surfacing the drift before users see it.
- **FR-020**: The set of new consumer-side automated tests added by this feature (covering at minimum FR-001 through FR-015 and FR-019, with FR-012 and FR-013 specifically requiring coverage on the cycle-time surface as called out in those requirements) MUST be staged in the same change set as the implementation, and the extension test-count contract (`.test-floor-contract.json` `extension.min_collected`) MUST be raised by exactly the count the project's standard ratchet-bump command reports for that change set. There is no marker waiver available for extension drift; the floor MUST equal the actual.

### Key Entities *(include if feature involves data)*

- **Cycle-time week dot**: a clickable point on the cycle-time trend chart representing one ISO week's P50 or P90 cycle time. Carries the week identifier and the metric label.
- **PR list section**: a stable section appended to the cycle-time drill-down panel that, depending on the active filter state and data availability, shows either a list of pull requests, an empty-state message, or a filter-blocked message — but always renders so panel section ordering stays the same across all states.
- **PR row**: one line item inside the PR list, carrying the pull request title, cycle time, the PR's destination URL in Azure DevOps, and (when the comments-metrics capability is on) the per-row thread, comment, and unresolved-thread counts.
- **Filter classification**: the user-facing reading of the active filter set — "no filters / author / repo / author+repo" (PR list shows), "team only" (PR list replaced by clear-team-filter message), "reviewer only" (PR list replaced by clear-reviewer-filter message), or "comparison mode" (drill-down denied entirely).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user investigating "why was last week's cycle time high?" identifies the specific contributing pull request titles in under 30 seconds from the moment they click the dot. Today, the same investigation requires switching to a separate Azure DevOps query and cross-referencing the chart week — a workflow that typically takes several minutes.
- **SC-002**: A user navigates from the cycle-time chart to the underlying pull request in Azure DevOps in exactly two clicks (one click on the dot, one click on the PR row). No additional UI navigation, no separate query, no copy-pasting of identifiers.
- **SC-003**: For 100% of week clicks where the data permits a PR list (the user is unfiltered or has only author / repository filters AND the week has at least one qualified PR AND the host data carries `prs` AND the host data has an Azure DevOps web context AND the rollup carries the cap marker), the panel shows the PR list. There are no silent fall-through cases where the data is present but the section is hidden or replaced.
- **SC-004a**: For 100% of week clicks under a team-only filter (no reviewer filter, no comparison gate), the panel shows the same `team-inline` message that the throughput drill-down already shows for the same filter shape. A user who has learned the team-filter message wording from the throughput chart sees identical wording on the cycle-time chart.
- **SC-004b**: For 100% of week clicks under a reviewer-only filter (no team filter, no comparison gate), the panel shows the same `reviewer-inline` message that the throughput drill-down already shows for the same filter shape. A user who has learned the reviewer-filter message wording from the throughput chart sees identical wording on the cycle-time chart.
- **SC-004c**: For 100% of week clicks where the data does not permit a PR list for non-filter reasons (zero qualified PRs in the week, or the host data is loaded outside an Azure DevOps web context, or the rollup is missing the cap marker), the panel shows the same `supported-empty` inline message that the throughput drill-down already shows for the same conditions — distinct from the team and reviewer filter messages.
- **SC-004d**: For 100% of week clicks under comparison mode, no panel opens; the existing comparison-mode toast denial fires unchanged from today.
- **SC-005**: A user with a screen reader hears the same section identity announced regardless of which of the four content states the section is in (`pr-list`, `supported-empty`, `team-inline`, `reviewer-inline`), because the section's accessible name is content-state-stable. The user does not lose track of where they are in the panel as state changes. Verified by a cycle-time-specific consumer test (FR-012) — not by citation of throughput's equivalent.
- **SC-006**: For every week where the producer's truncation flag is set, 100% of clicks render the truncation cue. For every week where the flag is not set, the cue does not appear. There is no week where the cue's presence and the underlying truncation state disagree.
- **SC-007**: There is zero observable regression in any existing chart behavior, drill-down behavior, panel behavior, or filter behavior on any other chart (throughput, reviewer activity, sparklines). Every previously-passing behavior continues unchanged. Verified by the project's authoritative local preflight (`python scripts/run_pr_preflight.py`) returning exit code 0 with no `--allow-local-degraded` flag, and by every CI gate passing on the resulting PR.
- **SC-008**: The feature ships behind no flag and no rollout gate. From the moment the change is delivered, every user with host data that permits a PR list sees the PR list; every user with comparison mode or team / reviewer filters sees the appropriate message; no opt-in or opt-out is required.
- **SC-009**: A non-technical stakeholder reading this specification's User Story 1 can describe, in their own words and within one minute, what the user sees today and what the user sees after the change. The framing of every other section in the spec serves that primary explanation, not the other way around.
- **SC-010**: The extension test-count contract (`.test-floor-contract.json` `extension.min_collected`) is bumped by exactly the count of new consumer-side tests added in the same change set, measured by the project's standard ratchet-bump command. No marker waiver is attempted on the extension floor (none is available). The Python test-count contract (`python.min_collected`) is unchanged because no producer-side tests are added.
- **SC-011**: The cross-surface PR-record schema-parity gate (`scripts/check_pr_record_schema_parity.py`) returns green on the change set with no field added or removed on any of the four parity-locked surfaces.

## Constraints and Inheritances

These are constraints inherited from upstream features, the constitution, or explicit parent-scope decisions. They shape the feature's boundaries but are not subject to verification (they are policy, not state).

- **Comments-metrics capability is host-controlled and read from the existing source.** Whether the per-row thread, comment, and unresolved counts appear on PR rows is decided by the host artifact's existing capability flag, which is already wired into the throughput drill-down. The cycle-time wiring will read the same flag from the same place via the existing `loader?.getCapabilityState?.()?.commentsMetricsAvailable ?? false` pattern; no new capability surface is introduced.
- **Drill-down policy under team / reviewer filters and in comparison mode is intentionally deferred.** PR-level detail under team-only filters, reviewer-only filters, or comparison mode is excluded from this feature by parent-scope decision (parent catalog #318); the inline filter messages (FR-006 / FR-007) and the comparison toast (FR-009) are the user-facing acknowledgment of those deferrals, not gaps in this feature.
- **Demo state is data-driven, not source-driven.** The feature behaves correctly under either outcome of #315 — if the demo continues to include `prs`, the panel renders the PR list (Verified Input above); if #315 ever strips them, the existing FR-011 `supported-empty` path takes over automatically. No spec change required either way.
- **Test coverage is consumer-surface only.** Because there is no producer-side change, no new producer-side tests are added. Consumer-side automated tests are added alongside the implementation in the cycle-time drill-down's existing test file (and new sibling test files for order / count-parity / capability-off baseline). For FR-012 (section accessible-name stability) and FR-013 (keyboard activation + Tab reachability), the spec explicitly disallows citation of the throughput equivalent — those tests cover throughput-rendered DOM, not cycle-time-rendered DOM, so cycle-time-specific tests are mandatory.
- **Test floor discipline is per-commit.** Any commit that adds N tests MUST bump `.test-floor-contract.json` `extension.min_collected` by exactly N in the same commit. The project's per-commit ratchet (`scripts/check_ratchet_bump.py`, walks first-parent history) flags drift on any commit individually. There is no marker waiver for extension drift. Multiple commits across a feature are allowed as long as each commit is internally consistent (its floor delta equals its test delta). The Python test floor is unchanged because no producer-side tests are added.
- **Final readiness is gated on the authoritative local preflight, not the pre-push hook alone.** Final proof of readiness is `python scripts/run_pr_preflight.py` returning exit code 0 with no `--allow-local-degraded` flag, on a clean working tree, with the extension test floor updated for new Jest tests, and with all generated artifacts (UI bundle, docs shell, broken-docs fixture) in sync. The pre-push hook invokes the preflight as one of its steps; the preflight is the authoritative arbiter on its own.

## Out of Scope

The following are explicitly NOT part of this feature and are deferred to separate scopes per the parent catalog (#318):

- PR-level detail under a team-only filter. The team-filter case shows an inline "clear the filter" message instead. Scoping per-team PR detail is a separate slice with different shape requirements.
- PR-level detail under a reviewer-only filter. Same deferral, same separate slice.
- PR-level detail in comparison mode. The existing comparison-mode toast denial covers all drill-down surfaces uniformly; revising the comparison-mode policy is a separate decision that affects every chart, not just this one.
- Any new field on the PR-record contract. The locked fields are reused as-is; introducing a new field is a separate scope item with cross-surface contract implications.
- Cross-dimension aggregates inside the panel (for example, per-author × per-repository tables). These are separate catalog items with their own UX considerations.
- PR-level detail on other charts (reviewer activity, sparkline). Each is a separate issue with its own data shape.
- Any change to the cycle-time chart itself (axes, dot rendering, tooltip content). The chart already emits the click hooks this feature needs.
- Any change to the public demo dataset (`docs/data/`). Whether the demo continues to include `prs` arrays (the current state) or begins stripping them (tracked under #315) is independent of this feature; cycle-time drill-down behavior is data-state-driven and renders the appropriate state in either case.
