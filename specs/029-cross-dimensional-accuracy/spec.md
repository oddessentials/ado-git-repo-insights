# Feature Specification: Cross-Dimensional Filter Accuracy

**Feature Branch**: `029-cross-dimensional-accuracy`
**Created**: 2026-02-11
**Status**: Draft
**Input**: User description: "Cross-dimensional filter accuracy for combined multi-filter dashboard metrics"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Accurate Team+Repository Metrics (Priority: P1)

An engineering manager selects both a specific team (e.g., "Team Alpha") and a specific
repository (e.g., "Backend API") in the dashboard filters. The dashboard displays exact
PR metrics (count, cycle time P50/P90, reviewer count) for that team-repository
intersection rather than an approximation. The manager uses these numbers to assess how
a particular team performs in a particular codebase and make resourcing decisions.

**Why this priority**: This is the most common multi-filter combination. Teams often
specialize in specific repositories, making the current proportional approximation
inaccurate by up to 60%. Incorrect data leads to wrong resourcing and performance
conclusions.

**Independent Test**: Can be fully tested by selecting a team and repository filter
simultaneously and comparing displayed metrics against known exact values from the
underlying PR data. Delivers immediate accuracy improvement for the primary use case.

**Acceptance Scenarios**:

1. **Given** a dashboard with team and repository data loaded, **When** a user selects
   one team and one repository filter simultaneously, **Then** the dashboard displays
   exact PR count, cycle time P50, cycle time P90, authors count, and reviewers count
   for that specific team-repository intersection.

2. **Given** a dashboard with team and repository data loaded, **When** a user selects
   multiple teams and multiple repositories simultaneously, **Then** the dashboard
   aggregates exact intersection metrics across all selected team-repository pairs.

3. **Given** a team that works exclusively in one repository, **When** the user selects
   that team plus that repository, **Then** the displayed PR count matches the team's
   total PR count (not a proportional underestimate).

4. **Given** a team that never contributes to a specific repository, **When** the user
   selects that team plus that repository, **Then** the dashboard displays zero PRs
   (not a non-zero proportional estimate).

---

### User Story 2 - Graceful Fallback for Legacy Data (Priority: P2)

A user views historical data from before cross-dimensional breakdowns were generated.
The dashboard seamlessly falls back to the existing proportional approximation without
errors or confusing UI changes. The user is not aware of any difference in behavior
other than the data being an approximation rather than exact.

**Why this priority**: Backward compatibility is essential. Users have existing datasets
and pipeline artifacts that lack cross-dimensional fields. The dashboard must continue
to function correctly with older data.

**Independent Test**: Can be tested by loading a dataset that does not contain
cross-dimensional breakdown fields and verifying that all existing filter combinations
continue to work with proportional estimates.

**Acceptance Scenarios**:

1. **Given** a dataset without cross-dimensional breakdown fields, **When** a user
   selects team and repository filters simultaneously, **Then** the dashboard uses
   the existing proportional intersection estimate and displays results without errors.

2. **Given** a dataset with a mix of weeks (some with cross-dimensional data, some
   without), **When** a user views a time range spanning both types, **Then** the
   dashboard uses exact data where available and proportional estimates where not,
   producing a seamless time series.

3. **Given** a dataset generated by an older version of the aggregation pipeline,
   **When** loaded into a dashboard that supports cross-dimensional accuracy, **Then**
   no validation errors occur and all existing functionality works unchanged.

---

### User Story 3 - Author-Repository Intersection Accuracy (Priority: P3)

A team lead selects a specific author and a specific repository to see that individual's
contribution metrics in a particular codebase. The dashboard provides exact metrics for
that author-repository intersection once author filters are implemented (dependency on
Author Contributor Filters feature).

**Why this priority**: Author-repository intersection is the second most common combined
filter pattern, but depends on the Author Contributor Filters feature being implemented
first. This story establishes the cross-dimensional data generation for future use.

**Independent Test**: Can be tested once author filters are available by selecting an
author and repository filter simultaneously and verifying exact intersection metrics.

**Acceptance Scenarios**:

1. **Given** a dashboard with author and repository data loaded, **When** a user
   selects one author and one repository, **Then** the dashboard displays exact PR
   metrics for that author in that specific repository.

2. **Given** an author who contributes to multiple repositories, **When** the user
   selects that author and one specific repository, **Then** only PRs from that
   repository are counted (not the author's total across all repos).

### Edge Cases

- What happens when a user selects all teams and all repositories? The exact intersection
  should equal the unfiltered total (consistency check).
- What happens when a team has zero PRs in a selected repository? The dashboard should
  show zero, not omit the team from results.
- What happens when team membership changes between weeks? Each week's cross-dimensional
  data reflects the team membership at extraction time, which may differ across weeks.
  Historical cross-dimensional data is not retroactively updated when team rosters change.
- What happens when cross-dimensional data is available for some weeks but not others
  within the selected date range? Per-week accuracy is derived from the presence or absence
  of the `by_team_and_repo` field (present = "exact", absent = "estimated") so the
  dashboard can surface which weeks use exact data and which use proportional fallback.
  No separate stored accuracy flag is needed. Without this distinction, trend lines that
  silently mix methods may appear as data corruption to users.
- What happens when the sparse data structure has no entry for a team-repo pair? This
  means zero PRs for that intersection, not missing data. The dashboard must treat a
  missing key as zero, never as undefined or NaN.
- What happens when a very large organization (50+ teams, 100+ repos) loads the dashboard?
  The additional data size (~50KB per week for team-repo alone) should not noticeably
  degrade performance. With author intersections added later (potentially 200+ authors x
  100 repos), per-week size could grow significantly. The system MUST define and enforce:
  (a) an upper bound on intersection entry count per week (e.g., 5,000 entries), (b) a
  maximum per-week JSON size threshold (e.g., 500KB), and (c) performance testing MUST
  use a hard reference dataset at the upper bound (50 teams, 100 repos, 200 authors,
  260 weeks).
- What happens when a single filter dimension is active (e.g., team only)? The existing
  single-dimension behavior is unchanged; cross-dimensional data is not consulted.
- What happens when numbers change as filters are added/removed? Users may see different
  totals when they add a second filter because the exact intersection replaces the
  approximation. This is expected and correct behavior (not a bug).
- What happens when a team or repository is renamed between extraction runs?
  Cross-dimensional breakdown keys use display names (matching the existing by_team
  convention), so renamed entities will produce fragmented time-series across the
  rename boundary. This is a known limitation accepted for backward compatibility.
  The dimensions data exposes stable IDs (`team_id`, `repository_id`) to enable a
  future migration to ID-based keys.
- What happens when a PR author belongs to no team? That author's PRs must NOT appear
  in any team-keyed cross-dimensional entry but must still appear in repository-only
  and global totals.
- What happens when a PR author belongs to multiple teams? That PR appears in each
  team's cross-dimensional entry for the relevant repository. This means: the sum of PR
  counts across all teams for a given repository will exceed that repository's
  single-dimension total. This violates naive aggregation expectations and MUST be
  communicated to the user (e.g., a visible indicator or tooltip explaining that
  multi-team membership causes intentional overlap in team-level counts).
- What happens when three or more filter dimensions are active simultaneously (e.g.,
  team + repository + author)? The system applies a deterministic resolution order:
  (1) team-by-repository exact data is used first if both team and repository filters
  are active, (2) author-by-repository exact data is used first if both author and
  repository filters are active but team is not, (3) the remaining unsupported dimension
  is applied via proportional estimation on top of the exact two-way result. This order
  is fixed, not user-configurable. Multi-team overlap in the exact pair is handled
  before the proportional step is applied.
- What happens when a platform/infrastructure team contributes to most repositories?
  That team's cross-dimensional data will be dense (many entries) rather than sparse.
  The system must handle dense matrices correctly without performance degradation.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST generate exact cross-dimensional breakdown data for
  team-repository pairs in weekly rollup outputs when team data is available.
- **FR-002**: The system MUST store cross-dimensional data in a sparse format, including
  only non-empty intersections (team-repo pairs with at least one PR).
- **FR-003**: The dashboard MUST prefer exact cross-dimensional data when available and
  fall back to proportional intersection estimates when the data is absent.
- **FR-004**: The system MUST maintain consistency between cross-dimensional breakdowns
  and single-dimension breakdowns for `pr_count`: the sum of `pr_count` across all repo
  entries within a team's cross-dimensional data MUST equal that team's single-dimension
  `pr_count` total. This invariant does NOT apply to `authors_count` or `reviewers_count`
  (distinct-count metrics are not additive across repos within a team).
- **FR-005**: The dashboard MUST continue to function correctly with datasets that lack
  cross-dimensional breakdown fields (backward compatibility).
- **FR-006**: The system MUST generate cross-dimensional breakdown data for
  author-repository pairs in weekly rollup outputs when author dimension data is
  available (depends on Author Contributor Filters feature).
- **FR-007**: The cross-dimensional breakdown fields MUST be optional (additive schema
  change) and require no data migration. The aggregates schema version MUST be bumped
  (minor increment) to signal to downstream consumers that cross-dimensional fields may
  be present. Consumers that cache schema assumptions need a version signal to invalidate
  stale assumptions when processing mixed datasets.
- **FR-008**: Each cross-dimensional breakdown entry MUST include the same metrics as
  single-dimension breakdowns: PR count, cycle time P50, cycle time P90, authors count,
  and reviewers count — subject to FR-019 minimum sample size threshold.
- **FR-009**: The system MUST NOT generate cross-dimensional data when the source
  dimension data is unavailable (e.g., no team data extracted, no author filter
  implemented yet).
- **FR-010**: The synthetic data generator MUST produce cross-dimensional breakdown
  fields to support dashboard testing and demonstration.
- **FR-011**: The system MUST expose a `features.cross_dimensional` boolean in the
  output manifest to signal that cross-dimensional breakdown data is available in the
  generated rollups.
- **FR-012**: Only two-way cross-dimensional pairs are supported in this feature scope:
  team-by-repository and author-by-repository. Three-way or higher-order intersections
  (e.g., team + repository + author) are out of scope and continue to use proportional
  estimation for the unsupported dimension.
- **FR-013**: PRs authored by users with no team membership MUST NOT appear in any
  team-keyed cross-dimensional entry. These PRs remain visible in repository-only and
  global aggregates.
- **FR-014**: The dashboard MUST derive per-week accuracy from the presence or absence
  of the cross-dimensional breakdown field (e.g., `by_team_and_repo` present = "exact",
  absent = "estimated"). When both team and repository filters are active and the visible
  date range includes weeks without cross-dimensional data, the dashboard MUST surface
  a visible indicator (e.g., tooltip or muted icon) explaining that some weeks use
  approximate data.
- **FR-015**: Cross-dimensional breakdown keys MUST use `team_name` and
  `repository_name` as keys, matching the existing `by_team` and `by_repository`
  keying convention. This preserves backward compatibility with the current dashboard
  contract. The dimensions data already exposes stable identifiers (`team_id`,
  `repository_id`) for a future migration to ID-based keys. Renames will cause
  time-series fragmentation under name-based keys; this is a known limitation
  documented in edge cases.
- **FR-016**: When multiple teams are selected and authors belong to more than one
  selected team, the dashboard MUST visually indicate that multi-team overlap causes
  team-level totals to exceed repository-level totals (e.g., tooltip or footnote
  explaining the intentional duplication).
- **FR-017**: The system MUST define and enforce an upper bound of 5,000 cross-dimensional
  intersection entries per week and a maximum per-week rollup JSON size of 500KB. If the
  threshold is exceeded, the system MUST log a warning, truncate the least-significant
  intersections (by PR count), and set a `_truncated` flag on the rollup to signal that
  the consistency invariant (FR-004) is relaxed for affected teams (truncated sum will be
  less than the team total).
- **FR-018**: When three or more filter dimensions are active, the system MUST apply
  a deterministic, fixed resolution order: team-by-repository is preferred when both
  team and repository are active; author-by-repository is used when author and
  repository are active without team. The remaining dimension uses proportional
  estimation applied on top of the exact two-way result.
- **FR-019**: The system MUST set cycle time P50 and P90 to null for cross-dimensional
  intersection entries with fewer than 5 PRs. Percentiles computed from 1-4 data points
  are statistically unreliable and may mislead users. The frontend already handles null
  cycle time values gracefully (skipping them in weighted-average aggregation).

### Key Entities

- **Cross-Dimensional Breakdown**: A nested data structure mapping one dimension (e.g.,
  team name) to another dimension (e.g., repository name) to a set of PR metrics. Only
  non-empty intersections are stored (sparse representation).
- **Breakdown Entry**: A set of PR metrics for a specific intersection: PR count, cycle
  time P50, cycle time P90, authors count, reviewers count.
- **Weekly Rollup**: The existing unit of aggregated data, extended with optional
  cross-dimensional breakdown fields alongside existing single-dimension breakdowns.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: When both team and repository filters are active and cross-dimensional
  data is available, displayed PR count is 100% exact (matching values computed from
  underlying PR data). Cycle time P50 and P90 are exact per individual cross-dimensional
  entry; when multiple entries are aggregated (e.g., selecting 2 teams + 3 repos), cycle
  times use PR-weighted averaging of per-entry percentiles (not true combined percentiles).
  `authors_count` and `reviewers_count` are exact per individual entry but are upper-bound
  sums when aggregated across entries (a single author contributing to two repos within
  the same team is counted in both entries). This eliminates the current up to 60% error
  from proportional estimates for PR count entirely and substantially improves accuracy
  for all other metrics.
- **SC-002**: Dashboard load time with cross-dimensional data increases by less than
  10% compared to the same dataset without cross-dimensional data, even for large
  organizations (50+ teams, 100+ repos).
- **SC-003**: 100% backward compatibility: all existing datasets without cross-dimensional
  fields continue to load and function identically to current behavior.
- **SC-004**: Cross-dimensional data adds no more than 15% to weekly rollup file sizes
  for typical organizations (20 teams, 30 repos).
- **SC-005**: The sum of PR counts across all repository entries within a team's
  cross-dimensional data equals the team's single-dimension PR count total for every
  weekly rollup (data consistency guarantee). Note: this invariant applies only to
  `pr_count`. `authors_count` and `reviewers_count` are distinct-count metrics and are
  NOT additive across repos within a team (a single author contributing to multiple repos
  is counted in each). Therefore `sum(by_team_and_repo[T][*].authors_count) >=
  by_team[T].authors_count` is expected.
- **SC-006**: For any team-repository pair where the proportional estimate previously
  differed from the exact PR count, the displayed value now matches the exact count
  (error rate drops from up to 60% to 0% for PR count). This directly improves trust
  in dashboard data for team-level resourcing decisions.
- **SC-007**: Pipeline aggregation time increases by less than 30 seconds for large
  organizations (50+ teams, 100+ repos, 260 weeks) when generating cross-dimensional
  breakdowns.
- **SC-008**: No weekly rollup file exceeds 500KB in JSON size for the hard reference
  dataset (50 teams, 100 repos, 200 authors, 260 weeks).
- **SC-009**: Time-series trend lines for mixed exact/estimated date ranges display a
  per-week accuracy indicator that allows users to distinguish exact from estimated
  data points.

## Assumptions

- Team membership data is available from the extraction pipeline (team filter is 95%
  complete per TODO/TEAM_REVIEWER_FILTERS.md).
- Author dimension data may not yet be available; author-repository cross-dimensional
  breakdowns are generated only when the Author Contributor Filters feature is complete.
- The sparse storage approach is valid for most organizations: typical orgs have partial
  overlap between teams and repositories, not full Cartesian product coverage. However,
  organizations with platform/infrastructure teams that contribute to many repositories
  will produce denser matrices; the system must handle both sparse and dense cases.
- Existing PowerBI users are not affected because cross-dimensional data appears in JSON
  aggregates only, not in the CSV export contract.
- Team membership changes between extraction runs are reflected in subsequent weeks' data;
  historical cross-dimensional data is not retroactively updated. A developer who moves
  teams mid-quarter will have historical PRs attributed to their old team in past weeks.
- Competing developer analytics tools (LinearB, Swarmia, DevLake) already deliver exact
  cross-dimensional data from actual intersection queries. The current proportional
  approximation is a competitive gap, especially for enterprise evaluation/POC scenarios
  where a 60% error is disqualifying.
- The dashboard should silently use exact data when available. When proportional
  estimates are used (legacy weeks), a subtle per-week indicator (e.g., tooltip or
  muted icon) surfaces the distinction. Confidence scores or error bars are not
  appropriate as they signal unreliability to non-technical users.
- Cross-dimensional breakdown keys use `team_name` and `repository_name` (matching
  the existing `by_team`/`by_repository` convention). The dimensions data already
  exposes `team_id` and `repository_id` for a future ID-based key migration. Team
  or repository renames will fragment time-series data under name-based keys; this
  is a known limitation traded off against backward compatibility.
- Performance testing MUST use a hard reference dataset at the defined upper bound
  (50 teams, 100 repos, 200 authors, 260 weeks) to validate all size and time
  thresholds before release.
