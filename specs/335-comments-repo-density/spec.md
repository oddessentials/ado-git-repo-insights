## Overview

This feature adds a per-repo comment-density breakdown to the dashboard's Metrics tab. It is the SECOND of three sibling Cap-2 dimension PRs (#334 author shipped on PR #349; this PR for repo; #336 for reviewer); the visual + interaction pattern locked in #334 is inherited verbatim with the per-repo-specific simplifications enumerated in the Background section. Sibling #321 (per-team) is deferred pending team-at-time-of-PR history modeling.

**Why now**: The drill-down (310) shows per-PR thread / comment / active-thread counts; the trend chart (333) shows weekly volume; the per-author breakdown (334) ranks authors by discussion load. Together they answer "is volume rising?" and "are any authors outliers?" — but they do not answer "are any repositories outliers in discussion volume — either producing or attracting it?" Repository concentration of review-conversation load is the cross-cutting view that surfaces ownership, complexity, and review-quality patterns at the codebase-unit granularity rather than the person-unit granularity. Today the existing `by_repository` per-week emission carries throughput-only metrics; nothing renders repository-level comments-density on a dashboard surface.

The feature is additive and gated on `capabilities.comments_metrics`. The dashboard MUST render byte-identical to its current rendering for users without comment extraction enabled (analog of 333 SC-1-04 / 334 SC-1-03 for this feature's namespace).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Identify highest-load repositories at a glance (Priority: P1)

A team lead opens the dashboard's Metrics tab on a Monday morning and wants to see which repositories are producing or attracting the most review-conversation load over the last quarter. They look at the new per-repo comment-density breakdown — positioned just below the per-author breakdown — and immediately see the top-N repositories ranked by their chosen count metric (default `comment_count`). Without sorting beyond the default, they identify outliers and notice if any repository's contribution differs sharply from the median.

**Why this priority**: This is the entire user-visible reason the feature exists. #322's Capability-2 repo-dimension ask was articulated as "are any repositories outliers in discussion volume?" Without P1 the feature has no value; the chart's first-glance readability is the success criterion.

**Independent Test**: Open a demo dashboard with `capabilities.comments_metrics` enabled and ≥10 distinct repositories with mixed comment-load. Confirm a chart titled with repository / density vocabulary renders below the 334 per-author breakdown on the Metrics tab. Confirm rows are ordered by `comment_count` descending. Confirm the date-range filter narrows the visible set when changed. Sort toggle (US2), capability-off (US3), and filter-not-supported posture (US4) are not required to be present for this test.

**Acceptance Scenarios**:

1. **Given** a dataset where `capabilities.comments_metrics` is enabled and the visible date range contains ≥10 repositories with non-zero comment activity, **When** the user opens the Metrics tab, **Then** the per-repo breakdown renders the top-50 repositories by `comment_count` descending, with each row showing repository display label (per CL-04) + `thread_count` + `comment_count` + `active_thread_count` + a per-row partial-coverage qualifier when the row's range-total `coverage_partial` reduces to `true` (per FR-4-03).
2. **Given** the breakdown is rendered, **When** the user changes the dashboard's date range to a narrower window, **Then** the breakdown re-renders with rows summing per-(week, repo) contributions over only the weeks within the new range; row ordering remains valid for the new sums.
3. **Given** the dataset has more than 50 repositories with non-zero activity in the visible range, **When** the breakdown renders, **Then** it shows the top-50 by chosen metric and surfaces a truncation indicator carrying the count of hidden repositories (analog of 334's truncation pattern; noun "repositories").

### User Story 2 — Toggle the chosen sort metric (Priority: P2)

The team lead notices a high `comment_count` for one repository but suspects the load might actually concentrate on threads (more discussions even if individually shorter), or on unresolved threads. They switch the sort metric to `thread_count` (or `active_thread_count`) and the rows re-order, surfacing different outliers.

**Why this priority**: A sort-metric toggle is a low-cost addition that closes the loop from "spot the dominant comment-count repository" to "see if thread-count or unresolved-count tells a different story." Sequencing it after P1 lets the foundation chart ship as the minimum viable unit. This story is the per-repo analog of 334 US2.

**Independent Test**: With User Story 1 visible, activate each of the three sort-metric options. Confirm the rows re-order each time and the active sort metric is visually indicated. Tie-break ordering MUST be deterministic (chosen-metric desc → repository display name ascending → `repository_id` ascending as the final tie-breaker, handling duplicate display names) so the rendered order is reproducible across reloads.

**Acceptance Scenarios**:

1. **Given** the breakdown is rendered with the default `comment_count` sort, **When** the user activates `thread_count` from the sort selector, **Then** the rows re-order by `thread_count` descending and the active-selector indicator updates.
2. **Given** the breakdown is rendered, **When** the user activates `active_thread_count`, **Then** the rows re-order by unresolved-thread count descending.
3. **Given** the user activates a sort metric that produces ties (multiple repositories with identical metric value, including duplicate display names from a renamed-repository dimension entry colliding with another live repository's name), **When** the rows re-order, **Then** ties break deterministically — first by repository display name ascending, then by `repository_id` ascending as the final tie-breaker; the rendered order is reproducible across page reloads under the same dataset.

### User Story 4 — Filter-not-supported posture (Priority: P3)

The user has applied a dashboard dimension filter (`repos` / `teams` / `authors` / `reviewers`). They see the per-repo breakdown surface in a self-explanatory empty state explaining that per-dimension comments slices are not yet supported.

**Why this priority**: Inherited from 333's FR-1-07 / 334's FR-4-07 resolution. The dashboard's `applyFiltersToRollups` / `buildFilteredRollup` carry comments namespaces through unchanged via `...rollup` spread; rendering filtered-rollup-driven rows would silently show unfiltered totals while the rest of the dashboard reflects filtered scope — an honesty regression. Hiding the chart entirely was rejected as a worse UX than a visible empty-state shell.

Note: the `repos` filter is one of the four dimensions that triggers this empty state. A user filtering to a single repository AND viewing the per-repo breakdown sees the filter-not-supported empty state rather than a degenerate single-row breakdown — the spec is intentional that the breakdown is a multi-repo comparison surface and any repo-narrowing filter should hide the body. This matches 334's behavior where the `authors` filter triggers the same empty state on the per-author breakdown.

**Independent Test**: With the breakdown rendered (US1 complete), apply a dashboard dimension filter (any of the four). **Acceptance Scenarios**:

### Edge Cases

- **Zero-repository week within visible range**: A range may include weeks with no PRs in W's canonical throughput PR set. These weeks contribute zero to all per-repo values; if the entire range is zero-PRs (capability-on but empty), the breakdown's body is the no-data-in-range empty state (distinct from filter-not-supported per US4).
- **Single-PR repository**: A repository with one PR (one comment, one thread) renders as a single row participating in sort / filter exactly like any high-load repository row. No special treatment.
- **All-unextracted repository in W**: Every PR in W belonging to repository R has `comments_extracted_at IS NULL`. The per-(week, repo) emission for R has all three numeric fields equal to zero (sum over an empty extracted-subset) AND `coverage_partial: true`; the bucket is still emitted with the four atomic fields per INV-3-08. The renderer's range-total reduction (FR-4-02) suppresses the row when the range-total numeric values are zero (no zero-rows render); when range-total values are non-zero from other weeks but that week's `coverage_partial` is true, the qualifier propagates per FR-4-03.
- **Repository renamed in production after dimension snapshot**: A repository's `repository_name` may have changed after the `dimensions.json` snapshot was taken; the row's display label MUST resolve from the snapshot (not from a live-rename). When the dimension entry for a `repository_id` is missing entirely (e.g., a brand-new repository created after the snapshot), the renderer falls back to the raw `repository_id` as the display label per CL-04. The fallback path MUST be unit-tested at the renderer module.
- **Repository repository_id not present in `repositories` table** (FK-violation production data — should never occur per CL-03): the aggregator MUST surface the violation (FAIL-LOUD posture per CL-03) rather than silently coerce; plan-level decision on the exact failure-mode wiring (raise vs. structured warning at build-time gate). Test fixture forced-violation MUST cause a deterministic failure of the build-time gate; the renderer MUST NEVER receive a row with a missing `repositories` dimension entry whose presence would be ambiguous between "renamed after snapshot" (CL-04 fallback path) and "FK violation."
- **Repository appears in multiple weeks with mixed extraction**: If repository R has both extracted-comment weeks and unextracted-comment weeks in the visible range, R's row contributes the extracted-subset sums (CL-09 propagation of 333 FR-2-03 / 334 FR-1-05) AND the row's range-total `coverage_partial` reduces to `true` if any constituent week's per-(week, repo) emission has `coverage_partial = true`. The renderer applies the partial-coverage qualifier per FR-4-03.
- **Truncation past top-50**: Repositories past the top-50 by chosen metric do not render; truncation indicator surfaces the count of hidden repositories. Switching the sort metric may re-rank such that a previously-hidden repository appears in the visible top-50 (and a previously-visible repository falls below the cap).
- **Capability flips OFF during a session via dataset reload**: The breakdown container removes cleanly without leaving stale geometry on the dashboard layout (333 / 334 lifecycle parity).
- **Sort metric switch while range filter changes simultaneously**: The breakdown re-renders once with both the new sort and the new range; no intermediate "stale sort + new range" frame is visible (333 idempotency pattern).
- **`active_thread_count > thread_count` for any per-(week, repo) emission** (data integrity violation per INV-3-07): MUST NEVER occur if aggregator and inclusion rules are correct. Treat as a backend bug; the renderer MUST NOT silently coerce. Surfaced via the FR-2-04 reconciliation extension which extends 334's FR-2-04 import-block-isolated reconciliation test.
- **Truncated week W (`_prs_truncated: true`) cross-aggregate sum coherence**: For any week W where the drill-down `prs[]` field is truncated by 310 INV-02's top-500 cap, the per-week `comments` aggregate (333) and the SUM of all per-(week, repo) `by_repository_comments[r]` numeric fields (this feature) MUST still agree numerically — both compute over the FULL extracted-subset of W's canonical throughput PR set, NOT over the drill-down's slice. The truncated W26 fixture is the witness; FR-2-03 enforces this contract.

## Requirements *(mandatory)*

### Functional Requirements — Aggregator emission

- **FR-1-01**: When `capabilities.comments_metrics` is enabled, the aggregator's weekly rollup MUST emit per-repo comments-density data covering all repositories with at least one PR in W's canonical throughput PR set whose `comments_extracted_at IS NOT NULL`. Emission unit is per-(week, repo) tuple.
- **FR-1-02 (emission shape)**: A new optional outer dict `rollup[W].by_repository_comments[<repository_id>]` MUST be emitted on the rollup root, containing exactly the comments fields (`thread_count`, `comment_count`, `active_thread_count`, `coverage_partial`) per inner entry. Capability-off path: the entire `by_repository_comments` key MUST be omitted (FR-3-03 analog from 333 / 334; INV-3-09 byte-identity inheritance). The existing `rollup[W].by_repository` namespace (throughput breakdown) remains unchanged in either capability state — this feature ADDS a parallel `by_repository_comments` namespace; it does not modify `by_repository`.
- **FR-1-03 (FK-protected keying — no sentinel per CL-03)**: The repository identifier used as the outer-dict key MUST be the PR's `pull_requests.repository_id` value. There is NO sentinel bucket and NO sentinel literal — the FK constraint at `src/ado_git_repo_insights/persistence/models.py` `pull_requests` table guarantees every emitted `repository_id` corresponds to a row in `repositories`. If the FK is violated at aggregation time (FK-violation production-data edge), the aggregator MUST surface the violation per CL-03's FAIL-LOUD posture rather than silently coerce.
- **FR-1-04 (C1 reference, not re-declaration)**: Per-(week, repo) counts MUST apply the C1 inclusion rules from `specs/310-comments-visualization/spec.md` "Shared inclusion-rule contract (C1)". This feature MUST reference that section as the authority and MUST NOT re-declare any inclusion rule. Re-declaration is itself an INV-3-03 violation.
- **FR-1-05 (extracted-subset rule, propagated from 333 FR-2-03 / 334 FR-1-05)**: Per-(week, repo) sums range over the EXTRACTED-SUBSET of W's canonical throughput PR set (PRs with `pull_requests.comments_extracted_at IS NOT NULL`). PRs with `comments_extracted_at IS NULL` contribute zero (equivalent to omission). The numeric values are therefore "known extracted-subset totals," not full-week truth.
- **FR-1-06 (per-repo coverage_partial)**: Each per-(week, repo) emission MUST carry a `coverage_partial: boolean` field that is `true` if AND ONLY IF at least one of repository R's PRs in W's canonical throughput PR set has `comments_extracted_at IS NULL` — even one such PR flips the (week, repo) to `true`. The reduction over the visible date range (chart-side) is `true` if any constituent week's per-(week, repo) `coverage_partial` is `true`.
- **FR-1-07 (atomicity, propagated from 334 INV-2-08)**: When the `by_repository_comments` key is present on a rollup root under capability-on, EVERY entry in the outer dict MUST contain ALL four count fields (`thread_count`, `comment_count`, `active_thread_count`, `coverage_partial`) together. Partial-fielded entries within the outer dict are forbidden. Mirrors 334's INV-2-08; surfaced as INV-3-08 in this spec's invariants.
- **FR-1-08 (ordering, propagated from 334 INV-2-07)**: For every per-(week, repo) emission under capability-on, `active_thread_count <= thread_count` MUST hold. Any aggregator path producing `active_thread_count > thread_count` is a correctness bug, surfaced via FR-2-05.
- **FR-1-09 (canonical PR set scope, propagated from 334 INV-2-10)**: The set of PRs the aggregator iterates for per-(week, repo) emission MUST be W's FULL canonical throughput PR set (i.e., the `week_pr_uids` set the existing aggregator already passes to its sibling helpers, identical to 334's `_compute_weekly_by_author_comments` input). It MUST NOT be restricted to the drill-down's top-500-by-cycle-time slice (310 INV-02 is preserved — that cap applies only to the per-PR `prs[]` drill-down, not to aggregator scope). This is the prerequisite that makes FR-2-03's truncated-week sum-coherence contract honor-able.
- **FR-1-10 (key omission under empty buckets)**: If the canonical throughput PR set for W is empty OR every PR in it is unextracted such that no repository bucket carries any extracted-subset contribution AND no repository bucket carries `coverage_partial: true` (defensive degenerate case where W has zero PRs whatsoever), the aggregator MUST omit the `by_repository_comments` key for W entirely (FR-3-03 omission contract; the key MUST be absent — NOT `null`-valued, NOT `{}`-valued, NOT partial). When buckets exist with all-zero numerics but `coverage_partial: true`, the buckets MUST be emitted with the atomic 4-field shape — `coverage_partial: true` carries user-facing signal per FR-4-03 even when numeric fields are zero.

### Functional Requirements — Cross-feature reconciliation (CL-05 closure)

- **FR-2-01 (per-repo parity — pairwise on extracted-subset of drill-down ∩ aggregator intersection)**: For every PR P in the drill-down's top-500-by-cycle-time slice for week W AND in W's extracted-subset (`comments_extracted_at IS NOT NULL` for P), the per-PR `thread_count` / `comment_count` / `active_thread_count` values rendered in the drill-down (310 PrRecord fields) MUST equal P's per-PR contribution to the corresponding numeric fields of the per-(week, repo = P's `repository_id`) aggregate emission. PRs in the drill-down's slice NOT in the extracted-subset are excluded from pairwise numeric comparison; they reconcile via 310 INV-10's per-PR partial sentinel (drill-down null/undefined) AND aggregator's exclude-from-sum (FR-1-05).
- **FR-2-02 (end-to-end aggregator correctness via independent re-computation)**: For each week W and each per-(week, repo) emission, the test MUST verify the values match an independent re-computation that:
  1. Determines W's canonical throughput PR set via DIRECT SQL against `pull_requests` — re-implementing the same week-attribution rule throughput uses (per 333 FR-2-03 / 334 FR-2-02 parity guard); the test does NOT call into either aggregator's helpers (333 round-9 / 334 import-block isolation extends to per-repo scope).
  2. Joins each PR with its `repository_id` per FR-1-03 (no sentinel mapping; direct column read).
  3. Filters to W's extracted-subset (`comments_extracted_at IS NOT NULL`).
  4. For each (W, repo) pair: applies C1 inclusion rules directly against `pr_threads` / `pr_comments`, sums per-PR contributions to produce expected `thread_count` / `comment_count` / `active_thread_count`.
  5. Re-derives expected `coverage_partial = (∃ PR by repo R in W's canonical set with comments_extracted_at IS NULL)`; asserts equality with the aggregator's emitted value.
  6. Asserts the aggregator's emitted per-(week, repo) value matches field-by-field.
- **FR-2-03 (cross-aggregate sum coherence — NEW for this feature, witness on truncated W26)**: For every week W in the demo dataset where `capabilities.comments_metrics` is enabled AND `rollup[W].comments` is present AND `rollup[W].by_repository_comments` is non-empty, the test MUST assert the following sum-coherence equalities:
  - SUM over all repositories R in `by_repository_comments` of `by_repository_comments[R].thread_count` EQUALS `comments.thread_count`.
  - SUM over all repositories R in `by_repository_comments` of `by_repository_comments[R].comment_count` EQUALS `comments.comment_count`.
  - SUM over all repositories R in `by_repository_comments` of `by_repository_comments[R].active_thread_count` EQUALS `comments.active_thread_count`.
  - LOGICAL OR over all repositories R in `by_repository_comments` of `by_repository_comments[R].coverage_partial` EQUALS `comments.coverage_partial`.

The W26 fixture proves the cross-aggregate sum-coherence holds on a truncated week, closing the deferred 333/334 cross-aggregate parity obligation.

  The FR-2-03 sum-coherence test does NOT replace FR-2-02's end-to-end independent re-computation — sum-coherence is necessary but not sufficient (it can pass while both aggregates agree on a wrong number). FR-2-02 grounds correctness against direct SQL; FR-2-03 grounds cross-aggregate consistency between the two aggregators' outputs.
- **FR-2-04 (test extension target — CL-05)**: The reconciliation test extension lives in `tests/integration/test_comments_trend_reconciliation.py` (extending 333's existing reconciliation test, already extended by 334) for FR-2-01 / FR-2-02 / FR-2-03. ### Functional Requirements — Render

- **FR-4-01**: When `capabilities.comments_metrics` is enabled, the dashboard MUST render a per-repo comment-density breakdown surface on the Metrics tab, positioned BELOW the 334 per-author breakdown row (anchor `[data-comments-author-density-row="true"]` per CL-10) and the existing throughput / cycle-time / reviewer-activity / summary-cards / 333 comments-trend surfaces. The reduction unit is range-total per row (one row per repository across the visible weeks). Repositories with zero contributions in the range MUST NOT render (no zero-rows; zero contributions = absent), even when their constituent weeks have `coverage_partial: true` — the partial-coverage qualifier (FR-4-03) applies only to rendered rows; suppression of all-zero rows is unconditional.
- **FR-4-03 (per-row partial-coverage qualifier)**: When a row's range-total `coverage_partial` reduces to `true` (any constituent week's per-(week, repo) `coverage_partial = true`), that row MUST render a partial-coverage qualifier consistent with 333's / 334's qualifier convention (the visual style — hatched fill / dimmed text / tooltip — inherits from the shared `.coverage-partial` CSS class hook). The qualifier MUST apply only to rows marked partial; non-partial rows render in the normal (non-partial) convention.
- **FR-4-04 (number formatting)**: Each row's three numeric metrics MUST use locale-aware integer formatting with no decimals (counts are whole numbers per FR-1-08), consistent with how throughput / 333's chart / 334's per-author breakdown present numeric counts.
- **FR-4-05 (sort, CL-06)**: The breakdown MUST be sortable among the three metrics (`comment_count` / `thread_count` / `active_thread_count`); default sort is `comment_count` descending; ties break deterministically — first by repository display name ascending, then by `repository_id` ascending as the final tie-breaker (handles duplicate display names from rename or fallback collisions). The active sort metric MUST be visually indicated. Switching the sort metric MUST re-render rows in the new order. Sort selector pattern: WAI-ARIA Toolbar (memory: `feedback_wai_aria_toolbar_for_keyboard_reachability.md` / 334 pattern) — `role="toolbar"` wrapper + plain `<button>` elements (default `tabindex=0` + `aria-pressed`); each button is independently Tab-reachable; Enter / Space activates.
- **FR-4-06 (display cap, CL-06)**: The breakdown MUST render at most 50 rows (constant `MAX_COMMENTS_REPO_DENSITY_ROWS = 50`) by chosen metric. If more repositories have non-zero values than the cap, a truncation indicator MUST surface the count of hidden repositories (analog of 334's `MAX_COMMENTS_AUTHOR_DENSITY_ROWS = 50` truncation pattern; noun "repositories").
- **FR-4-07 (filter-not-supported posture)**: When ANY of the dashboard's per-PR dimension filters (`repos` / `teams` / `authors` / `reviewers`) is active, the breakdown MUST render a self-explanatory filter-not-supported empty state instead of rows. The empty state MUST be visibly distinct from the no-data-in-range empty state (FR-4-08) AND MUST disappear cleanly when filters are cleared. Per-dimension comments slices that would let the breakdown honor filters are deferred to a future feature (out of foundation-PR scope). The `repos` filter explicitly triggers this empty state — narrowing to a single repository is intentional design rather than a degenerate case.
- **FR-4-08 (no-data empty state)**: When the visible date range yields zero repositories with non-zero contributions (capability-on path; e.g., zero PRs in range, or all PRs in range have `comments_extracted_at IS NULL`), the breakdown MUST render a self-explanatory no-data-in-range empty state distinct from filter-not-supported (FR-4-07).
- **FR-4-09 (no click-through, CL-07)**: Rows MUST NOT activate any drill-down or per-repo detail surface. The breakdown is informational. Plan-level: rows are not styled as clickable. A future per-repo drill-down panel is deferred outside this feature.
- **FR-4-10 (a11y)**: The sort selector MUST be keyboard-activatable (WAI-ARIA Toolbar pattern per FR-4-05); the breakdown table (or table-equivalent semantic structure) MUST expose per-row metric values via screen-reader-readable text. Pattern reference: 334's per-author breakdown `aria-pressed` / `tabindex` / `role` convention adapted for repository rows.
- **FR-4-11 (display label fallback)**: When the `repositories` dimension entry for a given `repository_id` is missing, the renderer MUST render the raw `repository_id` value as the display label (CL-04). This case MUST be unit-tested at the renderer module — the test MUST construct a fixture with a `by_repository_comments[<id>]` entry whose ID is absent from the `repositoriesDimension` array passed to the chart and assert the rendered row label equals the raw ID.
