## Overview

This feature adds a per-reviewer comment-density breakdown to the dashboard's Metrics tab. It is the THIRD of three sibling Cap-2 dimension PRs (#334 author shipped on PR #349, #335 repo shipped on PR #350; this PR for reviewer); the visual + interaction pattern locked by #334 / #335 is inherited verbatim with the per-reviewer-specific divergences enumerated in the Background section. Sibling #321 (per-team) is deferred pending team-at-time-of-PR history modeling.

**Why now**: The drill-down (310) shows per-PR thread / comment / active-thread counts; the trend chart (333) shows weekly volume; the per-author breakdown (334) ranks authors by discussion load; the per-repo breakdown (335) ranks repositories by discussion load. Together they answer "is volume rising?", "are any authors outliers?", and "are any repositories outliers?" — but they do not answer "are any reviewers outliers in review-conversation contribution — anyone driving disproportionate share of discussion load on PRs they didn't author?" Reviewer concentration of review-conversation activity is the cross-cutting view that surfaces individual review-quality patterns at the commenter granularity (separate from PR authorship). Today no dashboard surface renders reviewer-level comments-density.

The feature is additive and gated on `capabilities.comments_metrics`. The dashboard MUST render byte-identical to its current rendering for users without comment extraction enabled (analog of 333 SC-1-04 / 334 SC-1-03 / 335 SC-1-03 for this feature's namespace).

**Substantive divergences from #334 / #335** (locked at /speckit.specify time):

- **Iteration unit is `pr_comments`, NOT `pull_requests`** (per CL-13). #334 (per-author) and #335 (per-repo) iterate `pull_requests` and group by author or repository; #336 iterates `pr_comments` and groups by commenter `author_id`. This is the substantive aggregator divergence — fresh `_compute_weekly_by_reviewer_comments` helper rather than extending #334's helper.
- **Numeric semantics** (per FR-1-05): `comment_count` is raw row count; `thread_count` is `COUNT(DISTINCT thread_id)` per commenter (NOT raw rows); `active_thread_count` is the active subset of those distinct threads. Multi-counting is structural to `thread_count` / `active_thread_count` — sum across reviewers ≠ `comments.thread_count` (unlike #334 / #335 where sums DO equal `comments.*` fields).
- **Cross-aggregate parity contract** (per CL-12): `SUM_R(by_reviewer_comments[R].comment_count)` for W EQUALS an INDEPENDENT count of `pr_comments` rows in W's extracted-subset where commenter ≠ PR author. **NOT** vs `comments.comment_count` (which over-counts by self-comment delta). `thread_count` / `active_thread_count` sum-coherence NOT asserted (multi-counting metrics).
- **Demo synthetic commenter stream** (per CL-14): the demo generator currently has NO `pr_comments` stream — only PR-level aggregate counts. This feature ADDS internal `synthetic_pr_threads` + `synthetic_pr_comments` parallel lists per week, populated such that re-aggregating them yields each PR's pre-existing PrRecord aggregate counts (coherence guard). Required prerequisite for non-vacuous testing.
- **Coverage_partial semantics** (per CL-10): same-W flag (every reviewer in W shares the value of "any PR in W's canonical throughput PR set has `comments_extracted_at IS NULL`"). Bucket-specific definition is degenerate for per-reviewer because R's commenter relationship is invisible until extraction. Tooltip qualifier text MUST surface the week-level partial signal (NOT a bucket-specific partial signal that the data cannot support).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Identify highest-load reviewers at a glance (Priority: P1)

A team lead opens the dashboard's Metrics tab on a Monday morning and wants to see which reviewers are contributing the most review-conversation load on PRs they didn't author over the last quarter. They look at the new per-reviewer comment-density breakdown — positioned just below the per-repo breakdown — and immediately see the top-N reviewers ranked by their chosen count metric (default `comment_count`). Without sorting beyond the default, they identify outliers and notice if any reviewer's contribution differs sharply from the median. The "Former / unavailable author" sentinel row, when visible, qualifies how much of the load comes from commenters no longer in the user directory.

**Why this priority**: This is the entire user-visible reason the feature exists. #322's Capability-2 reviewer-dimension ask was articulated as "are any reviewers outliers in review-conversation contribution?" Without P1 the feature has no value; the chart's first-glance readability is the success criterion.

**Independent Test**: Open a demo dashboard with `capabilities.comments_metrics` enabled and ≥10 distinct commenters with mixed comment-load on PRs they didn't author. Confirm a chart titled with reviewer / density vocabulary renders below the 335 per-repo breakdown on the Metrics tab. Confirm rows are ordered by `comment_count` desc. Confirm the date-range filter narrows the visible set when changed. Sort toggle (US2), capability-off (US3), sentinel (US4), and filter-not-supported posture (US5) are not required to be present for this test.

**Acceptance Scenarios**:

1. **Given** a dataset where `capabilities.comments_metrics` is enabled and the visible date range contains ≥10 reviewers with non-zero comment activity on PRs they didn't author, **When** the user opens the Metrics tab, **Then** the per-reviewer breakdown renders the top-50 reviewers by `comment_count` descending, with each row showing reviewer display label (per CL-05) + `thread_count` (distinct eligible threads with at least one non-self comment by R per FR-1-05) + `comment_count` + `active_thread_count` + a per-row partial-coverage qualifier when the row's range-total `coverage_partial` reduces to `true` (per FR-4-03).
2. **Given** the breakdown is rendered, **When** the user changes the dashboard's date range to a narrower window, **Then** the breakdown re-renders with rows summing per-(week, reviewer) contributions over only the weeks within the new range; row ordering remains valid for the new sums.
3. **Given** the dataset has more than 50 reviewers with non-zero activity in the visible range, **When** the breakdown renders, **Then** it shows the top-50 by chosen metric and surfaces a truncation indicator carrying the count of hidden reviewers (analog of 334/335's truncation pattern; noun "reviewers").

### User Story 2 — Toggle the chosen sort metric (Priority: P2)

The team lead notices a high `comment_count` for one reviewer but suspects the load might actually concentrate on threads (more distinct discussions even if individually shorter), or on unresolved threads. They switch the sort metric to `thread_count` (or `active_thread_count`) and the rows re-order, surfacing different outliers.

**Why this priority**: A sort-metric toggle is a low-cost addition that closes the loop from "spot the dominant comment-count reviewer" to "see if thread-count or unresolved-count tells a different story." Sequencing it after P1 lets the foundation chart ship as the minimum viable unit. This story is the per-reviewer analog of 334 US2 / 335 US2.

**Independent Test**: With User Story 1 visible, activate each of the three sort-metric options. Confirm the rows re-order each time and the active sort metric is visually indicated. Tie-break ordering MUST be deterministic (chosen-metric desc → reviewer display name ascending → bucket key ascending as the final tie-breaker, handling duplicate display names AND a sentinel/real-name collision) so the rendered order is reproducible across reloads. The fixture MUST be designed so all three sort orderings are distinct (per kickoff lesson "non-vacuous sort fixtures") — otherwise Space-vs-Enter activation assertions pass vacuously.

**Acceptance Scenarios**:

1. **Given** the breakdown is rendered with the default `comment_count` sort, **When** the user activates `thread_count` from the sort selector, **Then** the rows re-order by `thread_count` descending and the active-selector indicator updates.
2. **Given** the breakdown is rendered, **When** the user activates `active_thread_count`, **Then** the rows re-order by unresolved-thread count descending.
3. **Given** the user activates a sort metric that produces ties (multiple reviewers with identical metric value, including duplicate display names from a renamed-user dimension entry colliding with another live user's name, OR a sentinel/real-name collision), **When** the rows re-order, **Then** ties break deterministically — first by reviewer display name ascending, then by bucket key (`user_id` or sentinel literal) ascending as the final tie-breaker; the rendered order is reproducible across page reloads under the same dataset.

### User Story 5 — Filter-not-supported posture (Priority: P3)

### Edge Cases

- **Zero-reviewer week within visible range**: A range may include weeks with no PRs in W's canonical throughput PR set OR weeks where every PR's eligible comment set is empty (e.g., every PR in W has self-comments only or no comments). These weeks contribute zero to all per-reviewer values; if the entire range is zero-eligible-comments (capability-on but empty), the breakdown's body is the no-data-in-range empty state (distinct from filter-not-supported per US5).
- **Single-comment reviewer**: A reviewer with one eligible comment (one row in `pr_comments` where commenter ≠ PR author) renders as a single row participating in sort / filter exactly like any high-load reviewer row. `thread_count` for that reviewer is 1 (the one thread containing their comment); `active_thread_count` is 0 or 1 depending on the thread's status. No special treatment.
- **Single thread with multiple commenters** (multi-counting witness): A PR with one thread T containing comments from 3 distinct non-self commenters A, B, C produces three buckets each with `thread_count = 1` for that thread. `SUM_R(thread_count)` for this PR is 3, while `comments.thread_count` for the PR is 1 — multi-counting confirmed. FR-2-03 does NOT assert sum-coherence for `thread_count` (covered by per-bucket FR-2-02 only).
- **PR with mixed self-only and non-self threads** (FR-2-01 structural narrowing witness): A PR P with thread T1 (self-comment by P's author only — no non-self commenters) AND thread T2 (≥1 non-self comment) has drill-down `thread_count = 2` but `SUM_R(thread_count contribution from P)` is bounded above by `count_threads_with_non_self_comments(P) = 1` (only T2). Therefore `SUM_R(thread_count contribution from P) ≤ 1 < 2 = P.thread_count_drilldown` — strict-less, no clean closed-form bound at the per-PR level. FR-2-01 does NOT assert thread_count or active_thread_count distribution coherence at the per-PR level for this reason; per-bucket correctness is covered by FR-2-02's independent re-computation only. The case is structural (NOT a producer bug) — the per-reviewer dimension excludes self-only threads by design per CL-04 self-comment exclusion. Plan-level: tasks.md T009 FR-2-01 sub-bullet narrows accordingly.
- **Self-comment-only week**: Every comment in W is a self-comment (commenter == PR author). The eligible reviewer-comment set is empty; `by_reviewer_comments` for W is empty → key is omitted entirely (FR-1-10 + FR-3-03 omission contract). The breakdown's body for a range of such weeks is the no-data-in-range empty state.
- **All-unknown-commenter week**: Every eligible comment in W is by a commenter absent from `users` (only possible under FK-disabled scenarios per CL-03 background). The sentinel bucket aggregates all contributions; no real-reviewer rows for W. If the entire visible range is sentinel-only, the breakdown shows a single sentinel row.
- **Reviewer appears in multiple weeks with mixed extraction**: If reviewer R has both extracted-comment weeks and weeks with `coverage_partial: true` (W contains an unextracted PR) in the visible range, R's row contributes the extracted-subset eligible-comment counts (CL-10 same-W flag propagation; chart-side partial signal applies if any constituent week's `coverage_partial = true`). The renderer applies the partial-coverage qualifier per FR-4-03 with tooltip text emphasizing **week-level** uncertainty (per CL-10 directive).
- **Truncation past top-50**: Reviewers past the top-50 by chosen metric do not render; truncation indicator surfaces the count of hidden reviewers. Switching the sort metric may re-rank such that a previously-hidden reviewer appears in the visible top-50 (and a previously-visible reviewer falls below the cap).
- **Capability flips OFF during a session via dataset reload**: The breakdown container removes cleanly without leaving stale geometry on the dashboard layout (333 / 334 / 335 lifecycle parity).
- **Sort metric switch while range filter changes simultaneously**: The breakdown re-renders once with both the new sort and the new range; no intermediate "stale sort + new range" frame is visible (333 idempotency pattern).
- **`active_thread_count > thread_count` for any per-(week, reviewer) emission** (data integrity violation per INV-4-07): MUST NEVER occur if aggregator and inclusion rules are correct. Treat as a backend bug; the renderer MUST NOT silently coerce. Surfaced via the FR-2-04 reconciliation extension which extends 334/335's import-block-isolated reconciliation test.
- **Sentinel row collides with real reviewer display name**: Per CL-03 the sentinel uses a reserved aggregator-side key (`__former_or_unavailable_author__`) that cannot collide with real `user_id` UUIDs (A-07), but the renderer-side label "Former / unavailable author" could in principle collide with a real user's display name. The sentinel branch (CL-05 step 1) takes precedence over the users-dimension lookup so the sentinel row ALWAYS shows the fixed label even if a real user's display name happens to match.
- **Self-comment-leak edge** (FR-1-04 violation): a `pr_comments` row where commenter == PR author MUST NEVER appear in any `by_reviewer_comments` bucket (including the sentinel bucket — even if the PR's author is themselves missing from `users`, their self-comments stay excluded). Surfaced via FR-2-05 meta-test injection (a deliberate self-comment-leak mutation that asserts FR-2-04 reconciliation FAILS).
- **Truncated week W (`_prs_truncated: true`) per-reviewer cross-aggregate parity**: For any week W where the drill-down `prs[]` field is truncated by 310 INV-02's top-500 cap, the per-week eligible-reviewer-comments count (FR-2-03 right-hand side) MUST still match the SUM of all per-(week, reviewer) `by_reviewer_comments[r].comment_count` (left-hand side) — both compute over the FULL extracted-subset of W's canonical throughput PR set, NOT over the drill-down's slice. The truncated W26 fixture is the witness; FR-2-03 enforces this contract.

## Requirements *(mandatory)*

### Functional Requirements — Aggregator emission

- **FR-1-01**: When `capabilities.comments_metrics` is enabled, the aggregator's weekly rollup MUST emit per-reviewer comments-density data covering all distinct commenters in W's canonical throughput PR set's extracted-subset whose `pr_comments.author_id ≠ pull_requests.user_id` (per CL-04 reviewer semantics) AND `pr_comments.is_deleted = 0` (C1). Emission unit is per-(week, reviewer) tuple.

- **FR-1-02 (emission shape)**: A new optional outer dict `rollup[W].by_reviewer_comments[<commenter_id>]` MUST be emitted on the rollup root, containing exactly the comments fields (`thread_count`, `comment_count`, `active_thread_count`, `coverage_partial`) per inner entry. Capability-off path: the entire `by_reviewer_comments` key MUST be omitted (FR-3-03 analog from 333 / 334 / 335; INV-4-09 byte-identity inheritance). The existing `rollup[W].by_reviewer` namespace (throughput-only reviewer breakdown) remains unchanged in either capability state — this feature ADDS a parallel `by_reviewer_comments` namespace with comments-density fields only.

- **FR-1-03 (sentinel bucketing per CL-03)**: The reviewer identifier used as the outer-dict key MUST be:
  - The commenter's `pr_comments.author_id` value when that ID is present in the `users` table (resolved via LEFT JOIN per FR-1-11 SQL pattern).
  - The reserved sentinel literal `__former_or_unavailable_author__` (`FORMER_OR_UNAVAILABLE_AUTHOR_SENTINEL` from `src/ado_git_repo_insights/transform/constants.py:27`) when the ID is absent from `users`. ALL such commenters' eligible-comment contributions collapse into this single bucket per 310 C1's "single sentinel identity" rule.

- **FR-1-04 (reviewer semantics — exclusion rules per CL-04)**: Each emitted per-(week, reviewer) bucket MUST exclude:
  - Self-comments where `pr_comments.author_id == pull_requests.user_id` (commenter == PR author). The aggregator's WHERE clause MUST enforce this; a self-comment-leak edge violates FR-1-04 and surfaces via FR-2-05.
  - Deleted comments where `pr_comments.is_deleted != 0` (C1).
  - Comments on PRs outside W's canonical throughput PR set's extracted-subset (PRs with `comments_extracted_at IS NULL` per FR-1-06 extracted-subset rule).
  Silent assigned reviewers (entries in `pr_reviewers` with no `pr_comments` row) are NOT emitted (per CL-04). Drive-by commenters ARE emitted.

- **FR-1-05 (per-reviewer numeric semantics — DISTINCT thread vs raw row)**: Each per-(week, reviewer) emission's numeric fields are computed as follows:
  - **`comment_count`** = COUNT of `pr_comments` rows where `author_id = R`, `pull_request_uid` ∈ W's extracted-subset, commenter ≠ PR author, `is_deleted = 0` (C1). This is a RAW ROW COUNT.
  - **`thread_count`** = COUNT(DISTINCT `pr_comments.thread_id`) values where R has at least one row meeting `comment_count`'s WHERE filter. This is **distinct eligible threads with at least one non-self comment by R**, NOT raw row count. A thread where R commented N times contributes 1 to R's `thread_count`.
  - **`active_thread_count`** = COUNT(DISTINCT `pr_comments.thread_id`) values satisfying both: (i) R has at least one row meeting `comment_count`'s WHERE filter for that thread AND (ii) the thread's `pr_threads.status = 'active'` (joined via `pr_comments.thread_id = pr_threads.thread_id AND pr_comments.pull_request_uid = pr_threads.pull_request_uid`). NOT raw row count.

- **FR-1-06 (extracted-subset rule, propagated from 333 FR-2-03 / 334 FR-1-05 / 335 FR-1-05)**: Per-(week, reviewer) sums range over the EXTRACTED-SUBSET of W's canonical throughput PR set (PRs with `pull_requests.comments_extracted_at IS NOT NULL`). Comments on PRs with `comments_extracted_at IS NULL` are absent from `pr_comments` (the extraction step never wrote them); the aggregator's INNER JOIN against extracted-subset PRs naturally excludes them. The numeric values are therefore "known extracted-subset totals," not full-week truth.

- **FR-1-07 (per-reviewer coverage_partial — same-W flag per CL-10)**: Each per-(week, reviewer) emission MUST carry a `coverage_partial: boolean` field that is `true` if AND ONLY IF at least one PR in W's canonical throughput PR set has `comments_extracted_at IS NULL`. This flag is **week-level**, NOT bucket-specific — every reviewer R emitted for W MUST share the SAME value, equal to `rollup[W].comments.coverage_partial` (333's flag). The reduction over the visible date range (chart-side) is `true` if any constituent week's per-(week, reviewer) `coverage_partial` is `true`. Renderer MUST surface tooltip text emphasizing **week-level** uncertainty (NOT bucket-specific) per CL-10.

- **FR-1-08 (atomicity, propagated from 334 INV-2-08 / 335 INV-3-08)**: When the `by_reviewer_comments` key is present on a rollup root under capability-on, EVERY entry in the outer dict (including the sentinel-bucket entry) MUST contain ALL four count fields (`thread_count`, `comment_count`, `active_thread_count`, `coverage_partial`) together. Partial-fielded entries within the outer dict are forbidden. Mirrors 334's INV-2-08 / 335's INV-3-08; surfaced as INV-4-08 in this spec's invariants.

- **FR-1-09 (ordering, propagated to per-reviewer)**: For every per-(week, reviewer) emission under capability-on, `active_thread_count <= thread_count` MUST hold (a thread is active or it isn't; the active subset cannot exceed the full distinct-thread set). Sentinel-bucket emissions MUST satisfy the same constraint. Any aggregator path producing `active_thread_count > thread_count` is a correctness bug, surfaced via FR-2-05.

- **FR-1-10 (canonical PR set scope, propagated from 334 INV-2-10 / 335 INV-3-10 / FR-1-09)**: The set of PRs the aggregator iterates for per-(week, reviewer) emission MUST be W's FULL canonical throughput PR set (the same `week_pr_uids` set the existing aggregator already passes to its sibling helpers). It MUST NOT be restricted to the drill-down's top-500-by-cycle-time slice (310 INV-02 is preserved — that cap applies only to the per-PR `prs[]` drill-down, not to aggregator scope). This is the prerequisite that makes FR-2-03's truncated-week parity contract honor-able.

- **FR-1-11 (key omission under empty buckets)**: If the canonical throughput PR set for W is empty OR every eligible-comment row would be filtered out (every comment in W is a self-comment, OR every PR's `comments_extracted_at IS NULL`, OR no PR has any commenter row), the aggregator MUST omit the `by_reviewer_comments` key for W entirely (FR-3-03 omission contract; the key MUST be absent — NOT `null`-valued, NOT `{}`-valued, NOT partial). When buckets exist with all-zero numerics (only possible if a reviewer's only comments in W are filtered out by a downstream fix-up — should not happen in well-formed data), the bucket MUST NOT be emitted (zero-bucket suppression at producer side; renderer's all-zero-row filter per FR-4-02 is a defense-in-depth, not the primary suppressor).

- **FR-1-12 (FAIL-LOUD on shape corruption per CL-15)**: The aggregator MUST raise `RuntimeError` if a `pr_comments.author_id` value encountered during iteration is NULL OR is non-UUID-format (does not match the existing extractor's UUID convention: 32 hex chars + 4 hyphens). Sentinel-bucket assignment for missing-`users` rows is the by-design path and is NOT FAIL-LOUD (per CL-15). Shape corruption is FAIL-LOUD because it indicates database integrity violation that silent coercion would mask.

### Functional Requirements — Cross-feature reconciliation (CL-06 closure)

- **FR-2-01 (per-PR drill-down ↔ per-reviewer aggregator `comment_count` distribution coherence)**: For every PR P in the drill-down's top-500-by-cycle-time slice for week W AND in W's extracted-subset (`comments_extracted_at IS NOT NULL` for P), the test MUST verify the following coherence relation between P's per-PR drill-down PrRecord `comment_count` value (310) and P's distributed contribution across reviewer buckets:
  - **`comment_count` distribution**: P's per-PR `comment_count` (drill-down) MINUS the count of self-comments on P (commenter == P's author per direct SQL) EQUALS the SUM over non-self commenters R of (count of `pr_comments` rows for P where `author_id = R` AND `is_deleted = 0`). The right-hand side is P's distributed contribution to non-self reviewer buckets; the equality witnesses that no eligible comment is dropped during bucket attribution.
  - **`thread_count` / `active_thread_count` per-PR distribution NOT asserted at FR-2-01 level**: the per-PR drill-down's `thread_count` counts ALL distinct threads on P after C1, INCLUDING threads with only self-comments by P's author. Such self-only threads contribute 0 to the per-reviewer aggregator (no non-self commenter exists for them per CL-04). Therefore `SUM_R(thread_count contribution from P)` is bounded above by `count_threads_with_at_least_one_non_self_comment(P)` which is itself ≤ P's drill-down `thread_count` — strict-less when P has ≥1 self-only thread. There is NO clean closed-form bound at the per-PR level (the gap between the two counts depends on P's self-only-thread count, which the per-PR drill-down does not record separately). Per-bucket correctness for `thread_count` / `active_thread_count` is covered by FR-2-02's independent re-computation; per-PR cross-checks at FR-2-01 are intentionally limited to `comment_count` only. The "PR with mixed self-only and non-self threads" edge case is the witness that this narrowing is structural, not a defect.
  Note: unlike #334 / #335 where each PR contributes to exactly one bucket and FR-2-01 is a clean per-PR equality across all three metrics, the per-reviewer dimension's many-to-one shape (one PR contributes to N reviewer buckets) plus the self-comment exclusion (CL-04) make per-PR equality clean only for `comment_count`. FR-2-02 is the load-bearing per-(W, R) parity assertion across all three metrics; FR-2-01 is the drill-down ∩ aggregator `comment_count`-distribution witness.

- **FR-2-02 (end-to-end aggregator correctness via independent re-computation)**: For each week W and each per-(week, reviewer) emission, the test MUST verify the values match an independent re-computation that:
  1. Determines W's canonical throughput PR set via DIRECT SQL against `pull_requests` — re-implementing the same week-attribution rule throughput uses (per 333 Decision 7 / 334 FR-2-02 / 335 FR-2-02 parity guard); the test does NOT call into either aggregator's helpers (333 round-9 / 334 / 335 import-block isolation extends to per-reviewer scope by-FILE, not by-dimension).
  2. Filters to W's extracted-subset (`comments_extracted_at IS NOT NULL`) and joins against `pr_comments` on `pull_request_uid`, applying C1 (`pr_comments.is_deleted = 0`).
  3. Excludes self-comments (`pr_comments.author_id != pull_requests.user_id`) per CL-04.
  4. Joins each commenter row with `users` via LEFT JOIN; resolves the bucket key as `users.user_id` if present, else `FORMER_OR_UNAVAILABLE_AUTHOR_SENTINEL` per FR-1-03.
  5. For each (W, reviewer) pair: computes expected `comment_count` (raw row count), `thread_count` (COUNT(DISTINCT thread_id)), `active_thread_count` (COUNT(DISTINCT thread_id) WHERE pr_threads.status='active') per FR-1-05.
  6. Re-derives expected `coverage_partial = (∃ PR in W's canonical set with comments_extracted_at IS NULL)` (same-W per CL-10); asserts equality with the aggregator's emitted value AND equality with `rollup[W].comments.coverage_partial`.
  7. Asserts the aggregator's emitted per-(week, reviewer) value matches field-by-field.

- **FR-2-03 (cross-aggregate parity — NEW for this feature, per CL-12)**: For every week W in the demo dataset where `capabilities.comments_metrics` is enabled AND `rollup[W].by_reviewer_comments` is non-empty, the test MUST assert:
  - **`comment_count` sum-coherence vs INDEPENDENT count**: SUM over all reviewers R in `by_reviewer_comments` of `by_reviewer_comments[R].comment_count` EQUALS the count of `pr_comments` rows in W's extracted-subset where `pr_comments.author_id != pull_requests.user_id` AND `pr_comments.is_deleted = 0` (C1). This count MUST be computed INDEPENDENTLY by direct SQL — the test MUST NOT reference `rollup[W].comments.comment_count` (which over-counts by the self-comment delta) as the right-hand side of the assertion.
  - **`thread_count` sum NOT asserted at FR-2-03 level**: per CL-12. FR-2-02 covers per-bucket correctness.
  - **`active_thread_count` sum NOT asserted at FR-2-03 level**: per CL-12. FR-2-02 covers per-bucket correctness.
  - **`coverage_partial` OR-coherence vs `comments.coverage_partial`**: LOGICAL OR over all reviewers R in `by_reviewer_comments` of `by_reviewer_comments[R].coverage_partial` EQUALS `rollup[W].comments.coverage_partial`. Tautological under CL-10 same-W lock; asserted as a producer-side bug guard against drift (e.g., a future regression where the producer fails to propagate the W-wide flag uniformly across reviewers in W).

  The truncated W26 demo fixture (`docs/data/aggregates/weekly_rollups/2025-W26.json` carrying `_prs_truncated: true` because W26 exceeds 310 INV-02's top-500-by-cycle-time cap) is the WITNESS that this contract holds even when the per-PR drill-down is truncated. The aggregator computes over the FULL canonical extracted-subset per FR-1-10; the drill-down truncation does not affect aggregator scope. The W26 fixture proves the parity holds on a truncated week, closing the deferred 334 / 335 cross-aggregate parity obligation on the reviewer dimension.

  The FR-2-03 parity test does NOT replace FR-2-02's end-to-end independent re-computation — sum-coherence-vs-independent-count is necessary but not sufficient (it can pass while both the aggregator and the independent count agree on a wrong number through a shared bug, e.g., both incorrectly excluding a comment type). FR-2-02 grounds correctness against direct SQL with C1 inclusion rules applied; FR-2-03 grounds cross-aggregate consistency between the aggregator's output and an independently-computed reference count.

- **FR-2-04 (test extension target — CL-06)**: The reconciliation test extension lives in `tests/integration/test_comments_trend_reconciliation.py` (extending 333's existing reconciliation test, already extended by 334 and 335) for FR-2-01 / FR-2-02 / FR-2-03. The 333 import-block isolation test (`tests/integration/test_comments_trend_reconciliation_isolation.py`) covers the extension automatically — aggregator imports from `src/ado_git_repo_insights/transform/aggregators.py` remain forbidden regardless of dimension scope.

- **FR-2-05 (failure-mode meta-test extension)**: The 334 / 335 meta-test (`tests/integration/test_comments_trend_meta_failure.py`) MUST be extended in-place with THREE new injections per the per-reviewer dimension:
  - **(a) Per-(week, reviewer) INV-4-07 violation**: mutate one bucket so `active_thread_count > thread_count`; assert FR-2-04 reconciliation FAILS on the mutated dataset.
  - **(b) FR-2-03 sum-coherence violation**: mutate one bucket's `comment_count` (e.g., subtract 1) so `SUM_R(comment_count)` no longer matches the independent count; assert FR-2-04 reconciliation FAILS on the mutated dataset.
  - **(c) Self-comment-leak violation (NEW for this feature)**: inject a synthetic bucket whose key is the PR author's own `user_id` (commenter == PR author edge); assert FR-2-04 reconciliation FAILS because either FR-2-02 (independent re-computation excludes self-comments) or FR-2-03 (independent count excludes self-comments) catches the leak. This catches silent-degrade-to-no-op for the CL-04 self-comment exclusion rule which is critical to the per-reviewer dimension's correctness.

### Functional Requirements — Render

- **FR-4-01**: When `capabilities.comments_metrics` is enabled, the dashboard MUST render a per-reviewer comment-density breakdown surface on the Metrics tab, positioned BELOW the 335 per-repo breakdown row (anchor `[data-comments-repository-density-row="true"]` per CL-11) and the existing throughput / cycle-time / reviewer-activity / summary-cards / 333 comments-trend / 334 per-author surfaces. The new row MUST carry the data attribute `[data-comments-reviewer-density-row="true"]`. Each row MUST show the reviewer's display label (per CL-05 lookup precedence) plus three numeric metrics (`thread_count`, `comment_count`, `active_thread_count`).

- **FR-4-02 (range-total reduction; all-zero filter BEFORE sort/truncate)**: The breakdown MUST honor the dashboard's existing date-range filter; changing the range MUST re-render the breakdown summing per-(week, reviewer) contributions across only the weeks falling inside the new range. The reduction unit is range-total per row (one row per reviewer across the visible weeks). Reviewers with zero contributions in the range (`thread_count == 0 AND comment_count == 0 AND active_thread_count == 0`) MUST NOT render — even when their constituent weeks have `coverage_partial: true`. **CRITICAL**: this all-zero filter MUST run BEFORE the sort step AND BEFORE the top-50 cap, NOT after — sorting by `active_thread_count` would otherwise hide reviewers with comments / threads but no active threads (per kickoff lesson from #335 session).

- **FR-4-03 (per-row partial-coverage qualifier)**: When a row's range-total `coverage_partial` reduces to `true` (any constituent week's per-(week, reviewer) `coverage_partial = true`), that row MUST render a partial-coverage qualifier consistent with 333 / 334 / 335's qualifier convention (the visual style — hatched fill / dimmed text / tooltip — inherits from the shared `.coverage-partial` CSS class hook). The qualifier MUST apply only to rows marked partial; non-partial rows render in the normal (non-partial) convention. The qualifier's tooltip text MUST emphasize **week-level** uncertainty (per CL-10 directive) — e.g., "This week's comments extraction is partial; reviewer activity may be incomplete" — NOT bucket-specific text that the data cannot support.

- **FR-4-04 (number formatting)**: Each row's three numeric metrics MUST use locale-aware integer formatting with no decimals (counts are whole numbers per FR-1-09), consistent with how throughput / 333's chart / 334's per-author / 335's per-repo breakdowns present numeric counts.

- **FR-4-05 (sort, CL-07)**: The breakdown MUST be sortable among the three metrics (`comment_count` / `thread_count` / `active_thread_count`); default sort is `comment_count` descending; ties break deterministically — first by reviewer display name ascending, then by bucket key ascending as the final tie-breaker (handles duplicate display names AND a sentinel/real-name collision per CL-05). The active sort metric MUST be visually indicated. Switching the sort metric MUST re-render rows in the new order. Sort selector pattern: WAI-ARIA Toolbar (memory: `feedback_wai_aria_toolbar_for_keyboard_reachability.md` / 334 / 335 pattern) — `role="toolbar"` wrapper + plain `<button>` elements (default `tabindex=0` + `aria-pressed`); each button is independently Tab-reachable; Enter / Space activates.

- **FR-4-06 (display cap, CL-07)**: The breakdown MUST render at most 50 rows (constant `MAX_COMMENTS_REVIEWER_DENSITY_ROWS = 50`) by chosen metric. If more reviewers have non-zero values than the cap, a truncation indicator MUST surface the count of hidden reviewers (analog of 334's `MAX_COMMENTS_AUTHOR_DENSITY_ROWS = 50` and 335's `MAX_COMMENTS_REPO_DENSITY_ROWS = 50` truncation patterns; noun "reviewers").

- **FR-4-07 (filter-not-supported posture)**: When ANY of the dashboard's per-PR dimension filters (`repos` / `teams` / `authors` / `reviewers`) is active, the breakdown MUST render a self-explanatory filter-not-supported empty state instead of rows. The empty state MUST be visibly distinct from the no-data-in-range empty state (FR-4-08) AND MUST disappear cleanly when filters are cleared. Per-dimension comments slices that would let the breakdown honor filters are deferred to a future feature (out of foundation-PR scope). The `reviewers` filter explicitly triggers this empty state — narrowing to a single reviewer is intentional design rather than a degenerate case.

- **FR-4-08 (no-data empty state)**: When the visible date range yields zero reviewers with non-zero contributions (capability-on path; e.g., zero PRs in range, or all PRs in range have `comments_extracted_at IS NULL`, or all comments are self-comments), the breakdown MUST render a self-explanatory no-data-in-range empty state distinct from filter-not-supported (FR-4-07).

- **FR-4-09 (no click-through, CL-08)**: Rows MUST NOT activate any drill-down or per-reviewer detail surface. The breakdown is informational. Plan-level: rows are not styled as clickable. A future per-reviewer drill-down panel is deferred outside this feature.

- **FR-4-10 (a11y)**: The sort selector MUST be keyboard-activatable (WAI-ARIA Toolbar pattern per FR-4-05); the breakdown table (or table-equivalent semantic structure) MUST expose per-row metric values via screen-reader-readable text. Pattern reference: 334's per-author breakdown / 335's per-repo breakdown `aria-pressed` / `tabindex` / `role` convention adapted for reviewer rows.

- **FR-4-11 (display label fallback per CL-05)**: When the `users` dimension entry for a given non-sentinel `user_id` is missing, the renderer MUST render the raw `user_id` value as the display label (CL-05 step 3). The sentinel branch (CL-05 step 1) takes precedence over both lookup and fallback. This case MUST be unit-tested at the renderer module — the test MUST construct a fixture with a `by_reviewer_comments[<id>]` entry whose ID is absent from the `usersDimension` array passed to the chart and assert the rendered row label equals the raw ID. This guards against regressions where a defensive empty-string or omit-row path silently hides a reviewer whose name lookup fails.
