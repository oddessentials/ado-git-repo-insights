# Quickstart: Comment visualization — Drill-down extension (Feature 310)

**Audience**: developer or team lead verifying Capabilities 3 + 4 locally after build. Covers the four in-feature acceptance criteria: SC-01 (identify most-discussed PR), SC-02 (identify unresolved-thread PRs), SC-03 (byte-identical baseline on capability-off), SC-04 (in-feature INV-07 closure).

SC-05 cross-feature reconciliation is NOT covered here — it is #322's obligation (see [plan.md](./plan.md) Phase 2 deferrals).

---

## Prerequisites

- Repo checked out, `pip install -e .[dev]` run, `pnpm --dir extension install` run.
- Local build of the extension: `pnpm --dir extension run build`.
- Demo dataset available under `artifacts/demo-enterprise/` (generated by `python scripts/build-demo-dataset.py` if missing).

## Step 1 — Produce both demo variants deterministically

Per R-08 (serialization-layer capability-off generation), both demo variants are produced by the canonical demo pipeline using a single generator code path; the `--comments-metrics` flag affects only serialization output, never generation. Result: the two variants are byte-identical except for the five gated keys.

```bash
# Produce both variants (canonical invocation)
python scripts/build-demo-dataset.py

# This runs generate-demo-data.py twice internally (once with
# --comments-metrics=true, once with --comments-metrics=false), producing:
#   artifacts/demo-enterprise/                   — capability-on (unchanged from pre-310)
#   artifacts/demo-enterprise-comments-off/      — capability-off (new in feature 310)
```

Sanity-check both manifests:

```bash
# Capability-on variant
python -c "import json; m = json.load(open('artifacts/demo-enterprise/data/dataset-manifest.json')); print(m['capabilities']['comments_metrics'])"
# Expected: True

# Capability-off variant
python -c "import json; m = json.load(open('artifacts/demo-enterprise-comments-off/data/dataset-manifest.json')); print(m['capabilities']['comments_metrics'])"
# Expected: False
```

Byte-identity verification (optional but informative):

```bash
python scripts/run_pytest.py tests/integration/test_demo_variants_byte_identity.py -v
# All three subtests pass: sorted-key-set equality, canonicalized byte equality, array-order parity.
```

A failure here is a **producer-contract bug**, not a test issue — it means the flag leaked into generation-layer logic instead of staying at the serialization layer (violates R-08's single-code-path constraint).

## Step 2 — SC-01: Most-discussed PR (capability on)

1. Open the extension dashboard pointed at the capability-on demo dataset (per existing dashboard bootstrap; the collectionUri / manifestPath parameters are branch-state-specific — consult `docs/data/` README).
2. Click a throughput-chart bar corresponding to a week with varied discussion depth (any mid-range week of the demo dataset qualifies).
3. The drill-down panel opens on the throughput chart. The "Pull requests" section now shows three additional columns per PR row: **threads**, **comments**, **unresolved** (labels may vary by implementation; semantics are per [data-model.md §1](./data-model.md)).
4. Click the **threads** column header to sort descending.
5. **Pass**: the top row of the PR list is the week's most-discussed PR (by `thread_count` after applying C1 inclusion rules).
6. Repeat with the **comments** column header.
7. **Pass**: the top row is the week's most-commented PR.

Interaction count: `sort + read = 2 interactions`. SC-01 threshold (`≤ 2`) satisfied.

## Step 3 — SC-02: Unresolved-thread PRs (capability on)

1. Using the same drill-down from Step 2, click the **unresolved** column header to sort descending.
2. **Pass**: every PR with `active_thread_count ≥ 1` appears above PRs with `active_thread_count = 0`.
3. Alternatively apply a filter (implementation detail per FR-3-03 / FR-4-02 — e.g., threshold input or column filter menu) of `unresolved ≥ 1`.
4. **Pass**: the filtered list narrows to PRs with at least one active thread. PRs with `null` (coverage partial) are surfaced in a distinguishable "partial" state per FR-3-05 / INV-10 — not silently dropped.

## Step 4 — SC-04: INV-07 in-feature closure (capability on)

For any PR visible in the drill-down, its rendered `thread_count`, `comment_count`, `active_thread_count` MUST be reproducible by a caller that reads `pr_threads` and `pr_comments` directly and applies the [Shared inclusion-rule contract (C1)](./spec.md).

Spot-check a single PR:

1. Pick one PR from the drill-down; note its `pull_request_uid`, `thread_count`, `comment_count`, `active_thread_count`.
2. Open the SQLite dataset at `artifacts/demo-enterprise/{dataset}.sqlite` (or the DB used by the capability-on demo).
3. Run:
   ```sql
   SELECT
     COUNT(*) AS thread_count,
     SUM(CASE WHEN status = 'active' THEN 1 ELSE 0 END) AS active_thread_count
   FROM pr_threads
   WHERE pull_request_uid = :uid
     AND is_deleted = 0;
   ```
4. Run:
   ```sql
   SELECT COUNT(*) AS comment_count
   FROM pr_comments
   WHERE pull_request_uid = :uid
     AND is_deleted = 0;
   ```
5. **Pass**: the three SQL results match the drill-down-rendered values.
6. If `pull_requests.comments_extracted_at IS NULL` for this PR: drill-down renders `null` (partial) for all three fields; the SQL counts may be any value — the NULL-sentinel takes precedence (FR-3-05 / INV-10).

## Step 5 — SC-03: Byte-identical baseline (capability off)

1. Point the extension at the **real capability-off artifact** produced in Step 1: `artifacts/demo-enterprise-comments-off/data/` (or `docs/data/comments-off/` once promoted). Do NOT use a synthetic-stripped fixture — per R-08 the baseline test must operate on the genuine pipeline-built artifact.
2. Open the same week's throughput-chart drill-down.
3. **Pass**: NO `threads` / `comments` / `unresolved` columns appear. The Pull Requests section renders the 5-field PR row shape identical to the pre-Feature-310 release.
4. Automated verification: `pnpm --dir extension test -- pr-list-capability-off-baseline` — the committed golden at `extension/tests/fixtures/throughput-drilldown-capability-off-baseline.html` is compared byte-for-byte against the DOM rendered from the real capability-off artifact. Test passes with zero drift.

Important: the test harness MUST load the artifact from `artifacts/demo-enterprise-comments-off/` (or its promoted `docs/data/comments-off/` location). Loading the capability-on artifact and stripping fields in test code would mask serialization-layer bugs that only manifest on a genuine pipeline-built capability-off variant — exactly the failure mode R-08 is designed to prevent.
