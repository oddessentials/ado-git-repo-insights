## User Scenarios & Testing _(mandatory)_

### User Story 1 - See which PRs a reviewer actually reviewed (Priority: P1)

A team lead opens the reviewer-activity chart, filters to a specific reviewer ("Alice"), and sees the panel headline say `"22 PRs reviewed"`. Today the panel stops there — to find out _which_ 22 PRs the user has to leave the dashboard, open Azure DevOps, and build a date+reviewer query manually. After this change, the same panel will also list those pull requests, slowest first, with a one-click link straight to each PR in Azure DevOps. The lead can immediately see which review queue Alice is carrying, whether her time is going into a few large PRs or a long tail of small ones, and click any row to see the diff.

**Why this priority**: This is the entire user-visible value of the feature. Without this story, the manager investigating reviewer load still has to leave the dashboard, build a query in ADO, and cross-reference it against the chart period — a workflow that typically takes several minutes and breaks the flow of investigation. With this story, the same investigation completes inside the dashboard in two clicks. Every other story in this feature is in service of making this one trustworthy and not misleading.

**Independent Test**: Filter the dashboard to a single reviewer with at least one qualified review in the period. Click the reviewer's bar in the reviewer-activity chart. Verify a list of pull requests appears in the side panel below the existing "Weekly activity" table, with the highest cycle times at the top, and that clicking any row opens that pull request in Azure DevOps in a new tab. Delivering only this story would already give a manager investigating any single reviewer the answer they need.

**Acceptance Scenarios**:

1. **Given** a reviewer filter is set to a single reviewer with at least one PR reviewed in the period and no team filter is active and comparison mode is off, **When** the user clicks the reviewer's row in the reviewer-activity chart, **Then** the side panel opens and shows, in this order: the reviewer's display name, the existing subtitle ("N PRs reviewed"), the existing four-cell stat row (Total reviews, PRs reviewed, Approval rate, Peak repositories), the existing "Weekly activity" breakdown table, and a list of pull requests for the period with the slowest first.
2. **Given** the side panel is already open showing the PR list for reviewer X, **When** the user clears the filter and re-applies it to reviewer Y, **Then** the panel content updates to show reviewer Y's PR list and stats — no stale rows from reviewer X remain visible. Existing panel-dismiss-on-filter-change behavior is preserved (the dismiss fires, the chart re-renders for reviewer Y, the panel is reopened by the user's next click).
3. **Given** the PR list is rendered, **When** the user clicks any PR row, **Then** the corresponding pull request opens in Azure DevOps in a new browser tab, leaving the dashboard state intact.
4. **Given** the PR list is rendered, **When** the user reads the rows top to bottom, **Then** the cycle times decrease (slowest first); ties on cycle time are broken by pull-request identifier, ascending.

**Construction (Option A locked)**: The list is constructed by concatenating each week's `by_reviewer[reviewerId].prs` array across the active period, then sorting the unioned set by `cycle_time desc, id asc` for stable rendering. The producer's per-(reviewer, week) sort is preserved within each week's slice, but the cross-week union MUST be re-sorted at the consumer. FR-019 makes the rendered DOM order the assertion target — not the input array shape — so the test catches consumer-side reorder bugs and producer-side drift identically.

### User Story 2 - Sensible behavior under filter overlays (Priority: P2)

The reviewer-activity drill-down differs from the throughput and cycle-time drill-downs in one critical way: **the reviewer filter is the SCOPE of the drill-down, not a blocker.** The reviewer chart only emits drill-down attributes on its rows when the user has selected a single reviewer (today's chart-side gating); without a reviewer filter, clicking a row is a no-op. So when this feature adds a PR list to the panel, the panel always opens with `filters.reviewers.length === 1`. The user-visible filter states therefore are:

- **No team filter, no comparison, optional author/repo filters**: the PR list shows pull requests reviewed by the focused reviewer (intersected with the active author/repo filters when present). This is the supported state.
- **Team filter active in addition to reviewer filter**: per-team intersection PR detail is intentionally deferred to a separate piece of work in the parent catalog (#318); the panel must replace the PR list with a short inline message ("Clear the team filter to see PRs"), verbally and visually identical to the message the throughput drill-down already shows under team-only filters.
- **Comparison mode on**: the existing comparison-advisory toast denial fires; no panel opens.

The nuance: in #361's cycle-time drill-down, the predicate `classifyFilterState(filters, false)` returns `"reviewer"` when the user has any reviewer filter set, and the cycle-time consumer maps that to a `reviewer-inline` "clear the reviewer filter" message. Reusing that predicate literally on the reviewer chart would always hit the `"reviewer"` branch — the panel would never show a PR list. The feature instead reuses the same predicate against a reviewer-stripped copy of the filter state (`{...filters, reviewers: []}`), so the classifier sees only "no team / team / supported" and the call site does not need to invent a parallel classifier.

**Why this priority**: Without this story, applying a team filter on top of a reviewer filter would either show a misleading PR list (rendered against the unfiltered set, contradicting the user's filter intent) or render a confusing empty state. The throughput drill-down already established the wording for "clear the team filter to see PRs"; for the reviewer drill-down to feel coherent next to it, the messaging must match exactly. Anything else feels like two charts written by two different teams.

**Independent Test**: With a single reviewer filter active, apply a team filter on top. Click the reviewer's row. Verify the panel shows the same `team-inline` "clear the team filter" message that the throughput drill-down already shows under team-only filters — same wording, same position. Clear the team filter, apply an author or repository filter on top of the reviewer filter, and verify the PR list renders normally with rows reflecting (reviewer ∩ author/repo) intersection.

**Acceptance Scenarios**:

1. **Given** the reviewer filter is set to a single reviewer AND a team filter is also active AND comparison mode is off, **When** the user clicks the reviewer's row, **Then** the panel's PR-list area is replaced by the inline "clear the team filter" message that is verbally and visually identical to the message the throughput drill-down panel shows under team-only filters.
2. **Given** the reviewer filter is set AND no team filter is active AND an author filter is also active, **When** the user clicks the reviewer's row, **Then** the PR list renders with rows representing the (reviewer ∩ author) intersection only.
3. **Given** the reviewer filter is set AND no team filter is active AND a repository filter is also active, **When** the user clicks the reviewer's row, **Then** the PR list renders with rows representing the (reviewer ∩ repository) intersection only.
4. **Given** the reviewer filter is set AND no team filter is active AND both an author filter AND a repository filter are active, **When** the user clicks the reviewer's row, **Then** the PR list renders with rows representing the (reviewer ∩ author ∩ repository) intersection only.
5. **Given** comparison mode is active at the moment of click, **When** the user clicks any reviewer row, **Then** the existing comparison-mode toast denial fires and no panel opens — behavior is unchanged from today.

**Intersection (Option A locked)**: Author and repository intersections are applied client-side on top of the per-(reviewer, week) `prs[]` slice. Each `PrRecord` already carries `author_id` and `repository_id`; the consumer filters by those fields after concatenation. The intersection is consumer-side and does not depend on the producer pre-emitting (reviewer × author × repository) tuples.

### User Story 3 - Honest signaling for high-volume and unavailable-data states (Priority: P3)

For some heavy reviewers in some weeks, the underlying PR set may exceed the producer's display cap. The panel needs to tell the user "you are looking at the slowest N of M PRs" rather than silently truncating. The throughput drill-down already renders this cue when its own list is truncated; the reviewer list should match.

Likewise, when per-PR detail is unavailable for the focused reviewer in the active period, the section must show a brief inline empty-state message instead of silently disappearing — preserving the panel's section ordering and signaling clearly that the data, not the feature, is the limitation. Per-PR detail is unavailable when (a) the reviewer has zero qualifying PRs in the period (e.g., they haven't reviewed anything in the displayed weeks), (b) the host data is loaded outside an Azure DevOps web context (so PR URLs cannot be composed), or (c) the rollup is malformed in a way that omits the truncation cap marker for the per-(reviewer, week) cap. The user sees the same inline empty-state message in all three cases — the throughput drill-down already exposes that exact state (`supported-empty`) and the reviewer drill-down must match it.

**Why this priority**: Most reviewers in most weeks will not hit the truncation cap, and the unavailable-data states are uncommon in practice. So this is not the primary value driver. But silently truncating without signaling — or silently dropping the section under unavailable-data conditions — would erode trust in every other view: a user who has been bitten once by a hidden truncation will second-guess every reviewer-load count thereafter. The cost of surfacing the cue is small; the cost of not surfacing it is cumulative across the entire product.

**Independent Test**: For the truncation case, identify (or construct via fixture) a reviewer-period whose PR set exceeds the per-(reviewer, week) cap, click the reviewer's row, and verify the same truncation cue the throughput drill-down already shows. For the empty case, construct a fixture reviewer with zero PRs reviewed in the active period and verify the same `supported-empty` inline message the throughput drill-down already shows for the same condition.

**Acceptance Scenarios**:

1. **Given** the focused reviewer's PR set for the active period exceeds the per-(reviewer, week) cap and no team / comparison gate is active, **When** the user clicks the reviewer's row, **Then** the panel renders the same truncation cue the throughput drill-down renders for the same condition.
2. **Given** the focused reviewer has zero PRs reviewed in the active period (a rare but possible state — e.g., the reviewer was on leave, or all their reviews were rejected with vote=0 which the existing aggregator filters out), **When** the user clicks the reviewer's row, **Then** the PR list section renders the same `supported-empty` inline message that the throughput drill-down renders for its zero-PR case — section ordering in the panel is preserved.
3. **Given** the dashboard is loaded outside an Azure DevOps web context (so the PR URL composer has no `webContext` to anchor against), **When** the user clicks any reviewer row, **Then** the PR list section renders the same `supported-empty` inline message — no half-built rows, no link-less list.
4. **Given** the reviewer has PRs in the active period but the rollup payload is missing the per-(reviewer, week) truncation cap marker (a malformed-payload state the schema validator warns on but does not reject), **When** the user clicks the reviewer's row, **Then** the PR list section renders the same `supported-empty` inline message — fail-soft to the empty state rather than rendering an unbounded list.

**Truncation cap shape (Option A locked)**: The cap is per-(reviewer, week). The producer truncates the per-(reviewer, week) `prs[]` slice when it exceeds the option's per-key cap (named `_prs_cap` on the inner `ReviewerBreakdownEntry`, with `_prs_truncated: bool`). The consumer detects truncation by reading the per-key marker on each rollup's `by_reviewer[reviewerId]` entry and OR-ing across the union of weeks the focused reviewer participated in. FR-010 specifies that the producer flag is the truth source — the consumer never independently truncates.

**Demo dataset note**: the demo generator (`scripts/generate-demo-data.py`) MUST mirror the new sub-array under each `by_reviewer[reviewerId]` entry. The demo should NOT exhibit a per-(reviewer, week) truncation under typical seed sizes (the demo's per-week PR count is bounded well below 500, so per-reviewer slices are even smaller). Demo behavior is data-state-driven; the appropriate state renders without further spec change once the producer side is wired.

### Edge Cases

- **Reviewer not present in any week's by_reviewer map**: today's reviewer drill-down opens the panel with zeros in the stat row and an `EmptyStateSection` for the weekly activity table (FR-071 lock at `reviewer-drilldown.ts:138-141`). The PR list section MUST emit the same `supported-empty` content state in this case — section ordering preserved, no header-only PR list.
- **Reviewer has weeks with reviews but the per-(reviewer, week) `prs[]` is empty for those weeks**: this is a producer-side coherence bug — the spec asserts `reviewed_prs == prs.length` as an invariant per-(reviewer, week) entry. The consumer renders `supported-empty` — fail-soft. Producer-side coherence tests catch the bug, not the consumer.
- **Single qualified PR for the reviewer**: the PR list still renders as a single-row list. Subtitle wording stays consistent (existing "N PR" / "N PRs" pluralization at `reviewer-drilldown.ts:156`).
- **Comparison mode toggled on while panel is open**: the existing panel-dismiss behavior triggers; no new code path is introduced by this feature. Reviewer-drill-down's existing comparison-toggled lifecycle handler (verified at `reviewer-drilldown.test.ts:497-502`) is preserved.
- **Filters changed while panel is open**: the existing panel-dismiss behavior triggers; no new code path is introduced.
- **Reviewer-id is a UUID GUID not present in the dimensions table**: today's behavior renders the GUID verbatim as panel title (`reviewer-drilldown.test.ts:216-242`). This is preserved unchanged; the PR list rows are unaffected by the title-resolution fallback path.
- **Reviewer-id contains an apostrophe or other CSS-attribute-special character**: row data attributes are HTML-escaped via the existing chart's `escapeHtml` (verified at `reviewer-activity.ts:207`). The PR list section consumes the resolved id from `data-drilldown-reviewer-id`; no new escape surface is introduced.
- **Host data without comments-metrics capability**: PR rows render with the same baseline columns (title, cycle time, link to ADO) the throughput drill-down renders before per-row comments counts existed — visually identical layout to throughput's pre-310 shape, no reserved space for absent columns.
- **Host data with comments-metrics capability**: PR rows include the same per-row thread, comment, and unresolved-thread counts the throughput drill-down already shows under the same capability — no new column, no new wording, no new policy introduced here. Capability gate is the existing `commentsMetricsAvailable` flag.
- **PR row with partial comments coverage**: when the capability is on but a particular PR's comments coverage is incomplete, the row's comments-metrics cells render the same partial-coverage indicator the throughput drill-down already renders (existing `isPartialPrRow` discriminator). This feature does not invent new partial-state semantics.
- **Producer-emitted PR order ever drifts**: if a future producer change re-orders the per-(reviewer, week) `prs[]` array away from `cycle_time desc, id asc`, the consumer-side rendered-order assertion (FR-019) fails. Implementation may either trust producer order or sort at the consumer; the test is the source of truth on what the user sees.

## Requirements _(mandatory)_

### Functional Requirements

#### Section ordering and visibility

- **FR-001**: When the user clicks a reviewer's row on the reviewer-activity chart with a single reviewer filter active, no team filter active, and comparison mode off, the side panel MUST render a list of pull requests for the focused reviewer, in addition to the existing reviewer-name title, subtitle, stat row, and weekly activity breakdown table.
- **FR-002**: The PR list section MUST appear AFTER the existing "Weekly activity" breakdown table in the panel content order, so the user reading top-to-bottom sees aggregate context first (stat row → weekly table), then specific PRs.
- **FR-003**: PR rows MUST be ordered slowest first (cycle time descending; pull-request identifier ascending as the stable tiebreak), so the natural top-of-list scan surfaces the PRs that drove the reviewer's load most.

#### Click-through and per-row behavior

- **FR-004**: Each PR row MUST be a click-through hyperlink to the pull request in Azure DevOps; activating the row opens the PR in a new tab/window without disturbing the dashboard state, panel state, or filter state.
- **FR-005**: When the host data carries the comments-metrics capability, the PR list rows MUST display the same per-row thread, comment, and unresolved-thread counts the throughput drill-down already displays under the same capability. When the capability is off, the PR list rows MUST render in a layout visually identical to the pre-capability shape — no reserved column space for absent counts.

#### Filter classification

- **FR-006**: When the reviewer filter is active AND a team filter is also active AND comparison mode is off, the PR list section MUST be replaced with the same `team-inline` message that the throughput drill-down panel shows under team-only filters — verbally and visually identical, same wording, same position. (Distinct from the empty-state in FR-011.)
- **FR-007**: When the reviewer filter is active AND no team filter is active AND no comparison gate is active AND any combination of author and/or repository filters may be present, the PR list MUST render the period filtered to the focused reviewer (intersected with author and repository when those are present). The existing throughput-equivalent `reviewer-inline` message MUST NOT appear on the reviewer chart's drill-down — the reviewer filter is the SCOPE on this surface, not a blocker.
- **FR-008**: The classifier the consumer uses to derive the four content states MUST reuse the existing shared `classifyFilterState` predicate (the narrowed-return overload, since comparison is short-circuited upstream) — but invoked against a reviewer-stripped copy of the filter state: `classifyFilterState({...filters, reviewers: []}, false)`. The classifier MUST NOT be reimplemented at the call site (per the static-authority invariant). The reviewer-stripping wrapper MUST be co-located with the reviewer drill-down module so the divergence from cycle-time/throughput's literal reuse is reviewable in one place.
- **FR-009**: When comparison mode is active at the moment of click, the existing comparison-mode toast denial behavior MUST remain unchanged: no panel opens, the toast informs the user that drill-down is unavailable in comparison mode (existing `reviewer-drilldown.ts:232-235` short-circuit, regression-locked).

#### Data states

- **FR-010**: When the focused reviewer's per-(reviewer, week) `prs[]` slice exceeds the per-(reviewer, week) cap in any week the focused reviewer participated in, the panel MUST render the same truncation cue the throughput drill-down already renders for the same condition. The cue MUST appear whenever any week's `by_reviewer[reviewerId]._prs_truncated` flag is `true`, and MUST NOT appear when no week's flag is set. The consumer detects truncation by OR-ing the per-key marker across the active period's weeks the focused reviewer participated in.
- **FR-011**: When per-PR detail is unavailable for the focused reviewer in the active period — that is, the union of per-(reviewer, week) `prs[]` slices is empty, OR the host data lacks an Azure DevOps web context for URL composition, OR any participating week's `by_reviewer[reviewerId]` entry is malformed (`prs` present but `_prs_cap` absent) — the PR list section MUST render the same `supported-empty` inline message that the throughput drill-down renders under the same conditions. The section MUST NOT be omitted; section ordering in the panel is preserved across all data scenarios.

#### Section identity

- **FR-012**: The PR list section's heading and accessible name MUST remain stable across all three content states the reviewer drill-down can reach (`pr-list`, `supported-empty`, `team-inline`). Assistive technology hears one consistent section identity regardless of which content state is rendered. (Note: unlike #361, the reviewer drill-down does NOT reach the `reviewer-inline` content state — the reviewer-stripping wrapper at FR-008 makes that branch unreachable on this chart by construction. The accessible-name stability assertion therefore covers three content states, not four.) Coverage MUST be proven by a consumer-side automated test on the reviewer drill-down — citation of the throughput or cycle-time equivalent is NOT sufficient, since those tests cover differently-rendered DOM.

#### Keyboard / a11y reachability

- **FR-013**: Drill-down activation on the reviewer-activity chart MUST continue to work via mouse click and via Enter / Space when a row is keyboard-focused — unchanged from today's behavior at `reviewer-drilldown.ts:267-277` and locked by `reviewer-drilldown.test.ts:508-538`. The PR list rows MUST be reachable via Tab once the panel is open, in the same focus order the throughput drill-down already establishes for its PR list. Coverage MUST be proven by consumer-side automated tests on the reviewer drill-down: at least one test for keyboard activation of a reviewer row opening the panel with a PR list, and at least one test for Tab reachability of PR rows inside the reviewer panel. Citation of the throughput or cycle-time equivalent is NOT sufficient — those tests exercise differently-rendered DOM.

#### Retarget-in-place

- **FR-014**: Switching from one reviewer-row to another reviewer-row by changing the reviewer filter (which dismisses the panel and re-renders the chart) MUST result in the panel re-opening on next click with the new reviewer's content; the PR list MUST be the new reviewer's set, not the prior reviewer's. The existing detail-panel dismiss-on-filter-change lifecycle is preserved unchanged. Within a single reviewer (no filter change), there is no metric-to-metric retarget on this chart (unlike cycle-time's P50↔P90 retarget at #361's FR-014); the reviewer chart is one bar per week, no per-bar metric switching.

#### Producer-side constraints

- **FR-016**: The aggregator's `_generate_reviewer_slice` (`src/ado_git_repo_insights/transform/aggregators.py:2139-2201`) MUST emit a `prs: list[PrRecord]` field on each per-(reviewer, week) entry, scoped to PRs where the reviewer cast a non-zero vote (mirroring the existing `outcome_group` filter at `aggregators.py:2177-2179`). The slice MUST be sorted `cycle_time desc, id asc` BEFORE the cap is applied — so when the slice is truncated, the retained 500 records are the highest-cycle-time PRs (the user-visible "slowest first" contract is preserved across the truncation boundary, not subverted by it). The cap value is **500**, exposed as the producer-side constant alias `_PR_DETAIL_CAP_PER_REVIEWER_WEEK = _PR_DETAIL_CAP` (defined alongside the existing `_PR_DETAIL_CAP: Final[int] = 500` at `aggregators.py:84` so future divergence is a one-line edit, not a call-site grep; the alias matches the production naming convention — the user's CL-02 wording `MAX_PRS_PER_REVIEWER_WEEK = MAX_PRS_PER_WEEK` was a semantic placeholder, since `MAX_PRS_PER_WEEK` does not exist in production code today). The truncation pair (`_prs_truncated: bool`, `_prs_cap: int`) MUST be emitted alongside the `prs` field on the same per-(reviewer, week) entry, atomic with the slice itself. `_prs_cap: 500` is emitted whenever the slice is present. `_prs_truncated: true` is emitted ONLY when the pre-truncation slice exceeded 500 (NOT when it equals 500 exactly — at exactly-500 the slice is uncapped). The Python `ReviewerSliceMetrics` TypedDict (in `src/ado_git_repo_insights/transform/types.py` — exact location to be pinned in Pass-3 plan validation) MUST be extended with the matching field set: `prs: list[PrRecord]`, `_prs_truncated: bool`, `_prs_cap: int`.
- **FR-017**: This feature MUST NOT change the field set of the existing 5+3 `PrRecord` contract. The Python `PrRecord` TypedDict (`types.py:289+`), the TypeScript `PrRecord` interface (`rollup.schema.ts:90-99`), the `PR_RECORD_REQUIRED_FIELDS` array literal, and the canonical-field declaration table at `specs/310-comments-visualization/contracts/pr-record-comments-fields.md` §1 ALL stay unchanged. The cross-surface schema-parity gate at `scripts/check_pr_record_schema_parity.py` MUST stay green by no-op — its `_TS_ACCEPTED_TYPES`, `_TS_FIELD` regex, `PYTHON_VALUE_TYPES`, and AST traversals are NOT touched. The TypeScript `ReviewerBreakdownEntry` interface at `rollup.schema.ts:58-64` IS extended with the new fields; this is a separate contract from `PrRecord` and is not subject to the schema-parity gate.

#### Consumer regression locks

- **FR-018**: This feature MUST NOT change the behavior of any other chart's drill-down (throughput, cycle-time, sparkline) or any other panel surface. All previously-passing drill-down behavior on other charts MUST remain unchanged. All 859 lines of currently-passing reviewer-drilldown tests at `reviewer-drilldown.test.ts` MUST continue to pass without modification, except where new tests are added for the new PR list section (existing tests' assertions on stat row, weekly table, MutationObserver, dispose, comparison advisory, keyboard activation, a11y attribute surface, rerender sequence, and the empty-state-when-reviewer-not-found path are preserved).

#### Order assertion

- **FR-019**: A consumer-side automated test on the reviewer drill-down MUST assert the rendered DOM order of PR rows is `cycle_time` descending with `id` ascending as the stable tiebreak. The assertion MUST operate on the rendered output, not on the input array — so the contract holds whether the implementation trusts the producer's existing sort or sorts in the consumer. If a future producer change re-orders the underlying source array, this test fails immediately, surfacing the drift before users see it.

A PR reviewed by N reviewers in a week appears in N per-(reviewer, week) entries; the duplication is the byte-cost trade-off of this option (measured before/after per SC-014).
- **Filter classification (with reviewer-stripping wrapper)**: the reviewer surface's reading of the active filter set under the FR-008 wrapper.
