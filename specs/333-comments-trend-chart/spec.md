# Feature Specification: Dashboard weekly discussion-volume trend chart + SC-05 cross-feature reconciliation

**Feature Branch**: `feat/333-comments-trend-chart`
**Created**: 2026-04-26
**Status**: Draft (locked decisions inherited from #322 parent + 310 sibling spec; planning-readiness pending Pass 2 code-validation)
**Issue**: #333 (split from #322 — Capability 1 of #182)
**Input**: Issue #333 body + locked product decisions from this session: chart shape A (stacked bars + overlaid line, no toggles), single PR scope, SC-05 reconciliation test as the sole authority for rollup parity (no schema-parity gate extension). C1 inclusion-rule contract referenced from `specs/310-comments-visualization/spec.md` lines 75–87 — not re-declared.

## Overview

Feature 310 shipped per-PR comments-metrics on the throughput drill-down panel but deferred the dashboard half of the original #182 ask. There is no weekly time-series view of review-conversation volume on the main dashboard, so a team lead cannot answer "is our team having more or fewer review conversations over time?" without opening individual drill-downs week by week.

This feature adds a single dashboard chart that surfaces weekly conversation volume and unresolved-thread load at a glance, alongside the existing throughput / cycle-time / reviewer-activity charts. It is the **foundation PR for the #322 dashboard block** — three sibling Cap-2 PRs (#334 per-author, #335 per-repo, #336 per-reviewer breakdowns) inherit the rollup-schema extension and the cross-feature reconciliation contract that this PR establishes.

The feature is additive and gated on `capabilities.comments_metrics`. The dashboard MUST render byte-identical to its current rendering for users without comment extraction enabled.

## Background — locked decisions inherited from prior clarifications

These decisions are inherited and MUST NOT be re-litigated in this spec. Authoritative sites are referenced inline.

- **Chart shape — stacked bars + overlaid comment line, no toggles.** Each weekly bar is stacked: the lower segment is resolved threads (`thread_count − active_thread_count`); the upper segment is unresolved threads (`active_thread_count`). A single line series for `comment_count` is overlaid on the same vertical axis. No metric toggles, no per-series interaction beyond click-to-drill. Locked in this session.
- **SC-05 reconciliation test is the sole authority for weekly-comments-aggregate parity.** Schema-parity gate (Row 38, QG-49 in `LOCAL_CI_PARITY_INVARIANTS.md`) covers only the per-PR `PrRecord` shape and is intentionally NOT extended to cover the new weekly comments aggregate object. The reconciliation test (FR-2-04) guarantees parity via two assertions: (a) **cross-surface coherence on the extracted-subset of the intersection** — drill-down per-PR counts equal the aggregator's per-PR contributions to the weekly comments aggregate on the drill-down's top-500-by-cycle-time slice ∩ W's extracted-subset (PRs with `comments_extracted_at IS NOT NULL`); unextracted PRs in the slice agree as "no data / pending" via different sentinels (drill-down null + aggregator zero-contribution) and are not pairwise-compared; (b) **end-to-end aggregator correctness via independent re-computation** — for each week W, each numeric field of `rollup[W].comments` equals the result of an independent computation that determines W's canonical throughput PR set independently of the comments aggregator, applies the SAME extracted-subset filter (PRs without `comments_extracted_at` contribute zero), reads `pr_threads` / `pr_comments` directly for the extracted-subset, applies C1 per PR, sums, and re-derives `coverage_partial` (asserts equality with the aggregator's emitted value). Three structural guards reinforce the test against silent decay: (i) FR-2-04 (b)'s **import-level isolation** — the independent re-computation MUST share no code, helpers, or shared utilities with the comments aggregator's bucket-computation path, enforced by an import-level structural check or a module-boundary mechanism (not by code-organization convention); (ii) FR-2-03's **week-attribution parity guard** — a single canonical week-attribution function shared by both aggregators, OR a per-PR parity test against throughput, NEVER duplicated logic without one of those guards; (iii) FR-2-05's **failure-mode meta-test** — a synthetic dataset injecting a known violation (e.g., `active_thread_count > thread_count` inside `rollup[W].comments`) MUST cause the FR-2-04 test to fail, proving the reconciliation test is real rather than passively passing. Capability-off byte-identity extends to the serialization layer (FR-3-03): the entire `comments` object MUST NOT appear in capability-off manifests. Cardinality-only or self-consistency-only checks were considered and rejected as insufficient — the aggregator could otherwise satisfy its own checks while emitting wrong values for set membership, per-PR contributions outside the drill-down intersection, or sum math. Bucket-sum-equals-drill-down-sum is intentionally NOT the contract — the chart aggregates over W's extracted-subset (which can exceed the drill-down's top-500 slice for high-volume weeks) to honor user-value SC-1-01, while the drill-down inherits 310's top-500 cap (INV-02), so for weeks with >500 extracted PRs the chart bucket exceeds the drill-down per-PR sum by design. Locked in this session.
- **C1 inclusion-rule contract is authoritative at `specs/310-comments-visualization/spec.md` lines 75–87.** This feature MUST reference that section and MUST NOT re-declare inclusion rules. Re-declaration is itself an INV-07 violation. Locked in 310 spec Pass 2.
- **C2 reviewer semantics, C3 density unit, C4 team slice deferral.** These are sibling Cap-2 concerns (#334–#336 + #321) and are out of scope for this feature. Inherited from #322 body.
- **Weekly comments aggregate object locked.** All weekly comment-metric data emitted by this feature lives in a single sub-object on the rollup root: `rollup[W].comments`, containing four fields — `thread_count: number`, `comment_count: number`, `active_thread_count: number`, `coverage_partial: boolean`. **The three numeric fields are "known extracted-subset totals," not full-week truth**: each is the sum over W's canonical throughput PR set of the per-PR value for PRs with `pull_requests.comments_extracted_at IS NOT NULL`; PRs without extracted comment data contribute zero (equivalent to omission). The `coverage_partial: boolean` field is `true` if AND ONLY IF at least one PR in W's canonical throughput PR set has `pull_requests.comments_extracted_at IS NULL` — meaning the numeric totals undercount the full-week truth by the contributions of those unextracted PRs. The visual qualifier (FR-1-04) communicates this incomplete-totals state to the user. Numeric values stay non-null even when partial (no nullable schema); the rendered bar shows the known-extracted-subset sum, with the visual qualifier surfacing the "incomplete" caveat. Gated on `capabilities.comments_metrics`: when capability is off, the entire `comments` object is absent (no partial-shape variants). When the object is present, all four fields are present together (atomicity per INV-1-08). Resolved 2026-04-26 across Codex stop-time reviews (round 5: dataset-level signal insufficient → per-week emission; round 6: rollup-root flat-key shadowing → sub-object namespace; round 7: numeric-vs-null contradiction when partial → extracted-subset rule with `coverage_partial` warning the undercount). Field contracts and test coverage live in FR-2-06; consumed by FR-1-04 and INV-1-07; gated by FR-3-03; atomicity locked by INV-1-08; cross-surface pairwise scope is FR-2-01 (extracted PRs only — unextracted PRs reconcile as "no data / pending" via different sentinels, not pairwise numeric equality).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Spot the conversation-volume trend at a glance (Priority: P1)

A team lead opens the dashboard's Metrics tab on a Monday morning and wants to see how review-conversation volume has changed over the last quarter. They look at the new comments-trend chart and immediately see, for each week in the selected range, how many threads were opened (split into resolved vs. unresolved) and how many individual comments were exchanged across the PRs whose comment data has been extracted. Weeks where some PRs are still pending extraction are visually qualified (FR-1-04) so the team lead can distinguish "small bar = quiet week" from "small bar = incomplete data, more conversation may emerge as extraction completes." Without sorting, filtering, or clicking, they can answer "across what we know so far, is our team having more or fewer review conversations over time?" and "is the known unresolved-discussion load building up?" — with the partial-coverage qualifier as the explicit warning that partial-week values are extracted-subset totals, not full-week truth.

**Why this priority**: This is the entire user-visible reason the feature exists. Capability 1 of #182 was articulated as "weekly trend chart"; without P1 the feature has no value. The chart's first-glance readability is the success criterion — any need to interact (toggle, sort, hover) before getting the answer is a usability regression.

**Independent Test**: Open a demo dashboard that has `capabilities.comments_metrics` enabled and at least 8 weeks of data. Confirm a chart titled with conversation/comment vocabulary renders below the existing four charts on the Metrics tab. Confirm each week is represented by a single stacked bar with two visually distinct segments and an overlaid line value. Confirm the chart honors the dashboard's existing date-range filter (changing the range narrows or widens the visible weeks). User Story 2 (drill-down click-through) is not required to be present for this test.

**Acceptance Scenarios**:

1. **Given** a dataset where `capabilities.comments_metrics` is enabled and the selected range contains 12 weeks, **When** the user opens the Metrics tab, **Then** the comments-trend chart renders with 12 weekly bars, each split into resolved + unresolved segments, with an overlaid comment-count line and a legend that names all three series.
2. **Given** the chart is rendered, **When** the user changes the dashboard's date range to a narrower window, **Then** the chart re-renders showing only the weeks within the new range, consistent with the throughput chart's behavior.
3. **Given** a dataset spans more than the chart's display cap (e.g., 130 weeks of data and a 104-week display cap), **When** the chart renders, **Then** it shows the most recent capped slice and surfaces a truncation indicator consistent with the throughput chart's pattern.
4. **Given** a week in the visible range has `rollup[W].comments.coverage_partial === true` (per FR-2-06: any PR in W has `comments_extracted_at IS NULL`), **When** that bar renders, **Then** it is visually distinguishable from full-coverage bars and the legend or tooltip explains the convention.

### User Story 2 — Drill into a specific week directly from the chart (Priority: P2)

The team lead notices a week with unusually high known unresolved-thread load (or, on a partial-marked week, wants to see which extracted PRs are driving the visible portion of the load) and wants to see which PRs are responsible. They click that week's bar; the existing drill-down panel opens for that week, showing the comments columns shipped by Feature 310 (thread count, comment count, unresolved-thread count per PR — with 310's per-PR partial sentinel for any PR still pending extraction).

**Why this priority**: Click-through reuses the existing Feature 060 drill-down panel and the Feature 310 columns — no new drill-down code is added by this feature. The integration is an inherited capability, not new behavior. Sequencing it as P2 lets P1 ship as the minimum viable unit; the click-through is a low-cost addition that closes the loop from "spot the spike" to "see the PRs."

**Independent Test**: With User Story 1 visible, click any bar. Confirm the drill-down panel opens for the corresponding week and the PR list shows the comments columns from Feature 310. Confirm the panel uses the same open/close lifecycle as bars on the throughput chart.

**Acceptance Scenarios**:

1. **Given** the comments-trend chart is rendered with `capabilities.comments_metrics` enabled, **When** the user clicks a weekly bar, **Then** the existing drill-down panel opens for that week and shows the PRs in that week with their comment-metric columns (per Feature 310).
2. **Given** a bar is focused via keyboard, **When** the user activates it (Enter or Space), **Then** the drill-down opens with the same panel state as a click, and the bar's `aria-expanded` attribute reflects the open state — consistent with the throughput chart's accessibility contract.

### Edge Cases

- **Zero-comment week within the visible range** (week has PRs, all extracted, but none had any comments/threads — `coverage_partial === false`, all three numeric fields = 0): the bar renders explicit zeros — height of zero, no segment of either color, with the comment line continuing from the prior week's value to the next. The absence of the partial-coverage visual qualifier distinguishes this honest-zero week from an "all-unextracted" week with the same numeric values but `coverage_partial === true`.
- **All PRs in week unextracted** (`coverage_partial === true`, `thread_count === 0`, `comment_count === 0`, `active_thread_count === 0`): the bar renders height-zero (sum over an empty extracted-subset) AND the partial-coverage visual qualifier. The qualifier is what distinguishes "we don't know yet" from a true-zero week — a renderer MUST honor this distinction (FR-1-04 mandates the qualifier applies only to weeks marked partial). The drill-down for this week, when opened, would show all PRs in 310's per-PR partial sentinel state (per INV-10).
- **Some PRs in week unextracted (mixed)** (`coverage_partial === true`, numeric fields are partial extracted-subset sums > 0): the bar renders with the partial sums (segment heights from the extracted-subset totals) AND the partial-coverage visual qualifier. The chart honestly shows what's known so far; the qualifier warns the user that more conversation volume may be discovered as extraction completes for the unextracted PRs.
- **All-active or all-resolved week** (all threads in the week are still active, or all are closed): the bar shows only one stacked segment color (the other has height zero); the legend item for the absent color is not removed (legend remains stable across weeks).
- **Single-week dataset** (1 week of data after filter): the chart still renders with a single bar; the line series shows a single dot rather than a line; legend renders normally.
- **Bar count exceeds display cap** (>104 weeks of data): chart shows the most recent 104 weeks and surfaces a truncation indicator; the dashboard's date-range filter is the user-facing remediation.
- **Week with more than 500 PRs** (drill-down inherits 310 INV-02 cap; chart aggregates over W's extracted-subset, which can include PRs outside the drill-down slice): the chart bar shows the extracted-subset totals across all extracted PRs in W (scoped by extraction completeness — qualified per FR-1-04 when partial — not by the drill-down's top-500 cycle-time cap); the drill-down shows the slowest 500 PRs by cycle-time (per existing 060 contract); summing the per-PR drill-down counts therefore yields a number less than the chart bar's value when W's extracted-subset extends beyond the drill-down's slice. This is intentional — the chart is the surface that reports the known weekly volume across all extracted PRs (with the partial-coverage qualifier when the canonical PR set has unextracted PRs), the drill-down is the surface that surfaces specific high-cycle-time PRs to investigate. The same scope difference already exists between the throughput chart's PR count and its drill-down today; this feature inherits the convention rather than inventing a new one.
- **Coverage partial across the entire visible range** (every week's `rollup[W].comments.coverage_partial === true`): all bars use the partial-coverage rendering convention; the chart legend's partial-coverage entry is the single visible explanation; no separate banner appears.
- **`rollup[W].comments.active_thread_count > rollup[W].comments.thread_count`** (data integrity violation per INV-1-06): MUST NEVER occur if the aggregator and inclusion rules are correct. Treat as a backend bug; the chart MUST NOT silently coerce. Surfaced via the SC-05 reconciliation test.
- **Capability flips OFF during a session** (dataset reload): chart container must remove cleanly without leaving stale geometry on the dashboard layout.

## Requirements *(mandatory)*

### Functional Requirements — Chart rendering

- **FR-1-01**: When `capabilities.comments_metrics` is enabled, the dashboard MUST render a weekly time-series chart for `thread_count`, `comment_count`, and `active_thread_count` on the Metrics tab.
- **FR-1-02**: The chart MUST render each week as a single bar stacked into two segments — `(thread_count − active_thread_count)` resolved (lower) and `active_thread_count` unresolved (upper) — with `comment_count` overlaid as a line series on the same vertical axis. No metric toggles, no per-series interaction beyond bar-click drill-down (per FR-1-05).
- **FR-1-03**: The chart MUST honor the dashboard's existing date-range filter; changing the range MUST re-render the chart with only weeks falling inside the new range.
- **FR-1-04**: When a week's `rollup[W].comments.coverage_partial` field is `true` (per FR-2-06), that week's bar MUST be rendered in a visually distinguishable convention consistent with the partial-state convention used elsewhere in the dashboard. The convention MUST be explained either in the chart legend or via tooltip on the partial-rendered bar. Weeks where `rollup[W].comments.coverage_partial` is `false` MUST be rendered in the normal (non-partial) convention; the visual qualifier MUST apply only to weeks marked partial, never blanket-applied across all bars.
- **FR-1-05**: Each weekly bar MUST be activatable (mouse click, keyboard Enter/Space when focused) and activation MUST open the existing drill-down panel for that week. The bar's `aria-expanded` state MUST reflect the panel state, consistent with the throughput chart's accessibility contract.
- **FR-1-06**: The chart MUST surface a truncation indicator and apply a display cap consistent with the throughput chart's behavior when the data range exceeds the cap.

### Functional Requirements — Cross-feature reconciliation (SC-05 closure)

- **FR-2-01 (C1 cross-surface coherence — per-PR pairwise, scoped to extracted-subset)**: For every PR P in the drill-down panel for week W AND in W's extracted-subset (i.e., `pull_requests.comments_extracted_at IS NOT NULL` for P), the per-PR `thread_count` / `comment_count` / `active_thread_count` values rendered in the drill-down (PrRecord fields per 310's contract) MUST equal the same PR's per-PR contribution to the corresponding numeric fields of `rollup[W].comments` as computed by the aggregator. This is per-PR pairwise equality on the extracted-subset of the drill-down ∩ aggregator intersection (P's drill-down value == P's aggregator contribution), NOT bucket-sum-equals-drill-down-sum. For PRs in the drill-down's top-500 slice that are NOT in W's extracted-subset (`comments_extracted_at IS NULL`), the test MUST EXPLICITLY EXCLUDE them from the pairwise numeric comparison AND MUST EXPLICITLY ASSERT that the drill-down renders them via 310's per-PR partial sentinel (INV-10 — i.e., `null` / `undefined` for each of the three per-PR numeric fields, NOT zero, NOT a number, NOT silently absent). This positive assertion verifies that the "no data / pending" state correctly surfaces on the drill-down side, while the aggregator's exclude-from-sum (per FR-2-03 extracted-subset rule) handles the producer side; the two surfaces agree on "no data / pending" via different but each individually-asserted conventions. The contract verifies that the C1 inclusion rules apply identically across the two code paths for PRs that have extracted data, AND that the partial-state sentinel is honored for PRs that do not.
- **FR-2-02**: The inclusion rules governing `thread_count`, `comment_count`, and `active_thread_count` in this feature's weekly aggregation MUST be the rules declared in `specs/310-comments-visualization/spec.md` lines 75–87 ("Shared inclusion-rule contract (C1)"). This feature MUST reference that section as the authority and MUST NOT re-declare any inclusion rule.
- **FR-2-03 (weekly comments aggregate ranges over W's extracted-subset under throughput's week-attribution)**: Each numeric field of `rollup[W].comments` (`thread_count`, `comment_count`, `active_thread_count`) MUST be computed as the per-PR sum over the **extracted-subset** of W's canonical throughput PR set — that is, PRs in W's set whose `pull_requests.comments_extracted_at IS NOT NULL`. PRs in W's set that are unextracted (`comments_extracted_at IS NULL`) MUST be excluded from the sum (their contribution is zero, equivalent to omission). The numeric fields are therefore "known extracted-subset totals" — they accurately report the sum over PRs WITH extracted comment data, NOT the full-week truth. The `coverage_partial: boolean` field (per FR-2-06) flags whether any PR was excluded by the extracted-subset filter. The week-attribution rule (which determines W's canonical throughput PR set in the first place) MUST be identical to throughput's, enforced by ONE OF: (a) the comments aggregator and the throughput aggregator both delegate to a single canonical week-attribution function (no duplicate logic — the rule lives in exactly one place); OR (b) the comments aggregator implements its own week-attribution and a separate parity test asserts, for every PR in the demo dataset, that comments-aggregator-week(P) equals throughput-aggregator-week(P). Duplicating the rule's logic without one of these guards is forbidden because it allows silent drift between the two aggregators that no other contract in this spec catches. W's CANONICAL THROUGHPUT PR SET (the set the extracted-subset is filtered from) MUST include all PRs the throughput aggregator attributes to W, not just the drill-down's top-500-by-cycle-time slice. For weeks where the throughput aggregator's per-week PR set exceeds 500 PRs, the extracted-subset (and therefore the numeric fields of `rollup[W].comments`) can include PRs outside the drill-down's slice — by design, so the chart honestly reports volume across the available extracted-subset (per SC-1-01). Verification of this contract is FR-2-04 (b)'s end-to-end test (independent re-computation that applies the same extracted-subset rule) plus the FR-2-03 (a)/(b) week-attribution guard above.
- **FR-2-04 (reconciliation test — the sole weekly-comments-aggregate parity authority)**: A reconciliation test MUST be added to CI that, for every week W in the demo dataset, asserts:
  - **(a) Cross-surface coherence on the extracted-subset of the intersection** (closes FR-2-01): For every PR P in the drill-down's top-500-by-cycle-time slice for W (per 310 INV-02) AND in W's extracted-subset (P has `pull_requests.comments_extracted_at IS NOT NULL`), the per-PR `thread_count` / `comment_count` / `active_thread_count` values rendered in the drill-down (PrRecord fields per 310's contract) equal the same PR's contribution to the corresponding numeric fields of `rollup[W].comments` as computed by the aggregator. Whether the two surfaces are produced by shared or separate code paths is plan-level; the contract is value equality. PRs in the drill-down's slice that are NOT in W's extracted-subset are excluded from the pairwise check (per FR-2-01 — the drill-down renders them via 310's per-PR partial sentinel, the aggregator excludes them from the weekly sum; both surfaces agree on "no data / pending" via different conventions and are not pairwise-numeric-compared).
  - **(b) End-to-end aggregator correctness via independent re-computation** (closes FR-2-03): For week W, each numeric field of `rollup[W].comments` MUST equal the result of an independent re-computation that (i) determines W's canonical throughput PR set via DIRECT SQL against the source `pull_requests` data — NOT by calling the throughput aggregator's code, NOT by reading the throughput rollup's emitted per-week PR list, NOT by reusing any helper either aggregator uses for week-attribution. The week-attribution rule in the test re-implements throughput's rule independently, and a separate parity test (per FR-2-03 (a) or (b)) asserts the two implementations agree per-PR; (ii) filters that set to W's extracted-subset (PRs with `pull_requests.comments_extracted_at IS NOT NULL`) — applying the SAME extracted-subset rule the comments aggregator applies per FR-2-03; (iii) for each PR in the extracted-subset, applies the C1 inclusion rules (per `specs/310-comments-visualization/spec.md` lines 75–87) directly against `pr_threads` / `pr_comments`; (iv) sums the per-PR contributions; (v) computes `coverage_partial` independently as `true` if the canonical throughput PR set differs from the extracted-subset (i.e., at least one PR was filtered out at step ii) and asserts it matches the aggregator's emitted `coverage_partial` value.

  The independent re-computation MUST share no code with EITHER (1) the comments aggregator's bucket-computation path OR (2) the throughput aggregator's PR-set-determination code path. This means: NO imports from `src/ado_git_repo_insights/transform/aggregators.py` (which houses both aggregators), NO calls into helpers either aggregator uses for week-attribution, no transitive dependency on either path's query builders or aggregation utilities. The "no shared code" constraint MUST be enforced structurally via an IMPORT-BLOCK test — an AST-based assertion that the test module's transitive imports do not intersect either aggregator's imports — OR a module-boundary mechanism (e.g., the test lives in a package configured with no shared transitive imports). Code-organization convention alone is insufficient. This single end-to-end check, with the import-block extended to cover throughput as well as the comments aggregator, verifies per-PR set membership (not merely cardinality), per-PR C1 correctness across all PRs in W's extracted-subset (not just the drill-down intersection), the extracted-subset filter rule, bucket-summing math, the `coverage_partial` flag, and any drift from the Shared inclusion-rule contract — without leaning on either aggregator's own code as the source of truth for "what PRs belong to W."

  Cardinality-only or self-consistency-only checks were considered and rejected as insufficient — the aggregator could otherwise satisfy its own checks while emitting wrong values. This test is the single authority for weekly-comments-aggregate parity; the existing per-PR `PrRecord` schema-parity gate is intentionally not extended to cover the new `comments` aggregate object.
- **FR-2-05 (failure-mode meta-test — proves FR-2-04 is not silently passive)**: A meta-test MUST be added to CI that, AT MINIMUM, injects a synthetic dataset where one week's emission has `rollup[W].comments.active_thread_count > rollup[W].comments.thread_count` (violating INV-1-06) and asserts that the FR-2-04 reconciliation test FAILS on that injected dataset. The meta-test catches the failure mode where the reconciliation test silently degrades to a no-op — e.g., a future refactor short-circuits the assertion, the fixture loader stops finding the dataset, or the comparison loop skips weeks under some condition. Without FR-2-05, the reconciliation test could pass on a wrong codebase forever and no signal would surface. Additional injected bad cases (missing PR in the per-week set, off-by-one bucket sum, wrong C1 application) are recommended but not required by this spec; the spec only requires the active-vs-thread integrity violation as the minimum positive control.
- **FR-2-06 (weekly comments aggregate object emission + tests)**: When `capabilities.comments_metrics` is enabled, the aggregator's weekly rollup MUST emit a `comments` object on each week's rollup root, with EXACTLY four fields. The numeric fields are **known extracted-subset totals** (per FR-2-03) — they accurately report the sum over PRs in W's canonical throughput PR set whose `comments_extracted_at IS NOT NULL`, and exclude unextracted PRs from the sum (zero contribution). They are NOT full-week truth when the week contains unextracted PRs:

  - `thread_count: number` — per-PR sum across W's extracted-subset of per-PR `thread_count` (C1-applied per FR-2-02). Unextracted PRs contribute zero.
  - `comment_count: number` — per-PR sum across W's extracted-subset of per-PR `comment_count` (C1-applied). Unextracted PRs contribute zero.
  - `active_thread_count: number` — per-PR sum across W's extracted-subset of per-PR `active_thread_count` (C1-applied). Unextracted PRs contribute zero.
  - `coverage_partial: boolean` — `true` if AND ONLY IF at least one PR in W's canonical throughput PR set has `pull_requests.comments_extracted_at IS NULL` (i.e., at least one PR was excluded from the extracted-subset above). There is no threshold — even one such PR flips the week to `true`. When `coverage_partial` is `true`, the three numeric fields above represent KNOWN-EXTRACTED-SUBSET totals and undercount the full-week truth by the contributions of the excluded PRs; the FR-1-04 visual qualifier communicates this to the user.

  The `comments` object MUST be added to the rollup schema (`extension/ui/schemas/rollup.schema.ts`) so the chart can read it without parsing-time errors. The schema declaration MUST encode the object as optional at the rollup root and require all four fields when present (matching INV-1-08). Numeric field types MUST stay non-null (`number`, not `number | null`); the extracted-subset rule keeps them computable even when the week is partial (zero is a valid sum over an empty extracted-subset).

  When `capabilities.comments_metrics` is NOT enabled, the entire `comments` object MUST be absent from the emitted rollup (the `comments` key is absent — not `{}`-valued, not partially-populated; per FR-3-03 and INV-1-08).

  Tests added to CI MUST cover, AT MINIMUM, the cases the round-5 review locked (re-anchored to the new path notation in round 6, extended in round 7 with the extracted-subset semantics):

  - **(i) All-full case**: a week where every PR in W's canonical throughput PR set has `comments_extracted_at IS NOT NULL` produces `rollup[W].comments.coverage_partial === false` and the three numeric fields populated normally with full-week sums.
  - **(ii) Partial-extracted case (mixed week — one or more PRs missing extraction, one or more PRs extracted)**: a week where at least one PR (but not all) has `comments_extracted_at IS NULL` produces `rollup[W].comments.coverage_partial === true`, with the three numeric fields populated as PARTIAL extracted-subset sums equal to the sum over the EXTRACTED-SUBSET ONLY (the unextracted PRs contribute zero — explicit assertion: the test fixture includes both extracted and unextracted PRs in the same week, the test verifies the numeric totals match the sum over only the extracted PRs and do NOT include any contribution from the unextracted ones).
  - **(iii) All-unextracted case** (round-7 addition): a week where EVERY PR in W's canonical throughput PR set has `comments_extracted_at IS NULL` produces `rollup[W].comments.coverage_partial === true` and `thread_count === 0` AND `comment_count === 0` AND `active_thread_count === 0` (sum over an empty extracted-subset). Numeric fields STAY non-null — zero is the correct sum, not a "no data" sentinel; the `coverage_partial: true` flag plus the FR-1-04 visual qualifier are the user-facing "we don't know yet" signal.
  - **(iv) Capability-off case**: with `capabilities.comments_metrics` disabled, no week's emitted rollup contains the `comments` key at all (entire object absent, not `{}`).
  - **(v) UI rendering case (mixed partial + non-partial weeks)**: in a manifest with mixed partial / non-partial weeks, the chart's render visibly qualifies ONLY the partial-marked weeks; non-partial weeks render in the normal (non-partial) convention. (Verifies FR-1-04's "applied only to weeks marked partial, never blanket-applied" clause.)
  - **(vi) UI all-unextracted-week rendering case** (round-9 addition): a manifest week where every PR in the canonical throughput PR set is unextracted (`coverage_partial === true`, `thread_count === 0`, `comment_count === 0`, `active_thread_count === 0`) MUST render a bar element in the DOM with explicit zero-height segments AND the partial-coverage visual qualifier applied. The bar element MUST be present (not silently omitted because all values are zero), the qualifier MUST be applied (not skipped on the assumption that "zero values mean no signal"), and the comment-line series MUST NOT skip the week (the line connects through the zero point, qualified). Prevents the silent-omission failure mode where a renderer optimizes out zero-value bars and inadvertently hides the "we don't know yet" signal that the partial qualifier carries.

### Functional Requirements — Capability gating

- **FR-3-01**: When `capabilities.comments_metrics` is NOT enabled, the comments-trend chart container MUST NOT render in the Metrics tab DOM. The four pre-existing charts MUST occupy the same layout positions and sizes they did before this feature shipped.
- **FR-3-02**: When the capability flag toggles from disabled to enabled or vice versa via dataset reload, the chart container MUST appear or disappear cleanly without leaving stale geometry on the dashboard layout.
- **FR-3-03 (capability-off serialization-layer gating)**: When `capabilities.comments_metrics` is NOT enabled in a dataset, the entire `comments` object introduced by FR-2-06 MUST NOT appear on any week's rollup. The `comments` key MUST be absent — explicitly: NOT present, NOT `null`-valued, NOT `{}`-valued (empty object), NOT present-with-partial-fields. The byte-identity test gates ALL FOUR of those failure modes individually so a regression emitting any of them under capability-off is caught at CI rather than at the dashboard render layer. (The four fields inside `comments` are atomic per INV-1-08; capability-off means the whole object is omitted.) The capability-off byte-identity baseline (per FR-3-01 and SC-1-04) extends to the SERIALIZATION layer: a capability-off-variant manifest MUST be byte-identical to the pre-feature manifest with respect to the `comments` namespace. The existing demo capability-off byte-identity test (file path to be pinned at plan time per the candidates already in the repo for similar variants) MUST be tightened to gate the `comments` object explicitly per the four failure modes above.

### Cross-feature Invariants

These are inherited or extended from feature 310. They are NOT deferred decisions and MUST be honored.

- **INV-1-01 (capability gating — both surfaces)**: Both the new aggregator emission and the new chart rendering MUST be gated on `capabilities.comments_metrics`. When the flag is off, neither produces nor consumes the new fields.
- **INV-1-02 (cross-feature inclusion-rule coherence — SC-05 / INV-07 closure)**: The Shared inclusion-rule contract (C1) declared in 310's spec applies identically to this feature's weekly aggregation and to the per-PR drill-down emission, on every PR that both surfaces touch. The reconciliation test (FR-2-04) is the executable closure of 310's SC-05 obligation; its two assertions cover (a) cross-surface coherence on the drill-down ∩ aggregator intersection (FR-2-01) and (b) end-to-end aggregator correctness via an independent re-computation that grounds outside the comments aggregator (FR-2-03's verification mechanism). Cardinality-only or internal-consistency checks were considered and rejected as insufficient — they cannot detect set-membership drift or per-PR C1 violations on PRs outside the drill-down intersection. Bucket-sum-equals-drill-down-sum is intentionally NOT the contract — the drill-down's top-500-by-cycle-time cap (310 INV-02) makes that contract impossible to honor on weeks with >500 PRs without sacrificing the chart's user-value (SC-1-01).
- **INV-1-03 (C1 reference, not re-declaration)**: This spec MUST NOT contain inclusion-rule statements that re-declare 310's C1. Where C1 rules need to be invoked, this spec references the authoritative section by file:line and prose.
- **INV-1-04 (PowerBI CSV contract is frozen)**: This feature MUST NOT change the PowerBI CSV contract. (Inherits 310 INV-05.)
- **INV-1-05 (extractor is frozen)**: This feature MUST NOT change the comment extractor. Source reads stay within `pr_threads` / `pr_comments`. (Inherits 310 INV-06.)
- **INV-1-06 (active-thread-count ordering, propagated to weekly)**: For any week W where `rollup[W].comments` exists, `rollup[W].comments.active_thread_count` MUST be less than or equal to `rollup[W].comments.thread_count`. Any aggregator path that produces `active > thread` for a week is a correctness bug. (Propagates 310 INV-09 to the weekly aggregate.)
- **INV-1-07 (coverage-partial state qualification, propagated to weekly)**: When `rollup[W].comments.coverage_partial` is `true` (per FR-2-06's definition: any PR in week W's canonical throughput PR set has `pull_requests.comments_extracted_at IS NULL`), week W's rendering MUST visibly qualify the partial state. Partial-coverage qualification MUST be all-or-nothing per week — a week is either fully qualified or fully unqualified, never per-series. (Propagates 310 INV-10 semantics to the weekly aggregate's render layer; the new per-week field is the data contract that makes per-week qualification implementable, resolved 2026-04-26 after Codex stop-time review of round 5.)
- **INV-1-08 (weekly comments aggregate atomicity)**: If a week's rollup has the `comments` object present, ALL FOUR fields (`thread_count`, `comment_count`, `active_thread_count`, `coverage_partial`) MUST be present together. No partial `comments` object — either all four fields exist with values, or the entire `comments` key is absent. This mirrors 310 INV-08's per-PR atomicity contract at the per-week aggregate level, ensuring renderers never see a `comments` object with a missing field (which would force defensive null-checks on every field read). Capability-off path (FR-3-03) MUST omit the entire object, never an empty `{}` or partial-fielded one.

### Key Entities

- **Weekly comments aggregate** (new): A sub-object emitted on each week's rollup root at the path `rollup[W].comments`, containing exactly four fields: `thread_count: number`, `comment_count: number`, `active_thread_count: number` (each computed under the C1 inclusion-rule contract over W's **extracted-subset** — the PRs in W's canonical throughput PR set whose `pull_requests.comments_extracted_at IS NOT NULL`; unextracted PRs contribute zero and are excluded from the sum), plus `coverage_partial: boolean` (per FR-2-06: `true` if at least one PR in W's canonical throughput PR set has `pull_requests.comments_extracted_at IS NULL`, signaling that the numeric totals are known-extracted-subset and undercount the full-week truth). The entire object is emitted only when `capabilities.comments_metrics` is enabled (FR-3-03), and when emitted, all four fields are present together (INV-1-08 atomicity); numeric fields stay non-null even when partial (zero-valued sums are correct, not "no data" sentinels). The `comments` namespace is deliberately separate from the per-PR PrRecord fields of the same numeric names (declared at `extension/ui/schemas/rollup.schema.ts:96–98` for the per-PR scope, locked by 310's schema-parity gate) so the two surfaces never share a flat-key namespace.
- **Comments-trend chart** (new): The dashboard surface that renders weekly comments aggregates as stacked bars + overlaid line, on the Metrics tab. Reads weekly aggregates; emits drill-down activation events on bar interaction.
- **Comment thread / comment / user / PR record / capability flag** (existing — see 310 spec Key Entities for definitions).

Both properties are verified by a single reconciliation test that runs in CI for the demo dataset (FR-2-04). Bucket-sum-equals-drill-down-sum is NOT asserted — by design, each numeric field of `rollup[W].comments` can exceed the drill-down per-PR sum on weeks with >500 PRs because the aggregate honors all extracted PRs across W's full set while the drill-down inherits 310 INV-02's top-500 cap.
