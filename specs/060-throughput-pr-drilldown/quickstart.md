# Quickstart: Verify Throughput PR-level Drill-down

**Audience**: reviewer or engineer who wants to verify the feature end-to-end against a real dataset once 060 is implemented. This walkthrough maps each spec success criterion to a concrete verification step.

## Prerequisites

- Local checkout of `060-throughput-pr-drilldown` branch (or `main` after merge).
- Python 3.12+ with `pip install -e .[dev]` completed.
- `pnpm` available for extension build + tests.
- A seeded SQLite database — either:
  - Pipeline-15 artifact via `stage-artifacts` (per `reference_oddessentials_test_data.md` — requires ADO PAT); or
  - A synthetic fixture generated by `scripts/generate-synthetic-dataset.py`.

## Step 1 — Aggregator produces PR-level detail (FR-001 / FR-002 / FR-003 / FR-012)

```bash
python -m ado_git_repo_insights.cli generate-aggregates \
  --database ./ado-insights.sqlite \
  --output .tmp/060-verify
```

**Expected**:
- `.tmp/060-verify/aggregates/weekly_rollups/*.json` files exist.
- Each week with ≥1 qualifying PR has a top-level `prs` array, plus `_prs_truncated` (bool) and `_prs_cap` (int, `500`) fields.
- PR records carry exactly `{id, title, author_id, repository_id, cycle_time}` — no extras.
- Records ordered by `cycle_time desc`, with PR id ascending on ties.

**Verify byte-determinism** (FR-012 / FR-025 / SC-005 / SC-014):

```bash
python -m ado_git_repo_insights.cli generate-aggregates \
  --database ./ado-insights.sqlite \
  --output .tmp/060-verify-2nd-run

# Both runs must produce byte-identical rollup JSON:
diff -r .tmp/060-verify/aggregates .tmp/060-verify-2nd-run/aggregates
```

**Expected**: `diff` returns no differences.

## Step 2 — Extension loads and renders PR list (FR-004 / FR-006 / FR-008 / SC-001 / SC-002)

```bash
cd extension && pnpm test
```

**Expected** (Jest suite):
- `tests/modules/drilldown/throughput-drilldown.test.ts` (extended) — green.

- `tests/modules/shared/detail-panel.test.ts` (extended) — green; `PrListSection` renders across all four content states with stable `<section id="pr-detail">` identity.

Manual UI check (optional, against staged artifact):
1. Load the dashboard in the extension dev harness.
2. Click any throughput bar for a week with PRs. Panel opens; PRs section shows the list with titles, cycle times, and clickable links.
3. Click a PR link → new tab opens at the ADO PR page.

## Step 3 — Supported filter parity (SC-002 / SC-011)

With a repo filter applied at the dashboard:
1. Read the filtered `pr_count` displayed on the throughput bar for any week.
2. Click the bar. Panel opens.
3. Count the PRs rendered in the PR section → MUST equal the filtered `pr_count` UNLESS the underlying `_prs_truncated=true` and some filter-matching PRs fell outside the top-cap (in which case the truncation indicator shows both counts).
4. Repeat with an author filter; with combined author+repo filters.

**Expected**: every rendered count satisfies `rendered_count == min(filtered_prs_that_survived_aggregator_truncation, _prs_cap)` and the truncation indicator displays both `rendered_count` and `actual_filtered_count` whenever they differ.

## Step 4 — Unsupported-filter inline messages (FR-007 / FR-010 / SC-003)

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `prs` field missing from rollup for a week that has PRs | All PRs in that week have `NULL cycle_time_minutes` (e.g., still-open PRs) | Verify DB state — check `SELECT COUNT(*) FROM pull_requests WHERE closed_date IS NOT NULL AND iso_week = ?`. |
| Byte-identical diff fails | Non-deterministic field ordering, or pandas row order changed | Verify sort key is `(-cycle_time, id)` tuple; verify no `dict()` literal-order dependency. |
| Demo build fails with `PrArrayResidueError` pointing at a specific file | `strip_pr_arrays_from_rollups` detected PR residue in the source dir passed to `promote_data` | The gate is wired INSIDE `promote_data` as its first step when destination equals `DOCS_DATA_DIR`. Residue indicates a fixture or upstream producer emitted `prs` / `_prs_truncated` / `_prs_cap` that the strip pass could not remove. Check that no code path bypasses `promote_data` (see FR-023 invariant test), then fix upstream. |
| Extension test `pr-list-count-parity` fails under filter | `applyFiltersToRollups` returning stale `prs` (not filtering) | Verify the extension change wired the filter predicates to BOTH the aggregate fields and the `prs` array in the same map callback. |
| Static check finds forked classification logic | A render-path consumer is doing `filters.teams.length` directly | Move that check into `filter-support.ts`; consumer should only branch on `classification` field. |
