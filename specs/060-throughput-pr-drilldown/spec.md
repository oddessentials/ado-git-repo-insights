# Feature Specification: Throughput chart PR-level drill-down

**Feature Branch**: `060-throughput-pr-drilldown`
**Created**: 2026-04-19
**Status**: Hardened through 4 spec passes + plan Pass 2 + 4 Codex-catch revisions (see `checklists/requirements.md` for full log)
**Input**: User description: "Throughput chart PR-level drill-down: extend the existing throughput drill-down panel with an inline, top-500-truncated list of individual PR records (id, title, author_id, repository_id, cycle_time) sourced inline from the weekly rollup JSON. URL derived client-side. Supported under unfiltered/author-only/repository-only/author+repo filters; disabled with an advisory toast when team, reviewer, or comparison mode is active. Supported-but-empty opens a normal empty-state section. Demo publish boundary strips PR arrays. First slice of Phase 2 from #205/#300."
> **Note on the Input line above**: the phrase "disabled with an advisory toast when team, reviewer, or comparison mode is active" captures the pre-revision intent at the time the skill was invoked. The revised contract (FR-007 / FR-007a / FR-010) gates the PR-level detail section only, with an inline message for team/reviewer filters and the existing Phase 1 toast preserved for comparison mode. The spec body below is the authoritative statement.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Explain a weekly throughput spike with individual PRs (Priority: P1)

A user viewing the weekly PR-throughput chart sees a week with an unusually high bar and wants to understand what drove it. They click the bar and the drill-down panel opens with the set of individual pull requests that contributed to that week's count, showing each PR's title, time-to-close, and a clickable link to the pull request in Azure DevOps. The user can quickly scan titles and click through to the PRs that look most relevant to their investigation.

**Why this priority**: This is the direct realization of the owner's product principle from #205 — "every data point is an entry point into an explanation." Aggregate breakdowns (Phase 1) answered "who and where"; PR-level detail answers "which specific work." Without this, the throughput drill-down stops one step short of the decision the user is actually trying to make.

**Independent Test**: Load the dashboard with no active filter, click any throughput bar whose week has PRs. The panel opens; the "PRs" section shows a list of individual pull requests for that week with titles, cycle times, and links that navigate to the correct Azure DevOps PR URL.

**Acceptance Scenarios**:

1. **Given** the dashboard is loaded with no filter active, **When** the user clicks a throughput bar for a week with 47 PRs, **Then** the drill-down panel opens and the "PRs" section lists 47 pull requests with each PR's title, cycle time, and a working link.
2. **Given** no filter is active and a week has more than 500 PRs contributing, **When** the user clicks that throughput bar, **Then** the panel opens, the list shows 500 pull requests ordered by cycle time (longest first), and a truncation indicator communicates that additional PRs were omitted (i.e. `rendered_count=500`, `actual_filtered_count>500`; FR-008 indicator-visibility criterion is satisfied).
3. **Given** the user clicks a PR link inside the panel, **When** the click is activated, **Then** a new tab or window opens to that pull request's page in Azure DevOps.

### User Story 2 - Filtered drill-down agrees with the filtered count (Priority: P1)

A user has applied a repository and/or author filter at the dashboard level and is looking at throughput under that filter. They click a throughput bar; the drill-down panel opens and the PR list shows the pull requests that contributed to the filtered weekly count. In the common case (`_prs_truncated=false`), the number of PRs displayed in the list equals the weekly count shown on the chart. When the week was aggregator-truncated (`_prs_truncated=true`), the rendered list may be a documented strict subset of the full attribution (some filter-matching PRs fell outside the top-cap by cycle time per FR-021); the truncation indicator then displays both `rendered_count` and `actual_filtered_count` so the user sees the gap explicitly.

**Why this priority**: Filter-consistent data is a correctness contract. If the PR list disagreed with the chart's count, users would lose trust in both. Co-priority with Story 1 because the filter-consistent case is the most common real-world usage pattern — users explore specific teams / projects / people, not the unfiltered global view.

**Independent Test**: Apply a repository filter; read the weekly count on the filtered throughput bar; click the bar; verify the count of PRs listed in the panel equals `filtered_prs.length` (which equals the chart's filtered weekly count when `_prs_truncated=false`, or is a documented subset with the truncation indicator visible and both counts displayed when `_prs_truncated=true`). Fixture MUST include at least one non-truncated and one truncated fixture week. Repeat for an author filter and for both filters combined.

**Acceptance Scenarios**:

1. **Given** a repository filter is active, `_prs_truncated=false` for the week, and the filtered throughput bar shows 12 PRs, **When** the user clicks that bar, **Then** the panel lists exactly 12 pull requests, all attributed to the filtered repository, and the truncation indicator is not shown.
2. **Given** an author filter is active, `_prs_truncated=false` for the week, and the filtered throughput bar shows 5 PRs, **When** the user clicks that bar, **Then** the panel lists exactly 5 pull requests, all authored by the filtered user, and the truncation indicator is not shown.
3. **Given** repository and author filters are both active, `_prs_truncated=false` for the week, and the filtered weekly count shows 3 PRs, **When** the user clicks the bar, **Then** the panel lists exactly 3 pull requests matching both criteria, and the truncation indicator is not shown.
4. **Given** a repository filter is active and `_prs_truncated=true` for the week (the unfiltered population exceeded the aggregator cap), where the filtered throughput bar shows 20 PRs but only 5 of those fell within the top-cap by cycle time, **When** the user clicks that bar, **Then** the panel lists those 5 pull requests, the truncation indicator is visible, and the indicator displays both `rendered_count=5` and `actual_filtered_count=20` so the user sees the 15-PR gap attributed to aggregator truncation per FR-021.

### User Story 3 - Clear inline explanation when PR-level detail is unavailable (Priority: P1)

A user has a team filter or a reviewer filter active. They click a throughput bar and the drill-down panel opens exactly as it does today (Phase 1 aggregate breakdowns render unchanged); in place of the new PR-level detail section they see a clear inline explanation stating that PR-level detail is unavailable under the current filter and naming which specific filter to clear. A separate user is in comparison mode; they click a throughput bar and the existing Phase 1 comparison-mode behavior is preserved exactly unchanged — the panel does not open and the existing comparison-mode advisory toast appears.

**Why this priority**: Silent absence of a section would confuse users ("why did PR detail stop rendering?"); "best effort" partial data would violate the filter-identity contract. An explicit inline explanation is the only approach that keeps the user oriented and the data trustworthy. This slice does NOT regress Phase 1 behavior: team and reviewer filters already open the panel today (showing aggregate breakdowns), and this feature preserves that exactly — only the new PR-level detail surface is gated. Comparison mode's existing toast-denial is untouched. Co-priority with Stories 1 & 2 because the team / reviewer / comparison states are reachable in normal usage and a misleading experience in any of these states undermines the whole feature.

**Independent Test**: Apply a team filter. Click a throughput bar. Verify the panel opens, Phase 1 aggregate sections render normally, and in place of the new PR-list section an inline message appears naming the team filter as the one to clear. Repeat with a reviewer filter. Separately, activate comparison mode and click a throughput bar; verify the panel does NOT open and the existing Phase 1 comparison-mode advisory toast appears (no change from current behavior).

**Acceptance Scenarios**:

1. **Given** a team filter is active, **When** the user clicks a throughput bar, **Then** the drill-down panel opens, the Phase 1 aggregate breakdown sections (by author, by repository) render unchanged, and where the new PR-list section would appear there is an inline message naming the team filter as the one to clear to view PR-level detail.
2. **Given** a reviewer filter is active, **When** the user clicks a throughput bar, **Then** the drill-down panel opens, the Phase 1 aggregate breakdown sections render unchanged, and where the new PR-list section would appear there is an inline message naming the reviewer filter as the one to clear.
3. **Given** comparison mode is active, **When** the user clicks a throughput bar, **Then** the existing Phase 1 comparison-mode behavior is preserved unchanged — the panel does not open, the existing comparison-mode advisory toast appears, and the new PR-list section is therefore not rendered either.
4. **Given** the user activates the bar via keyboard (Enter or Space) instead of mouse click, **Then** the same behavior applies: team / reviewer filter → panel opens with inline message in place of the PR section; comparison mode → Phase 1 toast-denial preserved unchanged.

### User Story 4 - Empty supported filter opens the panel with an empty state (Priority: P2)

A user has applied a supported filter (author, repository, or both) that yields zero matching PRs for a given week. They click that week's throughput bar. The panel opens normally and the PR section shows an "empty state" explaining that no pull requests match the active filter in this week. This message is distinct in content from the inline message shown under a team or reviewer filter — it communicates "zero matches for a filter we support," not "this filter isn't supported here."

**Why this priority**: Zero matches under a supported filter is a legitimate empty result, not a gated state. Using the unsupported-filter wording here would confuse users into thinking drill-down was blocked when it simply had nothing to show. Lower than P1 because the frequency is low (most non-zero bars have some PRs), but important for internal consistency.

**Independent Test**: Choose a fixture where a repository filter yields zero matching PRs for a given week. Click that week's throughput bar. Verify the panel opens and the PR section displays a "no PRs match the active filter" empty-state message — not the unsupported-filter "clear the team/reviewer filter" message.

**Acceptance Scenarios**:

1. **Given** a supported filter is active and a given week has no matching PRs, **When** the user clicks that throughput bar, **Then** the panel opens and the PR section renders an empty-state message indicating zero matches for the active filter (not an unsupported-filter message and not a toast).
2. **Given** the empty-state message is displayed, **When** the user reads the text, **Then** it clearly indicates that zero PRs match the active filter for the week — distinct in content from the team/reviewer unsupported-filter wording.

### User Story 5 - Public demo remains aggregate-only (Priority: P1)

An external visitor views the public demo dashboard. The demo shows the same Phase 1 drill-down panels with aggregate author/repository breakdowns, but no PR titles, IDs, URLs, or any other PR-level identifying data appear in any published artifact. The PR-level detail surfaces only for end-users inside Azure DevOps, where each viewer's ADO permissions already govern what they can see.

**Why this priority**: PR titles and IDs are tenant-sensitive content. Leaking them through public demo artifacts would violate the privacy posture, be effectively irrecoverable once published, and create trust/compliance risk with real customers. Co-priority with the functional P1 stories because a single accidental publication could undo weeks of user trust.

**Independent Test**: Inspect every weekly-rollup artifact in the published demo surface. Verify no artifact contains a PR-record array, a truncation flag, or any PR-identifying text. Verify the demo dashboard continues to render Phase 1 aggregate drill-down panels without errors.

**Acceptance Scenarios**:

1. **Given** the demo publish process has run, **When** an auditor inspects any published weekly-rollup artifact, **Then** no PR-record array, truncation flag, or PR-identifying field is present.
2. **Given** a user loads the public demo dashboard, **When** they click a throughput bar, **Then** the drill-down panel opens with Phase 1 aggregate breakdowns only (the "PRs" section is absent) and no error is displayed.
3. **Given** the demo publish process is re-run idempotently, **When** output is inspected, **Then** results remain PR-free regardless of how many times the process runs.

### Edge Cases

- **Exactly at aggregator truncation boundary (no filter active)**: a week with exactly 500 PRs has `_prs_truncated=false`, renders all 500 with no truncation indicator. A week with 501 PRs has `_prs_truncated=true`, `prs.length=500`, `rendered_count=500`, `actual_filtered_count=501`, so FR-008's indicator-visibility criterion (`rendered_count < actual_filtered_count`) is satisfied and the indicator is shown.
- **Filter applied to a truncated week — aggregator-omitted filter matches**: a week has 600 PRs (aggregator-truncated to top-500). An author filter matches 20 of the 600; 5 of those 20 are in the top-500. `rendered_count=5`, `actual_filtered_count=20`, `_prs_truncated=true`. FR-008 criterion satisfied → indicator visible showing "5 of 20." This is a truncation state driven by the filter-× aggregator-cap interaction, not by the week's unfiltered size alone.
- **Filter applied to a truncated week — no aggregator-omitted filter matches**: same 600-PR truncated week. An author filter matches 3 PRs, all 3 in the top-500. `rendered_count=3`, `actual_filtered_count=3`, `_prs_truncated=true`. FR-008 criterion NOT satisfied (`rendered == actual`) → indicator hidden. `_prs_truncated` remaining true is the aggregator-state flag; it does not drive indicator visibility on its own.
- **Tied cycle times**: when two PRs have identical cycle times, the tie is broken deterministically by PR id ascending, so ordering is reproducible across runs on the same data.
- **Multiple unsupported filters active together** (e.g. team AND reviewer): the panel still opens (Phase 1 behavior preserved); the inline message in place of the PR section names one filter dimension (deterministic precedence: team then reviewer). Clicking repeatedly does not change the rendered message.
- **Comparison mode AND a team filter active**: Phase 1's comparison-mode denial takes precedence — the panel does not open and the existing comparison-mode toast appears. The team-filter inline message is never reached because the panel never opens.
- **PR record with missing or empty title**: renders as an empty title cell; the PR row is still present and the link still resolves via PR id.
- **PR record with null cycle time**: excluded from the PR list for that week (the record cannot be ordered under the cycle-time sort key and would not be part of the closed-PR population that the weekly count represents).
- **Repository name missing from the repositories dimension**: the PR link falls back to a numeric-id-only URL form that Azure DevOps still resolves correctly, so the user can still navigate to the PR.
- **Filter changes while panel is open**: hard-dismissal behavior from Phase 1 applies (panel closes; no content revalidation). Opening after a filter change reflects the new filter state.
- **Tab switch or comparison mode toggled while panel is open**: existing Phase 1 dismissal semantics apply unchanged.
- **Same bar activated twice in succession**: second activation follows Phase 1's retarget / re-open behavior; no divergence from the existing contract.
- **Rollup artifact missing the PR array entirely** (e.g. demo publish output or older artifact): the PR-detail container still renders (per FR-020) with a supported-filter empty-state message; the Phase 1 aggregate sections render normally. The panel never omits the container itself — absence of data becomes a content state, not a missing element.
- **Repository id present in a PR record but absent from the `repository_id → repository_name` dimension mapping**: the row renders with a numeric-id fallback URL (which Azure DevOps still resolves). The row is not blanked, dropped, or silently hidden. The parity test for mapping completeness (FR-005a) catches the underlying data issue separately.
- **Two consecutive aggregate runs against the same database**: produce byte-identical weekly-rollup output including PR record order, tested via the determinism test (FR-025, SC-014).
- **PR title edited in ADO between two extracts**: the updated title appears in the next rollup's PR record after a re-aggregate; the previous title does not appear. Enforced by the snapshot-cadence integration test (FR-022, SC-012).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Each weekly rollup artifact MUST carry an optional list of per-PR records for the weeks that have contributing pull requests. Each record carries exactly five fields: PR id (integer), title (string), author identifier, repository identifier, and cycle time in minutes.

   **Backward-compat guarantee (load path)**: absence of the `prs` field is a valid, supported, permanent state of the artifact — not a bug, not an error, not a load-warning trigger. Rollups produced by the aggregator before this feature shipped, rollups emitted for weeks with zero qualifying PRs, and rollups under `docs/data/` (where PR arrays are stripped at the publish boundary per FR-023) are all legitimate examples. Consumers MUST render the supported-empty content state of the PR-detail container (per FR-020 state `"supported-empty"`) in every case where the rollup lacks a `prs` field and no unsupported filter is active. No consumer may refuse to render the panel, log an error, or degrade any other drill-down surface based on `prs` absence. This backward-compat clause is a permanent contract, not a transition policy — future aggregator versions that omit `prs` for any reason MUST remain loadable without consumer change.
- **FR-002**: The per-PR list MUST be limited to at most 500 records per week, ordered by cycle time descending, with ties broken deterministically by PR id ascending.
- **FR-003**: The contract surface for truncation state MUST expose exactly four accessors, locked now as the single source of truth for every consumer (panel UI, tests, future downstream):
   1. `_prs_truncated` (new rollup field, boolean): set by the aggregator to TRUE iff the week's unfiltered PR population exceeded the cap at aggregation time, causing the rollup's `prs` array to be a top-cap subset rather than the full week population. FALSE otherwise (or field absent when no `prs` field is present).
   2. `_prs_cap` (new rollup field, integer): the numeric cap applied by the aggregator when producing this rollup's `prs` array. Emitted on every rollup that carries a `prs` field so consumers never hardcode the cap; future cap changes are self-describing in the artifact.
   3. `rendered_count` (derived by the UI): the length of the `prs` array after the active supported filters have been applied (i.e., `filtered_prs.length`). Computed from the payload; never independently recomputed.
   4. `actual_filtered_count` (derived by the UI): the filtered `pr_count` from the filtered rollup returned by `applyFiltersToRollups`. Read from the payload; never independently recomputed.

   Consumers MUST NOT compute `_prs_truncated` or `_prs_cap` independently; both are read from the payload. **Flag values are immutable after load**: consumers MUST NOT mutate either field after receiving the rollup object, and MUST NOT re-derive `_prs_truncated` from observed `prs.length` (e.g., via `prs.length === _prs_cap`) because cap values can change across releases and inference would silently produce wrong results. Determinism depends on flag values traveling unchanged from the aggregator to every downstream consumer. The truncation indicator (FR-017) MUST use `rendered_count` and `actual_filtered_count` together when they differ, so users see both the visible rendering and the underlying filtered population.
- **FR-004**: The throughput drill-down panel MUST display the PR list as a distinct section alongside (after) the Phase 1 aggregate breakdown sections. Each row MUST show the PR title, its cycle time, and a way to navigate to the pull request in Azure DevOps.
- **FR-005**: The system MUST NOT persist the pull-request web URL in any rollup artifact. Navigation URLs are composed at render time from the PR id, the repository identifier, and the active Azure DevOps context.
- **FR-005a**: The `repository_id → repository_name` mapping required for URL composition MUST be emitted by the aggregator in the dimensions artifact on every non-demo aggregate-generation run (i.e., every run that produces PR records), and MUST be loadable by the extension at dashboard load time before any drill-down activation. Non-demo load paths are defined as: the Azure DevOps extension consuming a tenant's own aggregates (where PR records are present). Demo load paths are those consuming the public-stripped artifacts under `docs/data/` (where PR records are absent — URL composition is never exercised in that path). The mapping MUST be byte-identical across every dashboard entry point that is subject to parity enforcement. A parity test MUST fail if any of: (i) the mapping is absent from a non-demo dimensions artifact, (ii) the mapping is missing any `repository_id` referenced by any PR record in the loaded rollups, (iii) the mapping differs in any value between entry points. When a repository_id cannot be resolved at the UI level (fixture-only or future dataset corruption), the panel MUST fall back to a numeric-id-only URL form (edge case covered above) and MUST NOT crash, blank the row, or silently drop the link.
- **FR-006**: When no filter is active, or when only an author filter, only a repository filter, or both author and repository filters are active, clicking a throughput bar MUST open the drill-down panel with the PR list rendered.
- **FR-007**: When a team filter or a reviewer filter is active, clicking a throughput bar MUST open the drill-down panel exactly as Phase 1 opens it today (all Phase 1 aggregate content intact), and the new PR-level detail section MUST NOT render. In place of the PR-level detail section, an inline explanatory message MUST appear at the same location within the panel, naming the specific filter dimension (team or reviewer) that the user must clear to view PR-level detail. This feature MUST NOT change whether the panel opens in any filter state; the gate operates at the PR-section granularity only.
- **FR-007a**: When comparison mode is active, Phase 1's existing comparison-mode denial behavior MUST be preserved exactly unchanged — the panel does not open and the existing Phase 1 comparison-mode advisory toast is shown. Because the panel does not open, the new PR-level detail section is not rendered; no new inline message is needed for this case.
- **FR-008**: Under any supported filter state, the count of PR records rendered in the panel MUST equal `rendered_count` (per FR-003) — which is `filtered_prs.length`, the length of the post-filter array produced by the same single operation as the filtered `pr_count` (per FR-021). The truncation indicator (FR-017) MUST be visible whenever `rendered_count < actual_filtered_count` and MUST display both values. A test MUST fail if, for any supported filter state and any fixture week, the rendered count diverges from `filtered_prs.length` OR the truncation indicator's visibility diverges from `rendered_count < actual_filtered_count`.

   **Note on aggregator-truncation interaction**: when the aggregator has truncated the unfiltered PR population (`_prs_truncated=true`), applying a supported filter to the already-truncated array may yield a `rendered_count` that is smaller than the `actual_filtered_count` computed from the aggregate breakdown slices (because some filter-matching PRs were outside the top-cap by cycle time). This is the expected and documented behavior; the two-count display in the truncation indicator is how the user sees the gap. When `_prs_truncated=false`, the two counts are always equal.
- **FR-009**: Under a supported filter state with zero matching PRs for a given week, the panel MUST open normally and render a distinct "empty" presentation for the PR section, not an inline unsupported-filter message.
- **FR-010**: The inline explanatory message rendered in place of the PR section under a team or reviewer filter MUST be a persistent section-level presentation (not a transient toast), placed at the location where the PR section would otherwise appear, naming the specific filter dimension to clear, and announced to assistive technology as a status change (not as an interrupting alert). Phase 1's transient comparison-advisory toast pattern is retained for the comparison-mode case only (per FR-007a) and is not reused for team / reviewer cases.
- **FR-011**: The throughput bar's visible affordance (cursor, accessible name, keyboard focusability) MUST remain in place across every supported and unsupported filter state. Activation semantics are preserved from Phase 1: team / reviewer filters open the panel (with the PR section gated); comparison mode shows the Phase 1 toast; supported filters open the panel with the PR section rendered.
- **FR-012**: The system MUST produce byte-identical rollup artifacts across independent runs given identical source data, including identical PR ordering and content.
- **FR-013**: Weekly rollup artifacts published to any public or demo surface MUST NOT contain PR record arrays, the truncation marker, or any field derived from a PR record. Enforcement mechanism: FR-023 (strip gate invoked inside `promote_data`).
- **FR-014**: The project MUST include a written privacy posture section added to `docs/reference/dataset-contract.md` that states, in plain language:
   1. Private / tenant rollup artifacts (consumed inside the Azure DevOps extension against a tenant's own data) MAY contain per-PR arrays (the `prs` field), truncation markers, and PR-level identifying content.
   2. Promoted demo and public artifacts (anything under `docs/data/` or any other public-surface output) MUST NOT contain per-PR arrays, truncation markers, or any PR-identifying field; these MUST be stripped at the publish boundary (FR-023).
   3. This posture extends to other tenant-sensitive fields introduced in the future — the same strip-at-publish rule applies by default unless a new scoped decision grants an exception.

   Ordering constraint: the `docs/reference/dataset-contract.md` change MUST land in the same atomic commit as (or precede) the first code change in the branch that produces a `prs` field in any artifact. No commit in the branch's history may contain PR-array-producing code without the documented privacy posture already in the tree.

   **Enforcement (mechanized, not procedural)**: an automated gate MUST fail CI and the local pre-push hook if BOTH of the following hold: (a) the branch tree contains aggregator code that can emit `prs` (detected by grep for the literal key `"prs"` inside `src/ado_git_repo_insights/transform/aggregators.py` combined with an AST check that the key appears in an output-dict assignment, OR by the presence of a `PrRecord` TypedDict in `src/ado_git_repo_insights/types.py`); AND (b) `docs/reference/dataset-contract.md` does not contain the privacy-posture section (detected by grep for the locked section heading text, e.g., a stable anchor string defined once in the doc). Implementation as a single authoritative test (e.g., `tests/unit/test_privacy_posture_ordering.py`) invoked by name from pre-push and CI — no procedural reliance on reviewer diligence. The test MUST pass on commits that either contain neither (a) nor (b), OR contain both; it MUST fail the commit that introduces (a) without (b). Git-history-rewrite operations within the branch MUST preserve this ordering (the test runs against the working tree, not the commit graph; rebases that violate the ordering fail on pre-push regardless).
- **FR-015**: All Phase 1 drill-down behavior — including panel open/close semantics, focus management, dismissal reasons, existing aggregate breakdown rendering, sparkline navigation, cycle-time and reviewer drill-downs, and existing advisory-toast copy — MUST remain unchanged by this feature.
- **FR-016**: Keyboard activation of a throughput bar (Enter or Space) MUST exhibit the same supported / disabled / empty behavior as mouse-click activation.
- **FR-017**: The truncation indicator for the PR list MUST be visible exactly when FR-008's criterion holds (`rendered_count < actual_filtered_count`) — i.e., driven by the display-state counts, NOT by the aggregator-state `_prs_truncated` flag alone. Its placement and copy pattern MUST be consistent with the Phase 1 truncation indicator used for other chart surfaces. When visible, it MUST display both `rendered_count` and `actual_filtered_count` so the user can see the exact gap.
- **FR-018**: The classification of a filter state as supported or unsupported MUST depend only on which filter dimensions are active — not on whether those filters produce matches — so that an empty supported filter opens the panel with an empty PR section (per FR-009) while a team or reviewer filter opens the panel with an inline unsupported-filter message in place of the PR section (per FR-007) even when those filters would have matched some PRs.
- **FR-019**: Phase 1's existing behavior of rendering unfiltered `by_author` and `by_repository` aggregate breakdowns under any active filter state MUST remain unchanged by this feature. Addressing that pre-existing inconsistency is explicitly out of scope for this slice; any correctness guarantees introduced here apply only to the new PR-level detail surface.
- **FR-020**: The PR-detail area MUST be expressed as a SINGLE new variant of the sealed `PanelSection` discriminated union in `extension/ui/modules/shared/detail-panel.ts` (alongside the existing `BreakdownTableSection` / `StatRowSection` / `EmptyStateSection`). The new variant carries an internal `contentState` discriminant with exactly four values: `"pr-list"`, `"supported-empty"`, `"team-inline"`, `"reviewer-inline"`. The variant's render function MUST always return the same stable `<section>` element (same tag, same stable class/id/role identifying it as "the PR-detail area", same position among sibling sections); only its children swap based on `contentState`. Forbidden patterns (each would break the determinism contract): introducing multiple sibling `PanelSection` variants for the four states; conditionally including/omitting the section from `PanelContent.sections` at `buildPanelContent` time; branching the render switch on anything other than the `contentState` discriminant. Tests MUST assert container presence and stable element identity across all four content states.
- **FR-021**: Under any supported-filter state (including combined author+repository), the filtered PR array and the filtered `pr_count` MUST be produced by a single invocation of `applyFiltersToRollups` (or its direct authoritative replacement). The function operates as ONE input-to-output transform: one input rollup object, one pass over the active dimension predicates, one output containing both the filtered aggregate fields and the filtered `prs` array on the same rollup object. Forbidden (each is a design break): a parallel filter function; a cached intermediate between the aggregate filter and the PR-list filter; a second invocation of filter logic for the PR list; a conditional branch that routes `prs` filtering through any code path other than the one that produces `filtered_pr_count`; any post-processing pass that re-filters `prs` after the function returns.

   **Filter × aggregator-truncation interaction is intentional lossy behavior**: when the rollup's `prs` array is the full week population (`_prs_truncated=false`), the set of PR records rendered in the panel MUST be element-wise identical to the set of PRs that the aggregate filter code path attributes to the week. When the rollup's `prs` array is a top-cap truncated subset (`_prs_truncated=true`), the rendered set MUST be the filter applied to the aggregator-truncated array — i.e., **a documented strict subset of the full aggregate-attribution set**. This loss is BY DESIGN at the aggregator boundary (not a consumer-side degradation) and is surfaced by the truncation indicator per FR-008 / FR-017 displaying both `rendered_count` and `actual_filtered_count`. Consumers MUST NOT attempt to recover the omitted PRs by any means (no second fetch, no live DB query, no alternative data path) — the subset is the contract. Tests MUST cover both the `_prs_truncated=false` element-wise-identical case and the `_prs_truncated=true` subset case.
- **FR-022**: The snapshot-cadence contract (PR content in rollups reflects the database state at the moment of aggregation and updates on the next extract+aggregate cycle) MUST be enforced by an automated integration test that: (a) generates a rollup from a fixed database state; (b) modifies a PR title in the source database; (c) re-runs the aggregator; (d) asserts the updated title appears in the new rollup's PR record and the previous title does not.
- **FR-023**: The single authoritative write boundary into `docs/data/` is the existing `promote_data` helper at `scripts/build-demo-dataset.py:1044`. All production code paths that publish to `docs/data/` flow through this one helper. The privacy-safety guarantee for this feature operates at that single boundary plus a hard rule against bypass paths.

   **Actual invocation flow (source-verified)**: `scripts/build-demo-dataset.py` orchestrates demo generation. Its `GENERATOR_STEPS` list (line 54) runs `generate-demo-data.py` via `run_generator(script_name, ARTIFACT_DATA_DIR)` at line 1095, passing `ARTIFACT_DATA_DIR` explicitly as the output root — so `generate-demo-data.py`'s `DEFAULT_OUTPUT_DIR = docs/data/` (line 105) is NEVER exercised in the orchestrated/production flow. It is only reachable via standalone developer invocation. After the generators complete, `build-demo-dataset.py` calls `promote_data(ARTIFACT_DATA_DIR, DOCS_DATA_DIR)` at line 1120. There is ONE production write to `docs/data/`.

   **Gate placement (single authoritative site)**: the strip gate MUST be invoked as the FIRST step of `promote_data` when the destination is `DOCS_DATA_DIR` (or any configured public-surface root). This places the gate at the one authoritative boundary. The gate MUST fail the build if any rollup artifact at the source location contains any of: a `prs` field, a `_prs_truncated` marker, a `_prs_cap` marker, or any PR-identifying field at PR granularity (PR id, PR title, PR author_id, PR repository_id attached to a PR record, or any derived URL). The gate MUST be a single authoritative helper (one function in one module — the `strip_pr_arrays_from_rollups` helper from `contracts/demo-strip-gate.md`) invoked by name — no copy-pasted inline checks. The gate MUST strip-and-re-verify: it strips PR-level fields in the source location, then re-scans and fails if residue remains.

   **Privacy-safety invariant (gate-before-copy inside `promote_data`)**: because the gate runs INSIDE `promote_data` before its `shutil.copytree` step, a gate failure MUST prevent the copytree from running. On gate failure, `docs/data/` is therefore byte-identical to its pre-run state — not because the promotion step is rename-based atomic (it is not), but because the copy step never executes. A synthetic leak-test case MUST (a) inject PR residue into the source directory, (b) invoke `promote_data`, (c) confirm the gate fails hard and raises, (d) confirm `promote_data`'s copy step is NOT invoked, (e) confirm `docs/data/` is byte-identical to its pre-run state.

   **Known non-atomic copy step (acknowledged pre-existing behavior)**: the existing `promote_data` helper is implemented via `shutil.copytree(dirs_exist_ok=True)` + stale-file cleanup + content-match validation. It is NOT rename-based atomic. A crash DURING `promote_data`'s copy step — after the gate has successfully run — MAY leave `docs/data/` partially updated; however, any partial state would contain ONLY stripped output (no PR residue), because the gate has already cleaned the source. Upgrading `promote_data` to rename-based atomicity is a pre-existing repo concern out of scope for feature 060.

   **Bypass-prevention for the standalone developer path**: because `generate-demo-data.py`'s `DEFAULT_OUTPUT_DIR` is `docs/data/`, a developer who runs the script standalone would bypass `promote_data` and write directly into `docs/data/` — defeating the gate-at-`promote_data` strategy. This feature MUST close that bypass by ONE of:
   (a) Changing `generate-demo-data.py`'s `DEFAULT_OUTPUT_DIR` to a scratch location that is NOT `docs/data/`;
   AND/OR
   (b) Adding an early-exit guard at the top of `generate-demo-data.py` that raises when the resolved `--output-root` equals `DOCS_DATA_DIR`, printing a clear "use `build-demo-dataset.py` to publish to docs/data" message.

   Option (a) + (b) together are preferred (defense in depth). The orchestrated flow is unaffected because `build-demo-dataset.py` passes `ARTIFACT_DATA_DIR` explicitly and never uses the default. A static invariant test (grep or AST) MUST fail the build if any file under `scripts/` or `.github/workflows/` writes into `docs/data/` by any means OTHER than a call to `promote_data` — this prevents future bypasses.
- **FR-024**: The classification of a filter state as supported or unsupported — including team-filter-active, reviewer-filter-active, and comparison-mode-active detection — MUST be expressed as a single authoritative predicate. The UI code that gates PR-section rendering, the test code that asserts gating behavior, and any future consumer that needs the same classification MUST all import and use the same predicate. Forking detection logic across surfaces (e.g. one `!!filters.teams.length` check in the PR-section render path and a different check elsewhere) is forbidden. A test MUST assert that at least the rendering path and the test fixture path call the same exported predicate.
- **FR-025**: Determinism of PR record ordering — `cycle_time` descending with a stable tie-break by `id` ascending — MUST be proven by an automated test that runs the aggregator twice against a fixed database state that includes PRs with identical cycle times, compares the resulting rollup JSON byte-for-byte, and fails if any byte differs. The tie-break direction (`id` ascending) is locked: changing it would be a breaking schema change requiring an explicit scope revision.
- **FR-026**: When multiple unsupported-filter conditions could apply simultaneously, the unsupported-filter predicate (FR-024) and every consumer of its result MUST apply this fixed, total precedence:
   1. Comparison mode active → classify as `comparison`; panel does not open; Phase 1 toast-denial (per FR-007a).
   2. Otherwise, team filter active → classify as `team`; panel opens; PR-detail container renders the team-filter inline message (per FR-007).
   3. Otherwise, reviewer filter active → classify as `reviewer`; panel opens; PR-detail container renders the reviewer-filter inline message (per FR-007).
   4. Otherwise, no unsupported conditions → classify as `supported`; panel opens; PR-detail container renders the PR list (per FR-006) or the supported-empty state (per FR-009).

   The predicate MUST be a single exhaustive classifier returning a discriminated result `{ classification: "comparison" | "team" | "reviewer" | "supported" }`. Call-site reconstruction of precedence from independent boolean checks (e.g. separate `isTeamActive()` + `isReviewerActive()` branches) is FORBIDDEN. A test MUST assert that comparison+team, comparison+reviewer, team+reviewer, and comparison+team+reviewer all classify correctly under this precedence.

### Key Entities *(include if feature involves data)*

- **PR Record**: A single pull request attributed to a weekly rollup. Carries exactly five attributes: numeric PR id (navigation key), title (human-readable subject), author identifier (ties to the Author dimension), repository identifier (ties to the Repository dimension and is the input to URL composition), cycle time in minutes (the sort key).
- **Weekly Rollup (extended)**: The existing aggregate artifact for one ISO week, now optionally carrying a PR Record list and, when applicable, a truncation marker. All Phase 1 fields remain unchanged.
- **Filter State (classified)**: The existing dashboard filter construct. For drill-down purposes, filter states are classified as supported (none, author-only, repository-only, author + repository) or unsupported (team active, reviewer active, comparison mode active). No new fields are added to the filter state itself.
- **Drill-down Advisory (existing)**: The existing short, transient, toast-style message introduced in Phase 1 for comparison mode. Preserved unchanged and used only for comparison mode. This spec does NOT reuse it for team or reviewer filters.
- **Unsupported-filter Inline Message (new)**: A persistent content-slot message rendered inside the PR-detail container, naming the team or reviewer filter the user needs to clear. Separate UX pattern from the transient toast (persistent vs transient; container-content vs floating; status vs alert). The message is a content state of the container defined below, not a separate container.
- **PR-detail Container (new, stable across filter states)**: A single stable DOM container rendered within the drill-down panel whenever the panel is open. Always present with identical element identity, sibling position, and ARIA identity. Content switches deterministically among four states: rendered PR list (with optional truncation indicator), supported-filter empty-state, team-filter inline message, reviewer-filter inline message. Guarantees layout stability for snapshot testing and for assistive technology announcements.

   **Terminology note**: other sections of this spec use colloquial synonyms ("PR section", "PR list section", "PR-level detail section") to refer to the same DOM container defined here. "PR list" refers specifically to this container's rendered-list content state (the `"pr-list"` discriminant). All uses resolve to the single `<section id="pr-detail">` element defined by FR-020.
- **Unsupported-filter Predicate (new, single authoritative function)**: A single exported function that takes the active filter state and returns whether any unsupported dimension (team, reviewer, comparison) is active and which one. Single source of truth consumed by the UI, by tests, and by any future consumer needing the same classification.
- **Repository Name Mapping**: The existing dimensions-artifact `repository_id → repository_name` mapping. This feature adds a parity requirement: the mapping MUST be present at dashboard load time and MUST be identical across dashboard entry points. Any PR record's `repository_id` that cannot be resolved through this mapping triggers the numeric-id URL fallback.
- **Privacy Posture (new documented contract)**: A project-level written declaration identifying classes of tenant-sensitive fields and prescribing their removal from public/demo publication surfaces. First instance covers PR titles and ids; written to extend to future fields.

## Success Criteria *(mandatory)*

## Assumptions

- Users viewing PR-level drill-down inside the Azure DevOps extension already have ADO permission to view the underlying pull requests; PR titles and ids are not newly exposed to them by this feature.
- Public and demo surfaces are assumed to have zero tenant-data access rights; therefore stripping PR records at the publish boundary is sufficient privacy mitigation for the Phase 1 public surface.
- The existing repositories dimension carries sufficient repository-name information to compose human-navigable pull-request URLs from a PR id and repository identifier at render time.
- The Azure DevOps web context available to the running extension provides the organization and project identifiers needed for URL composition.
- A per-week cap of 500 PR records is sufficient to satisfy the "explain the spike" user value even for very high-throughput weeks, validated against the M1 measurement where real-seed weeks peaked at 464 PRs.
- Cycle time in minutes is well-defined for every PR that contributes to the weekly count; PRs without cycle time are not part of the weekly count population and are therefore not part of the PR list.
- The aggregator produces the per-week PR list with a deterministic sort (cycle-time descending, id ascending). This is the only sort performed; the extension does not re-sort client-side. Determinism therefore depends on the Python side alone and is enforced by byte-identical-output tests (FR-025, SC-014).
- Adding the PR-record array to the rollup artifact stays within the existing 500 KB per-file cap even at worst-case enterprise scales (validated by M2 measurement).
- Phase 1's existing aggregate breakdown drill-down behavior is retained as-is in this slice. This includes: (a) the panel opening under team and reviewer filters exactly as it does today; (b) the `by_author` / `by_repository` aggregate sections rendering unfiltered even under active filters (the pre-existing inconsistency). The new filter-identity contract (FR-008, SC-002) applies strictly to the new PR-level detail surface only. Any future unification of the Phase 1 aggregate surface with the new stricter contract is a separate scoped change.

## Out of Scope

- Team-filter support for the PR-level drill-down (the user must clear the team filter to view PR-level detail).
- Reviewer-filter support for the PR-level drill-down (the user must clear the reviewer filter to view PR-level detail).
- Comparison-mode PR-level drill-down (deferred; Phase 1 comparison-mode behavior preserved unchanged).
- PR-level drill-down for the cycle-time, reviewer-activity, or summary-card-sparkline chart surfaces.
- URL-bookmarkable drill-down state carrying a selected PR.
- PR-level detail on the CSV or PowerBI export surfaces.
- Upgrading Phase 1's `by_author` and `by_repository` aggregate breakdowns to also honor the stricter filter-identity invariant introduced here (they continue to render unfiltered under any filter state, exactly as Phase 1 shipped).
- Changing whether the throughput drill-down panel opens under team or reviewer filter (it continues to open exactly as Phase 1 does; only the new PR-level detail surface is gated).
- Expansion of PR-record field set beyond the five explicitly scoped fields (id, title, author identifier, repository identifier, cycle time).
- Cross-dimensional aggregates needed to expand supported filters in future slices.
- Snapshot-cadence changes: PR titles may lag between an upstream edit and the next aggregate-generation run; this matches the existing pipeline snapshot cadence and is not tightened here.
- Helper-extraction shape inside the aggregator. Whether the aggregator inlines PR-record construction at `_generate_weekly_rollups` or extracts a `_build_pr_records(group)` helper is an implementation choice, NOT a spec contract. The spec anchors behavior (sort order, truncation, payload fields, determinism); it does not mandate internal function boundaries. Any helper-extraction suggestion in `code-surface-map.md` is a non-contractual planning hint.
